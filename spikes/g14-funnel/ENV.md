## 코드 버전과 한계 (정직한 기록)
- 측정 시점의 스크립트는 **커밋 전 작업 트리**였다. 결과 JSON 의 `commit` 은 직전 커밋(`71802e2`)이고 `dirty` 필드는 **신뢰할 수 없다**(경로 기준 버그로 항상 false 가 나왔다 — 수정함). 스크립트를 커밋한 뒤 그 커밋 해시를 이 파일 맨 아래에 추가한다.
- `client.ts` 는 측정 도중 보강됐다. 결과의 `options`·시각으로 버전을 구분한다.
  1. 최초: `headers`, `ws-echo`, `idle`, `throughput`, `http` (01:35~01:38)
  2. `ws-connect` 추가 (01:38:44 이후)
  3. `http` 의 오류를 메시지별로 분류 (01:39:54 이후; 01:39:35 파일은 `error` 한 항목으로 집계)
  4. `throughput --par` 추가 (01:45 이후; 01:40:47 파일은 단일 다운로드)
  5. 결과 파일명에 pid 추가, `ws-watch` 추가, dirty 판정 수정 (01:55 이후)
- **결과 파일 하나가 덮어써졌다**: `idle --hb=0` 과 `--hb=25` 를 같은 밀리초에 띄워 같은 파일명이 됐고, 남은 것은 `hb=25`(`...-idle-hb25.json`)다. `hb=0` 결과는 표준출력 로그(`2026-11-10-idle-hb0.stdout.log`)로만 남아 있고 서버 로그(`notes.md`)가 대조 증거다.
- **클라이언트 시계가 서버 시계보다 느리다.** 같은 유휴 시험을 클라이언트는 889.2초, 서버는 960.0초로 쟀다(비율 0.926). 40초 대조 측정(`control-clock-rate.ts`)에서도 0.934 였다. **지속 시간은 서버 시계를 기준**으로 삼고, 클라이언트 `performance.now()` 로 잰 처리량·지연은 약 7% 불확실성이 있다.
- 원시 결과의 **클라이언트 공인 IP 는 `<CLIENT_PUBLIC_IP>` 로 치환**했다(`headers` 결과 한 곳). 서버 공인 IP 와 시험 토큰은 결과에 없다.
- 로컬 대조 결과는 파일명에 `LOCAL-control` 이 붙어 있다(Funnel 을 거치지 않음).
- 저장하지 못한 관찰: Funnel 을 처음 켠 직후의 WebSocket 실패 2건(첫 `ws-echo`, 첫 업그레이드 프로브)은 결과 파일이 없다(`ws-echo` 는 저장 전에 예외로 종료). 서버 로그의 첫 `upgrade` 시각으로 ‘원점에 도달하지 않았다’는 것만 확인했다(`notes.md`).

## 증거 커밋
- 스크립트·원시 결과·이 파일을 처음 커밋한 해시: `33eea7b` (2026-11-10). 이 커밋의 `client.ts` 는 위 v5 이며, v1~v4 에서 만든 결과 파일은 당시 버전으로 얻은 것이다(v5 는 상위집합).
- 이후 핵심 수치(대역폭 합계·동시 연결 임계)는 다른 출발지 측정 때 이 커밋 이후 버전으로 다시 잰다.

## 2차 측정(04:14~04:44 UTC)의 실행 방식과 한계
- 서버에는 소스를 두지 않았다. 저장소를 Docker 볼륨에 `git clone --depth 1` 로 받아 읽기 전용으로 붙여 실행했고, 실행 코드는 커밋 `5e1ffb82e1ef93b3639297c0a7ef78f59a8c1900` 이다(`notes.md` §4). 서버 Bun 1.3.11.
- 이 날 2차 결과의 `dirty=true` 는 코드가 달라서가 아니라 `results/` 에 아직 커밋하지 않은 새 결과 파일이 있기 때문이다(`git diff 5e1ffb8 -- spikes/g14-funnel/*.ts lab.html` 이 비어 있음을 확인).
- **출발지는 개발 PC, 휴대폰, 서버 자신(자기 공개 주소로 돌아오는 경로) 세 곳**이다. 서버 자신은 송수신과 암호화를 한 장비가 모두 해서 다른 출발지와 조건이 같지 않다.
- **시간 변동이 크다.** 같은 개발 PC·같은 조건의 병렬 4 합계가 01:46 UTC 2.28MB/s, 04:34 UTC 0.64MB/s, 04:36 UTC 0.50MB/s 였다. 두 회선(서버 업로드 12.1MB/s, 개발 PC 다운로드 48~62MB/s)은 그대로였으므로 Funnel 경로의 변동이다. 이 변동의 원인은 모른다.
- 동시 시험은 서버 쪽이 `ECONNRESET` 으로 끊겨 성립하지 않았다. ‘합계 상한이 출발지별인가 전체인가’는 **미결**이다.
- 2차 측정(재시작·인증서·휴대폰·서버 출발지) 결과와 기록: `98bf45a` (실행 코드는 `5e1ffb8`).
