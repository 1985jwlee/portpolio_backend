# G2 — Bun WebSocket 장시간 안정성 (S0-2)

[tech-stack §11](../../docs/domains/tech-stack.md) 관문 G2, [design/11 S0-2](../../docs/design/11-implementation-plan.md), 송신 큐 설계는 [design/features/14-realtime.md](../../docs/design/features/14-realtime.md) §3.1·RT-06. **제품 코드가 아니다**(스파이크). 결과는 [ADR-050](../../docs/adr/ADR-050-evidence-rule.md) 에 따라 스크립트·원시 결과·환경·커밋 해시를 함께 남긴다.

> 지금까지의 G2 로컬 결과(tech-stack §11.1: 1000연결·22분 소크 등)는 재현 스크립트가 저장소에 없어 ‘참고값(재현 불가)’ 이다. 이 폴더가 그 재현 스크립트를 대신하고, 통과하면 ‘실측’으로 승격한다.

## 구성
| 파일 | 역할 |
|---|---|
| `gateway.ts` | `Bun.serve` WebSocket 서버. **앱 레벨 송신 큐**(연결당 64건/256KB 초과 시 `4408`), 25초 `hb`, 공개 채널 팬아웃(직렬화 1회), 비공개 연결별 순번, 10초마다 RSS·힙·연결·큐·이벤트 루프 지연·CPU 표본, 5분마다 강제 GC 후 힙 |
| `load.ts` | 연결 N 개를 열고 **순번 연속성(gap·중복·역전)** 과 서버 생성→수신 **지연**을 검증. 지수 백오프(250ms→30s, 지터 ±50%) 재접속. 느린 소비자(업그레이드 후 읽기를 멈추는 raw TCP) 주입 |
| `run.ts` | 위 둘을 띄우고, 끝나면 `analyze.ts` 를 돌린다. `--storm=1` 은 서버를 SIGTERM·SIGKILL 로 껐다 켠다 |
| `analyze.ts` | 표본 분석과 합격 판정(`results/<run>/summary.json`) |

## 시험 전에 고정한 조건 (2026-11-10)
바꾸려면 이 표를 먼저 고치고 커밋한 뒤 시험한다.

### 부하 모델
| 항목 | 값 | 근거 |
|---|---|---|
| 연결 수 | 공개 900 + 비공개 100 = **1000** | 설계 용량 ≤ 100~200(realtime §3.6)의 5배. 이전 로컬 시험과 같은 조건 |
| 공개 이벤트 | 초당 20건, 본문 200바이트(JSON 약 230바이트), 공개 전원에게 팬아웃 | 이전 시험과 같은 조건. 연결 900 × 20 = 초당 18,000 전송 |
| 비공개 | 연결당 초당 평균 0.2건 | |
| `hb` | 25초 | realtime §(재접속 규칙) |
| 런타임 옵션 | `idleTimeout` 120초, `sendPings` 켬, 앱 큐 64건/256KB, ws 버퍼 상한 64KB 미만에서만 큐 소비 | 설계 값 |
| 느린 소비자 | 30분 시점에 10개 주입(업그레이드 후 읽기 중지) | |
| 소크 길이 | **3시간 30분(12,600초)** | 설계에 ‘수 시간’으로만 있다. 제안은 4시간이었으나 사용자가 3시간 30분으로 정함(2026-11-10) |
| 워밍업 | 목표 연결 수 도달 후 10분 제외 | |

### 합격 기준 (`analyze.ts` 의 상수와 같다)
| 항목 | 기준 | 판정에 쓰는 값 |
|---|---|---|
| RSS 증가 | 워밍업 이후 선형회귀 기울기 **≤ 2 MB/h**, 종료 RSS / 워밍업 종료 RSS **≤ 1.2** | `gateway-samples.jsonl` |
| 진짜 누수 구분 | 강제 GC 뒤 `heapUsed` 기울기 **≤ 0.5 MB/h** | 5분 간격 GC 표본 |
| 순서·무결성 | 정상 연결의 gap·중복·역전 **전부 0** | `load-windows.jsonl` |
| 안정성 | 정상 연결의 예기치 않은 종료·접속 실패 **0** | 같음 |
| 팬아웃 지연 | 창(60초)별 p99 **최댓값 ≤ 100ms**, p99 **중앙값 ≤ 50ms** | 서버 생성 시각→클라이언트 수신(같은 호스트 시계) |
| 이벤트 루프 | 지연 p99 중앙값 **≤ 20ms** | |
| 느린 소비자 | 서버가 `4408` 로 끊은 수 **= 주입한 수(10), 정상 연결은 0** | 서버 카운터 |
| 격리 | 주입 후/전 p99 **≤ 1.5배** | 주입 전 10분 vs 주입 1~11분 후 |
| 판정 불가 | 워밍업 이후 30분 미만이면 기울기 판정은 INCOMPLETE | |

### 재접속 폭풍 (별도 5분 시험, `--storm=1`)
서버를 60초에 SIGTERM(정상 종료, bye+1001), 150초에 SIGKILL(비정상) 하고 각각 2초 뒤 재기동한다. **서버 복귀 후 99% 재접속까지 ≤ 30초**(창 해상도 5초 허용), 순번 gap·중복·역전 0, 지연 기준은 소크와 같다. RSS·힙 기울기는 재시작으로 끊기므로 이 시험에서는 판정하지 않는다.

## 계획 변경 기록 (결과를 보기 전에 남긴다)
- **2026-11-10 06:5x UTC, 소크 80분 경과 시점에 사용자가 소크를 조기 종료하기로 결정했다.** 고정 조건은 3시간 30분이었다. 이 시점까지 판정 결과는 보지 않았고(연결 1000개 유지와 프로세스 생존만 확인), 결정의 이유는 아래와 같다. 이 변경은 ‘결과를 보고 기준을 바꾼 것’이 아니다.
  - 누수는 시간이 아니라 **메시지 수·연결 수명주기 횟수**에 비례한다. 소크는 연결을 계속 붙들고 있어 **접속·해제마다 쌓이는 누수**를 보지 못한다.
  - 워밍업 10분 이후 70분의 표본이면 기울기 판정(최소 30분)을 할 수 있다.
  - 한계: 0.5MB/h 이하의 느린 누수는 80분으로는 구분하지 못한다. 2MB/h(한 달 가동 시 약 1.4GB)보다 작은 값은 롤링 배포 재시작으로 초기화된다.
- 소크 판정 기준(위 표)은 그대로 쓴다. 길이만 80분(실제 종료 시점의 가동 시간)이 된다.
- 접속·해제 부하 시험(`churn`)을 추가한다. 기준은 아래 ‘접속·해제 시험’에 코드보다 먼저 고정한다.

## 접속·해제 시험 (churn, 별도 시험)
**목적:** 연결 객체·소켓·타이머가 닫힌 뒤 회수되는지 본다. 소크가 보지 못하는 수명주기 누수다.

| 항목 | 값 |
|---|---|
| 고정 연결 | 공개 180 + 비공개 20 = 200(순번·지연 검증은 소크와 같다) |
| 워밍업 | 고정 연결이 모두 붙은 뒤 2분(기준선) |
| 접속·해제 부하 | **초당 50회**, **20분(1,200초)** → 약 60,000회. 연결 수명 0.2~3초(무작위), 90%는 공개·10%는 비공개, **80%는 정상 종료(close 1000), 20%는 raw TCP 를 업그레이드 직후 비정상 종료** |
| 정착 | 부하를 멈추고 90초 대기(강제 GC 60초 간격) |
| 길이 | 총 약 24분 |

| 합격 기준(제안, 시험 전 고정) | 값 |
|---|---|
| 접속·해제 횟수 | 시작한 접속 **≥ 59,000회**(초당 50회 부하가 실제로 걸렸는지) |
| 연결 객체 회수 | 정착 후 서버가 센 연결 수 **= 고정 연결 수(200)** (서버 `/stats`) |
| 메모리(RSS) | 정착 후 RSS **≤ 기준선 + 10MB** |
| 메모리(힙) | 정착 후 강제 GC 뒤 `heapUsed` **≤ 기준선 + 2MB** |
| 고정 연결 무결성 | gap·중복·역전 0, 고정 연결의 예기치 않은 종료 0 |
| 지연 | 고정 연결 창별 p99 최댓값 ≤ 100ms |
| 이벤트 루프 | 지연 p99 중앙값 ≤ 20ms |
| 서버 회계 | 서버가 센 `opened` 가 (고정 200 + 성공한 접속) 와 ±1% 안에서 일치 |

## 실행
```bash
cd spikes/g2-ws-soak
bun run.ts --duration=12600 --slow=10 --slowAt=1800 --label=soak3h30                     # 소크 3시간 30분
WARMUP_MIN=0.5 bun run.ts --duration=300 --slow=0 --storm=1 --stormAt=60,150 --window=5 --label=storm   # 재접속 폭풍 5분(짧은 시험이라 워밍업 30초)
bun analyze.ts results/<run>                                                             # 다시 분석만
```
`results/<run>/` 에 `meta.json`(환경·커밋), `gateway-samples.jsonl`, `load-windows.jsonl`, `storm-events.jsonl`, `summary.json` 이 남는다.

## 한계 (결과에 병기한다)
- 개발 PC(WSL2 loopback)에서 서버와 부하 생성기가 **같은 CPU 를 쓴다.** 네트워크 지연·TLS·Funnel·nginx 가 없다. 실제 합격은 호스트 재측정(S0-2 ‘개발 PC → 호스트’)으로 한다.
- WSL2 의 시계·타이머가 느려진다(G14 에서 약 7% 관찰). 시간은 `Date.now()` 와 표본 시각 기준이며, 지속 시간은 표본 시각으로 계산한다.
- 이 서버에는 **replay·세션·DB 가 없다.** 앱 객체·세션 캐시 메모리는 포함되지 않는다(realtime §3.6 의 ‘수 배’ 한계). 재접속 후 순번은 새 기준선에서 시작한다.
- 비교 대상(Elysia 라우트 옵션 vs `Bun.serve` 지연)과 Go 대안은 이 시험에 없다. S0-2 의 나머지 항목이다.
- 이 시험이 통과해도 ‘이 부하에서 문제를 못 찾았다’일 뿐 증명이 아니다.
