## 한계
- 호스트가 아니다. 이 결과는 ‘개발 PC 에서 이 부하에 문제를 찾지 못했다’이지 호스트에서의 합격이 아니다.
- 서버에 replay·세션·DB·앱 객체 캐시가 없어 실제 앱의 메모리 증분은 포함되지 않는다(design/14 §3.6 의 ‘수 배’ 한계).
- Elysia 라우트 옵션 대 `Bun.serve` 지연 비교와 Go 대안은 이 시험에 없다(S0-2 의 남은 항목).
- WSL2 시계 지연(G14 에서 약 7% 관찰)이 있으나 이 시험의 지속 시간·기울기는 서버 표본의 `Date.now()` 시각 기준이다.
- 느린 소비자가 `4408` 로 끊기기까지 이 부하(연결당 초당 20건·약 230B)에서 약 26분이 걸렸다. 격리는 작동하지만 즉시가 아니다(앱 큐가 차기 전에 커널 소켓 버퍼가 먼저 찬다).

## 호스트 재측정 (2026-11-11 실행, 2026-11-12 기록)
호스트(집 서버 qdServer): Xeon Bronze 3204 6코어 1.9GHz, Ubuntu 24.04, 커널 6.8.0-149(재부팅 후), Docker 29.1.3, Bun 1.4.4(`oven/bun:1.4.4` 컨테이너), 소스 커밋 `e714a39`. 서버에 코드를 두지 않고 `spikes/host-remeasure/run.sh` 로 컨테이너에서 실행했다. 원시 결과: `spikes/host-remeasure/results/`(커밋 `0a0d520`). 개발 PC 결과와 교차 비교하지 않는다 — 합격/불합격만 말한다.
- **storm(5분, 1000연결): PASS** — 검사 7개 모두 통과. 순번 gap·중복·역전 0, 팬아웃 지연 창별 p99 최대 25ms, SIGTERM 뒤 99% 재접속 3.5초.
- **churn(25분): PASS** — 검사 10개 모두 통과. 접속·해제 약 59,698회 연결 수 회수, RSS 33.4→33.5MB, 정상 연결의 예기치 않은 종료 0.
- **soak82m(81.9분): PASS** — 검사 10개 모두 통과. RSS 기울기 0.531MB/h(한계 2)·종료/워밍업 1.016(한계 1.2)·GC 후 힙 기울기 0.013MB/h(한계 0.5)·gap/중복/역전 0·정상 연결 예기치 않은 종료 0. 총 메시지 88,078,609건. 느린 소비자 10/10 을 4408 로 격리(주입 전후 p99 중앙 23→19ms, 비율 0.83).
- 원시 결과: `host-remeasure/results/g2-ws-soak/`(storm·churn·soak82m).
- **한계:** 공유 서버라 soak 종료 시점 loadavg 6.97/6.87/6.63(6코어)이었다. **2026-11-12 서버 점검에서 이 서버의 한 컨테이너에서 CPU 6코어를 점유하던 무허가 프로세스(채굴 악성코드)가 확인됐고, 시작 시각은 약 14:03Z(소크 13:40~15:02Z 의 후반 약 59분과 겹침)였다.** 같은 구간의 팬아웃 p99 는 악화되지 않았고(25ms → 격리 뒤 18~19ms) 합격 판정은 유지하지만, 소크 후반이 CPU 경쟁 아래 있었다는 점이 사실로 확정됐다. storm·churn·다른 기준의 측정(12:46~13:19Z)은 이 프로세스 시작 전이다(G10b·G11 시작 loadavg 0.9). 또한 호스트의 무결성이 확인되지 않은 상태에서 얻은 값이다. 세부는 이 저장소에 적지 않는다. 합격 판정은 유효하나 ‘여유가 얼마나 있는가’의 근거로는 쓰지 않는다. 수 시간 소크는 미실행.
