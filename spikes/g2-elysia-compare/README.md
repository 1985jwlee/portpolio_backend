# S0-2 — Elysia 대 `Bun.serve` WebSocket 비교

[design/features/14-realtime.md](../../docs/design/features/14-realtime.md) §3.1(`SocketRuntime` 경계, 앱 레벨 송신 큐), [tech-stack §11.1](../../docs/domains/tech-stack.md) G2, [ADR-022](../../docs/adr/ADR-022-tech-stack-definition.md) §11. **제품 코드가 아니다**(스파이크). 증거 규칙은 [ADR-050](../../docs/adr/ADR-050-evidence-rule.md).

> 이전 기록(design/14 §3.1: Elysia 라우트 옵션은 무시(0/10), 최상위 옵션은 느린 연결을 끊지만 이전 조건(초당 2000건)에서 정상 연결 p99 531~886ms 악화, 순수 `Bun.serve` 는 0.5~0.7ms; 재시험 조건(100연결·초당 200건·1KB)에서는 악화 재현 안 됨)은 재현 스크립트가 없어 ‘참고값’이다. 이 폴더가 재현 스크립트를 대신한다.

## 알고 싶은 것 둘
- **Q1.** Elysia 를 WS 런타임으로 쓰되 **앱 레벨 송신 큐**는 그대로 둘 때(변형 B), `Bun.serve` 직접(변형 A)와 비교해 지연·메모리가 감당할 만한가?
- **Q2.** 런타임 자체의 백프레셔 옵션(변형 C·D·E)이 **앱 큐를 대체**할 수 있는가? (대체 못 하면 앱 큐를 유지한다는 설계 D4 의 근거가 된다.)

## 변형
| ID | 런타임 | 느린 소비자 격리 방식 |
|---|---|---|
| **A** | `Bun.serve` | 앱 레벨 큐(연결당 64건/256KB 초과 시 `4408`) — 기준선 |
| **B** | Elysia `.ws()` | 앱 레벨 큐 (A 와 같은 코드) |
| **C** | Elysia `.ws()` **라우트 옵션** `backpressureLimit`·`closeOnBackpressureLimit` | 런타임 옵션만(앱 큐 없음, 한도 256KB) |
| **D** | Elysia **최상위 옵션** `new Elysia({ websocket: {…} })` | 런타임 옵션만(한도 256KB) |
| **E** | `Bun.serve` 네이티브 `websocket.backpressureLimit`·`closeOnBackpressureLimit` | 런타임 옵션만(한도 256KB) |

모든 변형이 같은 발행자·같은 부하 생성기([`../g2-ws-soak/load.ts`](../g2-ws-soak/load.ts), 수정 없이 사용)를 쓴다. 느린 소비자는 업그레이드 뒤 읽기를 멈추는 raw TCP 연결이다.

## 시험 전에 고정한 조건과 기준 (2026-11-11)
**반드시 이 PC 를 다른 부하 없이 단독으로 쓴다**(지연 측정). 시나리오는 셋이다.

| 시나리오 | 연결 | 발행 | 느린 소비자 | 길이 | 변형 × 반복 |
|---|---|---|---|---|---|
| **SA** 정상 규모 | 공개 900 + 비공개 100 | 초당 20건 × 200B | 120초에 10개 | 240초 | A·B × 2 |
| **SB** 고부하 소수 | 공개 90 + 비공개 10 | 초당 200건 × 1KB | 30초에 10개 | 150초 | A·B·C·D·E × 3 |
| **SC** 극고부하 | 공개 40 + 비공개 10 | 초당 2,000건 × 1KB | 30초에 10개 | 120초 | A·B·C·D·E × 3 |

SB 는 design/14 §3.1 의 재시험 조건, SC 는 이전에 악화가 보였다는 ‘초당 2000건’ 조건이다. SC 의 연결 수는 부하 생성기(단일 스레드)가 병목이 되지 않도록 줄였다(아래 유효성).

### 유효성 (모든 실행에 먼저 적용)
- 부하 생성기 평균 CPU **< 0.85코어**(넘으면 지연이 클라이언트 탓이므로 그 실행은 **무효**로 표시하고 한 번 다시 돌린다)
- 정상 연결의 99% 이상이 접속에 성공
- 기준선 A 가 K1~K4 를 통과하지 못하면 그 시나리오의 비교는 무효(조건이 시험으로 부적합)

### 합격 기준 (제안, 이번에 고정)
| # | 기준 | 시나리오 | 합격 |
|---|---|---|---|
| K1 | **느린 소비자 격리**: 주입한 10개를 서버가 닫은 수(`전체 서버 종료 − 정상 연결 종료`) | SB·SC | 10/10, 반복 **전부** |
| K2 | 정상 연결 무결성: gap·중복·역전 0, 정상 연결의 예기치 않은 종료·접속 실패 0 | 전부 | 0 |
| K3 | 정상 연결 지연: 주입 10초 뒤부터 끝까지 창별 p99 의 중앙값이 **기준선 A 의 1.5배 이하**이고 절대 상한 이하 | 전부 | SA·SB 100ms, SC 250ms |
| K4 | 메모리: 끝의 RSS − 주입 전 RSS ≤ **30MB**, 마지막 3분의 1 구간 기울기 ≤ 5MB/분 | SB·SC | 둘 다 |
| K5 | (관찰) 느린 소비자가 닫힐 때 서버가 본 종료 코드(`4408` 인가 `1006` 인가) | SB·SC | 기록 |

### 결론 규칙 (결과를 보기 전에 정해 둔다)
- **Q1**: 변형 B 가 SA(K2·K3)와 SB·SC(K1~K4)를 모두 통과하면 **‘Elysia 를 WS 런타임으로 쓸 수 있다(앱 큐 유지)’**. 하나라도 실패하면 WS 부분은 `Bun.serve` 로 둔다(`SocketRuntime` 경계가 그 교체를 이미 허용한다).
- **Q2**: 변형 C·D·E 각각이 K1~K4 를 통과하면 ‘런타임 옵션이 앱 큐를 대체할 수 있다’고 쓰되, K5 가 `1006` 이면 **클라이언트가 종료 사유를 알 수 없다**는 한계를 함께 적는다. 통과하지 못하면 앱 큐가 필요하다는 근거가 된다.

## 구성
| 파일 | 역할 |
|---|---|
| `src/common.ts` | 설정, 연결 모델, 앱 큐(`pump`/`offer`), 발행자(10ms 틱 누적기), 표본·GC·종료 |
| `gateway.ts` | `VARIANT` 에 따라 `Bun.serve` 또는 Elysia 로 WS 서버를 띄운다 |
| `compare.ts` | 시나리오 × 변형 × 반복을 하나씩 실행하고 판정한다(`results/<일시>/`) |

## 실행
```bash
cd spikes/g2-elysia-compare
bun compare.ts                       # 전부(약 85분)
bun compare.ts --scenarios=SB --variants=A,B --reps=1   # 일부
```

## 한계
- 개발 PC(WSL2 loopback)에서 서버와 부하 생성기가 같은 CPU 를 쓴다. 호스트(Xeon 1.9GHz)에서는 절대값이 다르다.
- Elysia 의 라우트 옵션·최상위 옵션이 실제로 Bun 에 전달되는지는 **동작(느린 소비자가 닫히는가)** 으로만 판단한다. 내부 구현은 읽지 않았다.
- 정상 연결 지연은 발행 시각 → 클라이언트 수신 시각이며, 같은 호스트 시계다.
