# ADR-049: 핫 캐시와 몰림 대응 — 병합 먼저·보존은 열화 모드, 단계적 열화 사다리, 기다리는 곳에 상한
- 상태: **Accepted** (2026-11-06, 사용자 결정 HC-1~HC-11 — HC-5 반영 후 확정. HC-5 만 권장안과 다르게 '카운터 열 도입'. 결정 표는 [design/18 §12](../design/18-hot-cache-and-surge-control.md))
- 날짜: 2026-11-06
- 근거: AC-013(동시 50, API p95 ≤ 300ms, LCP ≤ 2.5s) · G14 ⑦ 합격선(제안값) · ADR-024(Redis 이음새·장애 거동) · ADR-038(재고 두 게이트) · ADR-021(동시성) · ADR-018(CQRS) · ADR-033(호스트 6코어 1.9GHz) · U19(입장 토큰 + 속도 제한만) · 개발 PC 측정(2026-11-06, 호스트 재측정 필요) · HC-5 정수 시뮬레이션(2026-11-06, design/18 §4.4.6)
- 관련 문서: [design/18](../design/18-hot-cache-and-surge-control.md) (정본), [design/08 §9.1](../design/08-test-strategy.md), [F11 §3.6](../design/features/11-guestbook-write.md), [F12](../design/features/12-guestbook-read.md), [database-schema §4-2·§10](../domains/database-schema.md), [F14](../design/features/14-realtime.md), [F17](../design/features/17-ops-observability.md), [P2 §4](../design/phases/02-commerce.md)

## 맥락
집 PC 한 대를 Tailscale Funnel(CDN 없음, 대역폭 비공개)로 노출한다. 평상시 부하는 작지만 링크 공유로 수백 명이 몰리는 순간, 배포·단절 직후의 WebSocket 재접속 폭풍, 타임딜 오픈 순간은 현실적인 위험이다. 각 설계 문서가 부분 장치(nginx 제한, `SendQueue`, `bye` 분산, 입장 버킷, 품절 1초 캐시)를 갖고 있지만 **"몰릴 때 무엇을 먼저 포기하는가"와 캐시를 언제 넣는가의 기준**이 없었다. 계산상 현재 규모에서 CPU 는 병목이 아니고(설계 18 §8), 풀 고갈은 부하가 아니라 대기 중 연결 보유에서 온다(§6.3).

## 결정
1. **몰림은 단계적 열화로 받는다.** 과부하 사다리 0 정상 → 1 캐시 우선·비필수 갱신 감속 → 2 읽기 전용(일반 쓰기 `503 overloaded`) → 3 우선순위 외 차단 → 4 정적 대체 페이지(수동). 진입은 **자동**(이벤트 루프 지연·풀 대기·처리 중 요청·p95, 진입 10초·해제 30초 히스테리시스)이되 **그림자 모드(`OVERLOAD_MODE=shadow`)로 시작**하고 S9-6 측정으로 임계를 확정한 뒤 집행한다(HC-1). 임계 수치는 제안값이다. **열화는 `/readyz` 를 떨어뜨리지 않는다.**
2. **우선순위 클래스 C0~C5**(운영 생존 > 진행 중 약속 > 일반 쓰기 > 읽기 > 신규 WS > 익명 세션 발급)를 두고 아래부터 포기한다. C0·C1 은 자동으로 거절하지 않는다.
3. **캐시는 병합(single-flight, 보존 0초)을 먼저, 보존(TTL)은 열화 모드의 동작으로 둔다.** 상시 보존으로 바꾸려면 측정 근거가 있어야 한다. 보존 캐시는 논리 만료·지터·세대 가드·`stale-if-error` 를 갖고, 무효화는 "원본 커밋 먼저"(`NOTIFY` 는 커밋 시 전달) + TTL 안전망이다. **M1 은 공개 조회에 공유 가능 캐시 헤더를 허용하지 않고**(현행 `no-store`, 딜 조회만 Phase 3 재검토 — HC-3), **ETag·조건부 요청을 도입하지 않는다**(HC-4).
4. **틀리면 안 되는 값은 캐시하지 않는다**: 권한·잔액·재고 확정·REST 세션 폐기 판정·멱등 결과·결제 상태·쓰기 잠금.
5. **WS 스냅샷은 head 단위로 공유한다** — 구독 등록 직후의 `PublicHub.lastRead` 를 head 로 쓰고 `caughtUp` 으로 만든 것만 공유한다. 스냅샷 계약(2초 대기 후 4500)은 그대로다. 업그레이드에는 별도 admission(제안 100/초)을 둔다.
6. **기다리는 곳에 상한을 둔다**: **한 DB 풀 위에 클래스별 허용량**(세마포어, 물리 풀 분할 없음 — HC-10), 반응은 글 단위 동시 1, 모든 대기에 대기열 상한과 시간 제한. 한 요청은 연결을 최대 1개, 획득 순서는 클래스 → 핫 키 → 풀 → tx 로 고정.
7. **타임아웃은 안쪽이 바깥보다 짧다**(nginx 30s > api 마감 8s > `statement_timeout` ≤ 5s > `lock_timeout` 2s), 재시도는 한 층에서만, 나가는 호출은 재시도 예산 10%.
8. **Phase 3 Redis 에 캐시 키를 두지 않는다** — `noeviction` 단일 인스턴스에서 캐시가 메모리를 채우면 재고 Lua 쓰기가 실패해 구매가 멈춘다. L2 캐시는 Phase 4 측정 후 판정한다(HC-9).
9. **반응 핫 로우는 쓰기 경로 문제로 다루고, 총개수는 쓰기 모델의 카운터 열로 구한다(HC-5, 사용자 변경).** 글 행 `FOR NO KEY UPDATE` 직렬화(`seq` = 커밋 순서 불변식)를 유지하고 대기는 글 단위 세마포어로 메모리에 옮긴다. 총개수는 `count(*)` 대신 **`guestbook.reaction_count.count`** 를 반응 행 INSERT/DELETE 가 **실제로 1행 바뀐 경우에만 같은 tx 에서 ±1** 하고 그 `RETURNING count` 를 이벤트에 싣는다. 잠금 순서는 글 행 → 반응 행 → 카운터 행 → outbox 로 고정한다. 새 불변식 **I-R1(카운터 = 반응 행 수)** 은 대사(`pf_projection_drift{projection="reaction_count"}`)로 감시하고, 어긋나면 `repair reaction-count` → `rebuild entry_view` 순서로 고친다. 재구성 스냅샷은 카운터가 아니라 반응 행을 집계한다. `reaction.changed` v1 계약·프로젝터(덮어쓰기 + 이모지별 순번 가드)는 바뀌지 않는다. 낙관적 재시도·카운터 샤딩·배치 집계·**읽기 모델 증분 카운터**는 기각.
10. 응답·한도·타임딜: 열화 거절은 **새 wire 코드 `overloaded`(503 + `Retry-After`)** 이고 `write_locked` 를 재사용하지 않는다(HC-2). IP 미확보(G14 ④)로 판정되면 **앱 읽기 버킷 `read.session`·`read.nosession` 을 신설**한다(HC-8, 확보면 만들지 않음). 1단계 이상에서 메트릭 iframe 은 **정적 안내 + 링크**로 바뀐다(HC-11). 타임딜의 "입장 토큰"은 P2 §4.8 의 **토큰 버킷**이며 서명된 개별 증표를 도입하지 않는다(HC-7). 남은 수량은 **구간으로 표시**한다(HC-6).

## 설계 상세
정본은 [design/18](../design/18-hot-cache-and-surge-control.md): 핫 데이터 분류표(§2), 계층(§3), 스탬피드·경쟁 인터리빙·반응 카운터(§4), 팬아웃 몰림(§5), 사다리 동작표·bulkhead·타임아웃·차단기·재시도(§6), 타임딜(§7), 용량 모델(§8), 장애 매트릭스(§9), 지표 `pf_cache_*`·`pf_admission_*`·`pf_shed_total`·`pf_pool_wait_seconds`·`pf_loop_lag_seconds`·`pf_breaker_*` 와 시험 SG-1~SG-9(§10), 구현 작업 S4-8·S6-1(보강)·S6-11·S6-12·S7-7·S9-6(§11), 결정 표(§12).

측정·계산 요지(개발 PC, 호스트 재측정 필요): 콜드 키 동시 300 요청에서 병합 없는 TTL 캐시는 원본 256회·p95 203ms, 병합은 원본 1회·p95 약 14ms. 스냅샷 26.8KB 직렬화 34.5µs — 400 연결 공유 이득의 대부분은 직렬화가 아니라 DB 왕복(1,600 → 수십 질의). IP 미확보 시 현행 `pf_wsup`(30r/분·burst 20)을 전역 키에 두면 400 재접속 수락에 760초.

HC-5 해석 요지(design/18 §4.4): 읽기 모델 `entry_view.reactions` 는 **이미 카운터**이고 프로젝터는 이벤트 `count` 로 덮어쓴다 — `count(*)` 는 쓰기 tx 안에만 있다. 그래서 '카운터 열'은 쓰기 모델 위치(a)일 때만 핫 로우 잠금 보유 시간을 줄인다. 읽기 모델 증분(b)은 이모지별 순번 가드와 양립하지 못하고(역전 시 델타 유실) 그림자 재구성의 이중 적용에서 이중 계산한다 — 정수 시뮬레이션에서 각각 2,000/2,000 회 최종값이 틀렸고, (a) 는 동시 300 요청 2,000 회에서 I-R1 위반 0, 재전달·역전 프로젝터 최종값 오류 0 이었다.

## 대안과 기각 이유
- **상시 TTL 캐시 먼저**: 측정상 필요가 없고, 병합 없이는 만료 순간 효과가 거의 없다(원본 256/300). 신선도 문제만 들여온다.
- **가상 대기열·캡차**: U19 로 범위 밖.
- **물리 풀 분할**: 풀 간 중첩 획득이 새 교착 경로다.
- **과부하 시 readyz 실패로 인스턴스 제외**: 남은 쪽으로 몰려 연쇄 장애.
- **Phase 3 Redis 에 공용 캐시**: `noeviction` 에서 재고 쓰기를 멈추게 하는 역전.
- **반응 카운터 샤딩·배치 집계**: 이벤트의 `count` 계약과 `seq` 순서 불변식을 바꾼다.
- **반응 카운트를 읽기 모델에서 증분(±1)**: 핫 로우(쓰기 tx) 보유 시간을 줄이지 못하면서 순번 가드·재전달·재구성 안전성을 잃는다.
- **카운터를 `entry` 행의 jsonb 열로**: 반응마다 본문을 실은 글 튜플을 다시 쓰고, 글의 `version`·`updated_at`(낙관적 버전·계약 필드) 의미를 깨기 쉽다 — (글, 이모지) 별 행으로 둔다.
- **`write_locked` 재사용**: 원인(관리자·수동 vs 자동·일시)·문구·재시도 간격이 다르다.

## 결과
- 얻는 것: 몰림에 대한 답이 "증설"이 아니라 **포기 순서와 그 근거**로 문서·지표·시험에 남는다. 정본 불변식(`seq` = 커밋 순서, 멱등, outbox, CQRS)은 건드리지 않고, 반응 핫 로우의 잠금 보유 시간에서 O(반응 수) 항이 빠진다. 열화 단계가 공개 대시보드에 보인다.
- 치르는 것: `SingleFlightCache`·사다리·세마포어·지표 구현(S6-11·S6-12·S4-8·S7-7), 평소 쓰이지 않는 열화 경로를 썩지 않게 하는 상시 시험(SG-7), 새 wire 코드 `overloaded`. HC-5: 테이블 하나(`guestbook.reaction_count`)·불변식 하나(I-R1)·대사 한 줄·복구 CLI 하나, 반응마다 카운터 행의 죽은 튜플 하나(HOT 정리 대상). 반응 수가 적은 글에서는 카운터 갱신이 `count(*)` 보다 이득이 없을 수 있다(미측정, SG-6 이 함께 잰다).

## 위험과 완화
| 위험 | 완화 |
|---|---|
| 제안 임계로 정상 트래픽을 거절 | 그림자 모드로 시작, S9-6 측정 후 집행(HC-1) |
| 보존 캐시의 옛 값 | 세대 가드 + TTL + `CacheInvalidationFailing` 경보 |
| 대역폭이 먼저 터져 서버 보호가 무의미 | 첫 방문 전송량 축소, 원점/종단 지표 분리(G14 ⑦) |
| 세마포어·풀·잠금 조합 교착 | 획득 순서 고정(tx 안은 글 행 → 반응 행 → 카운터 행 → outbox), SG-8(풀 2) |
| 반응 카운터가 행 수와 어긋남(버그·수작업 SQL) | 행 변화 조건부 증감, 대사 → `ProjectionDrift` 경보, `repair reaction-count` → `rebuild` 순서, 재구성 검증이 I-R1 위반 시 교체 중단 |
| 카운터 행 부풂(한 행에 초당 수백 판) | `fillfactor` 낮춤(제안 50), `pf_db_oldest_xact_age_seconds` 감시 |

## 검증 방법
design/08 §9.1 SG-1~SG-9 — 각 장치는 **끈 변형이 실패하는지**로 가드를 검증한다(병합·세대 가드·구독 순서·글 단위 세마포어·히스테리시스·획득 순서). HC-5 는 SG-6 에 합쳐 검증한다: 한 글에 300 세션 버스트 후 I-R1, 이모지별 `seq` 순 `count` 가 ±1 씩만 변함, 조건 없는 증감 변형과 '글 행 잠금 없음 + outbox 를 카운터 앞으로' 변형이 실패. F11 GB-04·05 의 L3 속성 시험(무작위 추가·취소 순열 후 I-R1). 합격선은 AC-013·G14 ⑦ 인용, 새 숫자는 제안.

## 실서비스라면
CDN 의 공유 캐시와 `stale-while-revalidate`, 오토스케일, 전용 캐시 클러스터(`allkeys-lru`)와 재고 클러스터 분리, 가상 대기열, 전역 속도 제한 서비스. 반응처럼 '좋아요' 수가 폭증하는 서비스는 카운터 샤딩 + 근사 표시를 받아들이고 이벤트를 증감 계약으로 바꾸는 경우가 많다 — 이 프로젝트는 '총개수 덮어쓰기' 계약의 단순함을 택했다.

## 재검토 조건
S9-6 측정에서 상시 보존 없이 AC-013 을 못 맞출 때, Phase 4 레플리카 ≥ 2, Funnel 이 아닌 CDN 경로가 생길 때, G14 ④ 결과(IP 확보 여부 → HC-8), 사다리가 정상 트래픽에서 발동할 때, SG-6 에서 카운터 방식의 잠금 보유 시간이 `count(*)` 방식보다 나쁘게 나올 때(HC-5 — 되돌림은 카운터 테이블을 남긴 채 읽기만 `count(*)` 로 돌리면 된다), 대사가 I-R1 위반을 반복해 보고할 때.
