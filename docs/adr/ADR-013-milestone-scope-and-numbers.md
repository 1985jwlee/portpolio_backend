# ADR-013: M1 을 전부 한 번에 내되, 성능 수치는 측정 후에만 쓴다
- 상태: Accepted
- 날짜: 2026-11-03
- 근거: 원 계획안 모순 #9·#10, Part 2 원칙 / 명세 FR 전체, NFR Performance, AC-013, 가정 A-012 / 인터뷰 R7-Q2·Q3, R9-Q3

## 맥락
원 계획안의 원칙은 "각 Phase 는 단독 DoD 를 가진다, 중간에 멈춰도 결과물이 남는다"이다. 또한 "10,000+ TPS" 같은 **근거 없는 수치**를 모순으로 지적했다. 한편 명세의 M1(방명록·인증·소개·폴백·시각화·WebSocket·Grafana)을 사용자는 **작게 쪼개지 않고 전부 한 번에** 내기로 했다(추천은 분할이었다).

## 결정
- M1 은 Phase 0 과 Phase 1 사이에 위치하며 **한 번에 출시**한다. 위험(출시 지연, 문제 원인 분리 곤란)은 사용자가 감수한다.
- 완화: TODO 를 **의존 순서**(기반 → 코어 → 이벤트 → 실시간·관측 → 프런트 → 검증)로 쌓고, 각 단계의 완료 기준을 명세 AC 로 건다.
- **성능 수치는 측정 전에는 '목표'로만 쓴다.** 목표: API p95 ≤ 300ms, 첫 화면 LCP ≤ 2.5초, 동시 접속 50. 원 계획안의 TPS 는 "목표 TPS"로 표기하고 **k6 부하 결과로 확정한 뒤** README 에 수치를 기재한다.

## 설계 상세

### M1 구현 순서(의존 순서)
| 순서 | 내용 | 완료 기준 |
|---|---|---|
| 0 | 모노레포, Compose, CI, Funnel 노출(`*.ts.net`) | CI 통과, `*.ts.net` 주소로 hello 응답 |
| 1 | DB, 익명 세션, GitHub 로그인, 방명록 API | AC-004~007 |
| 2 | outbox, 디스패처, 멱등 소비, 정리 작업 | AC-001~003, AC-011 |
| 3 | WebSocket, 지표, Grafana | AC-008, AC-012 |
| 4 | Next.js 화면, 시각화, 폴백 | AC-009, AC-010 |
| 5 | 부하·이중 호스팅 검증 | AC-013, AC-014 |

중간에 일정이 밀리면 **0~1 + 4의 소개·폴백만 먼저 공개**하는 축소안이 열려 있다(재검토 조건).

### 측정 규칙(수치를 주장하기 위한 조건)
- 부하 도구는 k6. 시나리오·동시 접속 수·지속 시간을 문서에 고정한다.
- **측정 지점을 명시**한다: Funnel 경유 여부, 클라이언트 위치. 결과는 측정 환경과 함께 기록한다(가정 A-012).
- 결과가 목표 미달이면 **미달을 그대로 기록**하고 원인과 대응을 쓴다.
- LCP 는 실제 페이지 기준으로 측정한다.

## 대안과 기각 이유
- **M1 을 방명록+인증+소개+폴백으로 축소하고 시각화·WS·Grafana 를 2차로**: 위험이 낮으나 사용자가 선택하지 않았다.

## 결과
- 얻는 것: 공개 시점에 핵심 데모가 모두 있다.
- 치르는 것: 출시 전까지 공개할 것이 없다. 중간에 멈추면 "중간에 멈춰도 결과물이 남는다" 원칙이 약해진다.

## 위험과 완화
| 위험 | 완화 |
|---|---|
| 한 번에 내려다 출시가 무기한 지연 | 순서별 완료 기준, 일정 지연 시 축소안 발동 |
| 문제 발생 시 원인 분리 곤란 | 단계별 AC 통과를 게이트로 삼아 쌓는다 |
| 측정 환경 때문에 수치가 유리하게 나옴 | 환경을 함께 기록하고 Funnel 경유 측정을 기본으로 |

## 검증 방법
AC-013(성능 목표), 위 측정 규칙을 만족하는 보고서. README 의 수치는 보고서 링크를 동반한다.

## 실서비스라면
작은 단위로 자주 낸다.

## 재검토 조건
M1 작업 중 일정이 크게 밀릴 때(축소안 발동).
