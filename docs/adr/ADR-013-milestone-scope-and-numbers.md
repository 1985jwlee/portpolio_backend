# ADR-013: M1 을 전부 내되(공개는 A층 먼저, 2026-11-06 개정), 성능 수치는 측정 후에만 쓴다
- 상태: Accepted (**2026-11-06 개정**: 공개 방식 — ‘ABC 모두 완성 후 한 번에’를 ‘A층 완성 시 먼저 공개, B·C층은 이어서 공개’로 바꾼다. 개정 이력 참고)
- 날짜: 2026-11-03
- 근거: 원 계획안 모순 #9·#10, Part 2 원칙 / 명세 FR 전체, NFR Performance, AC-013, 가정 A-012 / 인터뷰 R7-Q2·Q3, R9-Q3

## 맥락
원 계획안의 원칙은 "각 Phase 는 단독 DoD 를 가진다, 중간에 멈춰도 결과물이 남는다"이다. 또한 "10,000+ TPS" 같은 **근거 없는 수치**를 모순으로 지적했다. 한편 명세의 M1(방명록·인증·소개·폴백·시각화·WebSocket·Grafana)을 사용자는 **작게 쪼개지 않고 전부 한 번에** 내기로 했다(추천은 분할이었다).

## 결정
- M1 의 범위는 A·B·C 전부이며 Phase 0 과 Phase 1 사이에 위치한다. **공개는 A층(방명록 데모) 완성 시 먼저 하고 B·C층은 이어서 공개한다**(2026-11-06 사용자 결정으로 개정; 이전 결정 ‘A·B·C 모두 완성 후 한 번에 공개’(2026-11-05)는 대체됨). 층 라벨은 바꾸지 않는다. A층 공개 전에는 **공개 게이트 선행 항목**(아래 표)을 마쳐야 한다. 위험(문제 원인 분리 곤란)은 사용자가 감수한다.
- 완화: TODO 를 **의존 순서**(기반 → 코어 → 이벤트 → 실시간·관측 → 프런트 → 검증)로 쌓고, 각 단계의 완료 기준을 명세 AC 로 건다.
- **성능 수치는 측정 전에는 '목표'로만 쓴다.** 목표: API p95 ≤ 300ms, 첫 화면 LCP ≤ 2.5초, 동시 접속 50. 원 계획안의 TPS 는 "목표 TPS"로 표기하고 **k6 부하 결과로 확정한 뒤** README 에 수치를 기재한다.

## 개정 이력
| 날짜 | 변경 | 이유 |
|---|---|---|
| 2026-11-06 | 공개 방식을 ‘A·B·C 모두 완성 후 한 번에 공개’(2026-11-05 확정)에서 **‘A층 완성 시 먼저 공개, B·C층은 이어서 공개’** 로 개정. M1 범위(A·B·C)와 층 라벨은 그대로이고 공개 시점만 바뀐다 | **장기 비공개 위험(검토 지적)** — 모든 층이 끝날 때까지 공개하지 않으면 비공개 기간이 길어지고 그동안 점검·피드백이 없다. **사용자 결정 2026-11-06** |

## 설계 상세

### A층 공개 게이트 — 공개 게이트 선행 항목
A층을 공개하기 전에 필요한 보안 점검이다. 아래 항목은 **현재 층 라벨(C)을 바꾸지 않고** 공개 시점 기준으로만 앞당긴다(‘공개 게이트 선행 항목’ 표기). 나머지 C 항목은 A층 공개 후에 이어서 구현한다.
| 항목 | 현재 층 | 공개 전에 필요한 범위 | 이유 |
|---|---|---|---|
| FR-110 비밀 스캔 (AC-027) | C | 전부 — CI `secret-scan` + pre-commit, 공개 전 전체 이력 1회 스캔 | 저장소·사이트를 공개하면 커밋된 비밀이 즉시 노출된다 |
| FR-111 사고 대응 절차 (AC-035) | C | **최소판** — 연락처·1차 대응(비상 스위치, 비밀 회전 순서, 증거 보존) 문서. 분기별 회전 리허설은 공개 후 | 공개 직후의 유출·침해에 대응할 절차가 없으면 안 된다 |
| FR-013 세션 일괄 폐기 | C | 전체 세션 폐기 수단 1개(수동 절차 허용) | 세션 탈취·키 노출 시 즉시 무효화 수단 |
| 장기 비공개 금지 해제 | — | 저장소·사이트의 비공개 상태를 해제하는 점검 | 사용자 결정 2026-11-06 (범위는 사용자 확인 필요) |

### M1 구현 순서(의존 순서)
순서 0~5 는 **A층 → B층 → C층** 순으로 쌓고, A층 완료와 공개 게이트 선행 항목이 끝나면 A층을 먼저 공개한다(B·C층은 이어서 공개).

| 순서 | 내용 | 완료 기준 |
|---|---|---|
| 0 | 모노레포, Compose, CI, Funnel 노출(`*.ts.net`) | CI 통과, `*.ts.net` 주소로 hello 응답 |
| 1 | DB, 익명 세션, GitHub 로그인, 방명록 API | AC-004~007 |
| 2 | outbox, 디스패처, 멱등 소비, 정리 작업 | AC-001~003, AC-011 |
| 3 | WebSocket, 지표, Grafana | AC-008, AC-012 |
| 4 | Next.js 화면, 시각화, 폴백 | AC-009, AC-010 |
| 5 | 부하·이중 호스팅 검증 | AC-013, AC-014 |

중간에 일정이 밀리면 **0~1 + 4의 소개·폴백만 먼저 공개**하는 축소안이 열려 있다(재검토 조건).

### 측정 규칙(수치를 주장하기 위한 조건)
- 부하 도구는 k6. 시나리오·동시 접속 수·지속 시간을 문서에 고정한다.
- **측정 지점을 명시**한다: Funnel 경유 여부, 클라이언트 위치. 결과는 측정 환경과 함께 기록한다(가정 A-012).
- 결과가 목표 미달이면 **미달을 그대로 기록**하고 원인과 대응을 쓴다.
- LCP 는 실제 페이지 기준으로 측정한다.

## 대안과 기각 이유
- **M1 을 방명록+인증+소개+폴백으로 축소하고 시각화·WS·Grafana 를 2차로**: 위험이 낮으나 사용자가 선택하지 않았다.

## 결과
- 얻는 것: A층 완성 시점에 핵심 데모(방명록)가 공개된다. 장기 비공개 위험이 줄고 B·C층은 공개된 상태에서 이어서 쌓인다.
- 치르는 것: 공개된 뒤에 B·C층(운영 성숙도)을 구현하므로 공개 게이트 선행 항목(비밀 스캔·사고 대응 최소판)을 앞당겨야 한다. 공개 후 변경은 라이브에 영향을 준다.

## 위험과 완화
| 위험 | 완화 |
|---|---|
| 전부 끝내려다 공개가 무기한 지연(장기 비공개) | A층 완성 시 먼저 공개(2026-11-06 개정), 순서별 완료 기준, 일정 지연 시 축소안 발동 |
| 문제 발생 시 원인 분리 곤란 | 단계별 AC 통과를 게이트로 삼아 쌓는다 |
| 측정 환경 때문에 수치가 유리하게 나옴 | 환경을 함께 기록하고 Funnel 경유 측정을 기본으로 |
