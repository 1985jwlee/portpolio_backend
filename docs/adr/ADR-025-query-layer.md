# ADR-025: 쿼리 계층 — Drizzle 빌더 기본, 측정으로 정당화된 raw 탈출구
- 상태: Accepted
- 날짜: 2026-11-04
- 근거: 사용자 제안("Drizzle ORM 을 기본으로 하고, ORM 한계로 개선이 어려우면 Bun.sql 로 처리") / G4·G10 로컬 실측(tech-stack §11.1) / ADR-017·019·021
- 관련 문서: [tech-stack.md](../domains/tech-stack.md), [design/01](../design/01-repository-structure.md), [F16](../design/features/16-cross-cutting.md)

## 맥락
Drizzle 은 스키마 정본과 마이그레이션에 쓰기로 확정됐지만(ADR-022), 런타임 쿼리를 빌더로 쓸지 raw SQL 로 쓸지는 정해지지 않았다. feature 문서의 SQL 스니펫은 의미 설명용인데 raw 구현으로 읽혔다. 또 "느리면 raw"를 허용하면 **트랜잭션 경계가 깨질 수 있다**(별도 연결로 보낸 쿼리는 명령의 원자성 밖이다).

## 결정
1. **기본은 Drizzle 쿼리 빌더**(`adapter/postgres`)다. 컬럼 이름 변경이 컴파일 오류로 잡히는 타입 안전성이 이유다.
2. 빌더로 표현할 수 없거나 **측정이 정당화한 곳만** raw 로 간다. raw 의 1순위는 **같은 `tx` 객체에서 실행하는 `sql` 템플릿**이고, 별도 연결은 아래 3곳뿐이다.
3. **모든 쓰기(INSERT·UPDATE·DELETE, 즉 CRUD 의 C·U·D)는 반드시 트랜잭션 안에서 실행한다.** 한 문장짜리 쓰기도 예외 없이 `uow.run` 으로 감싼다(자동 커밋 쓰기 금지). 아래 "쓰기와 트랜잭션" 절.
4. usecase·service·domain 은 Drizzle 타입을 모른다(포트 뒤, B2·B3 그대로). Drizzle 은 `adapter/postgres` 와 `packages/db` 안에서만 쓴다.

## 설계 상세

### 수준 (Tier)
| 수준 | 방식 | 트랜잭션 | 쓰는 곳 |
|---|---|---|---|
| **T0** | Drizzle 빌더 | 호출자의 `tx` | 기본: CRUD, 커서 조회, 프로젝터 UPSERT(`onConflictDoUpdate` + `setWhere`), 멱등 키 선점, 유일 키 INSERT, 단순 선점(`.for('update', { skipLocked: true })`) |
| **T1** | 같은 `tx` 의 `sql` 템플릿 | **호출자의 `tx` 그대로** | 빌더로 표현이 어렵거나 측정이 요구한 쿼리: 집합체 선두 규칙(`NOT EXISTS`)이 붙은 선점 CTE, 배치 삭제(`DELETE … WHERE ctid IN (SELECT … LIMIT n)`), `pg_notify`, 재구성 `RENAME` DDL |
| **T2** | 별도 연결(Bun.sql `reserve()`/전용) | **트랜잭션 밖** | LISTEN 전용 연결, 리더 선출 advisory lock 연결, (필요 시) 장기 읽기 전용 배치 |

- **명령·이벤트 처리 usecase 가 연 트랜잭션 안에서는 T0·T1 만 쓴다.** T2 는 처음부터 트랜잭션이 없는 곳에만 쓴다.
- T1 은 같은 연결·같은 트랜잭션이라 도메인 변경 + outbox 의 원자성이 유지된다.

### 쓰기와 트랜잭션 (C·U·D 전부)

| 규칙 | 내용 |
|---|---|
| 전수 | 명령 usecase 의 변경뿐 아니라 **잡·정리·집계·재구성·세션 갱신(`last_seen_at`)·reaper·`trace_step` 기록·시드·관리 CLI 의 모든 쓰기**가 `UnitOfWork.run` 안에서 실행된다 |
| 단문도 감싼다 | 쓰기 한 문장이어도 `uow.run` 으로 연다. 일관성(항상 같은 경로), 감사(`trace_id`·`tx.now`), 시간 제한(`statement_timeout`) 적용이 한 곳에서 보장되기 때문이다 |
| 구조로 강제 | `DbPool` 이 밖으로 주는 핸들은 **읽기 전용(`ReadDb`: select 만)** 이다. `insert`/`update`/`delete`/쓰기 `execute` 는 `UnitOfWork` 가 주는 `TxContext` 에만 있다 → 트랜잭션 없이 쓰는 코드는 **컴파일되지 않는다** |
| 배치 | 대량 삭제·집계는 **배치마다 별도의 짧은 트랜잭션**(예: 1000행)으로 쪼갠다. 긴 트랜잭션 하나로 묶지 않는다 |
| T2 | 별도 연결(T2)은 읽기·세션 락·LISTEN 전용이다. **T2 로는 쓰지 않는다** |
| 마이그레이션 | 마이그레이션 실행기가 자체 트랜잭션으로 적용한다(G10: 대기 중 마이그레이션은 한 트랜잭션) |
| 읽기 | 조회 usecase 는 `ReadDb` 를 쓰고 트랜잭션을 열지 않는다(필요하면 `READ ONLY`) |
| 검사 | `check-purity` 가 `adapter/postgres` 밖의 `.insert(`·`.update(`·`.delete(` 사용과 `raw/` 밖의 쓰기 SQL 을 찾아 실패시키고, 08 이 "`ReadDb` 로 쓰기 시도는 타입 오류/런타임 거절" 을 시험한다 |

### 탈출 조건 (둘 중 하나)
1. **표현 불가**: 빌더로 쓸 수 없거나, 쓰면 의미가 불명확해지는 문장(예: 선점 CTE).
2. **측정**: 같은 쿼리를 빌더와 raw 로 각 N회(제안: 1000회, 워밍업 제외) 돌려 비교해 **차이가 해당 경로의 p95 예산을 위협**할 때. 그 전에 `EXPLAIN ANALYZE` 로 **실행 계획·인덱스를 먼저 고친다** — 느림의 원인은 대개 ORM 이 아니라 계획이다.

### raw 관리 규칙
| 규칙 | 내용 |
|---|---|
| 위치 | 손으로 쓴 SQL 은 `adapter/postgres/raw/<이름>.ts` 에만 둔다. 빌더 코드는 다른 파일 |
| 머리말 | 파일마다 ① 탈출 사유(표현 불가 / 측정 근거 링크) ② `EXPLAIN` 요약 ③ 사용하는 인덱스 |
| 타입 | raw 반환 행은 **런타임 검증**(TypeBox `Value.Check`)으로 타입을 보장한다 — 컬럼 변경이 컴파일 오류로 안 잡히는 약점을 보완 |
| 시험 | raw 쿼리마다 실제 Postgres 통합 시험 1개 이상(경합이 있는 것은 08 의 동시성 시험) |
| 목록 | 아래 레지스트리에 한 줄씩 등록. 목록에 없는 raw 는 CI(`check-purity`)가 `adapter/postgres/raw/` 밖의 `sql\`` 사용을 찾아 실패시킨다 |
| DDL | 마이그레이션의 raw 객체(부분 인덱스·함수·트리거)는 G10 규칙(tech-stack §11.1)과 같은 목록으로 관리 |

### 초기 raw 레지스트리 (제안, 구현 시 갱신)
| 쿼리 | 수준 | 사유 | 기능 |
|---|---|---|---|
| outbox/inbox 선점(집합체 선두 `NOT EXISTS` + `SKIP LOCKED` + 토큰 발급) | T1 | 표현 불가(스파이크 S0-4 에서 빌더 가능성 재확인) | EV-02·04 |
| 리더 선출 `pg_try_advisory_lock` | T2 | 세션 소유 락, 전용 연결 | EV-02 |
| `LISTEN`/`pg_notify` | T2 / T1 | 드라이버 기능 / 단문 | EV-13 |
| 배치 삭제(`ctid` 서브쿼리 + LIMIT) | T1 | PG 에 `DELETE … LIMIT` 없음 | EV-10 |
| 재구성 `RENAME`/락 순서 | T1 | DDL | GB-26 |

나머지(글/반응/신고 CRUD, `ListEntries` 키셋 조회, 프로젝터 UPSERT, `request_key` 선점)는 T0.

## 대안과 기각 이유
- **전부 raw SQL**: 타입 안전성·마이그레이션 정본과의 정합을 잃는다.
- **전부 빌더(탈출구 금지)**: 선점 CTE 같은 문장을 억지로 표현하면 의미가 흐려진다.
- **"느리면 별도 연결의 raw"**: 트랜잭션 경계가 깨진다(원자성 위반). T2 를 처음부터 트랜잭션 밖으로 한정한 이유.
- **Kysely 등 다른 쿼리 빌더 병용**: 도구가 둘이 된다. 이득이 없다.

## 결과
- 얻는 것: 기본은 타입 안전, 예외는 사유·측정·시험이 남는 목록으로 통제된다.
- 치르는 것: `raw/` 파일마다 머리말·검증·시험을 붙이는 규율이 필요하다. 빌더 쿼리는 DB 없이 단위 시험이 어려워 통합 시험 비중이 커진다(08).

## 위험과 완화
| 위험 | 완화 |
|---|---|
| raw 가 늘어 타입 안전성이 사라짐 | 레지스트리와 CI 검사, 반환 런타임 검증 |
| 빌더 오버헤드를 과대평가해 불필요한 raw | 탈출 조건 2(측정)와 계획 우선 개선 |
| Drizzle 0.45.x → 1.0 업그레이드 | raw 가 모여 있어 영향 범위 파악이 쉽다(ADR-022 재검토 조건) |
| 빌더가 선점 CTE 를 표현 가능한데 raw 로 둠 | S0-4 에서 가능성을 시험하고 가능하면 T0 로 내린다 |

## 검증 방법
- S0-4: 선점 쿼리를 빌더(`.for('update', { skipLocked: true })` + 서브쿼리)로 쓸 수 있는지, 집합체 선두 규칙까지 가능한지 시험하고 레지스트리 갱신.
- `check-purity`: `raw/` 밖 `sql` 템플릿 사용 검출.
- 08: 명령 트랜잭션 안에서 T2 호출이 없음을 구조 검사.

## 실서비스라면
쿼리 성능 회귀를 CI 의 `EXPLAIN` 스냅샷·슬로우 쿼리 경보로 지키고, ORM 과 raw 의 경계를 코드 소유자 리뷰로 관리한다.

## 재검토 조건
raw 비율이 커져(예: 전체 쿼리의 20% 초과) 빌더의 이점이 줄 때. Drizzle 1.0 업그레이드. 빌더 오버헤드가 p95 예산을 실제로 위협할 때.
