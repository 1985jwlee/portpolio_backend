# ADR-051: Tailscale Funnel 관문(G14) 실측 결과와 설계 반영
- 상태: **Proposed** (2026-11-10) — 측정 ①②③④⑧(단일 출발지)은 끝났고 ⑤⑥⑦·다중 출발지는 남았다. 결정 5·6 은 **사용자 결정(2026-11-10)**, 결정 1~4 는 제안(사용자 확인 대기).
- 날짜: 2026-11-10
- 근거: tech-stack §11 G14 ①~⑧ · ADR-003(Funnel 노출, 미검증 🔴 세 건) · ADR-008(원 접속 주소 신뢰) · ADR-022(관문 G14) · ADR-049(대역폭이 먼저 터질 가능성, HC-8) · ADR-050(증거 규칙) · ADR-033(호스트 프로필·공유 호스트)
- 증거: [`spikes/g14-funnel/`](../../spikes/g14-funnel/) — 스크립트(`server.ts`·`client.ts`), 원시 결과(`results/*.json`), 환경(`ENV.md`), 원문 기록(`results/notes.md`). 표기는 ADR-050 범례를 따른다. 스크립트·원시 결과는 커밋 `33eea7b` 에 보존돼 있다(`ENV.md` 맨 아래). 측정 도중 스크립트를 보강했고 덮어써진 결과 하나가 있다 — 한계는 `ENV.md` 에 적었다.
- 관련 문서: [tech-stack §11](../domains/tech-stack.md) · [design/18](../design/18-hot-cache-and-surge-control.md) §8·§12

## 맥락
공개 경로는 전부 Tailscale Funnel 하나이고(ADR-003), 그 성질 세 가지(WebSocket 통과, 대역폭, 클라이언트 IP)가 문서에서 확인되지 않아 ‘미검증 🔴’로 남아 있었다. 설계의 여러 결정(실시간 방식, 속도 제한 키, 첫 방문 전송량, AC-013 판정 방법)이 이 세 가지에 걸려 있다. 2026-11-10 에 실제 집 서버(`qd.tail91f132.ts.net`)에서 에코 서버를 Funnel 로 노출하고 개발 PC 에서 측정했다.

## 측정 결과
**조건:** 서버 = Xeon Bronze 3204, 62GB, Ubuntu 24.04(공유 호스트, 측정 시 로드 0.02~0.22), Funnel 443 → `127.0.0.1:28080` → `oven/bun:1` 컨테이너. 클라이언트 = 개발 PC WSL2, **출발지 1곳**. 표기: **실측**(ADR-050 범례).

### ① WebSocket
| 항목 | 결과 | 표기 |
|---|---|---|
| 업그레이드 통과 | `101 Switching Protocols`, 200회 왕복, 클라이언트 `close 1000` 이 서버에 `1000` 으로 전달 | 실측 |
| 왕복 지연(작은 메시지) | p50 69ms · p95 116ms · p99 153ms · max 291ms (n=200) | 실측 (클라이언트 시계 ±7%) |
| 접속 성공률(짧게 열고 닫기) | 60/60 (연결 시간 p50 303ms · p95 804ms) | 실측 |
| 접속 성공률(5분 관찰, 2초 간격) | 88회 중 81 성공. 실패 7 = **계획된 정지 구간 4** + **계획 밖 3**(5초 타임아웃, 01:59:37·49·59). 그 구간에서 성공한 시도도 연결 시간이 3.3~4.7초였다 | 실측 |
| 켠 직후 첫 연결 | 처음 켰을 때 WS 2건이 원점에 도달하지 못했다(서버 로그에 없음, 파일 없음). 정지 후 재개 시험에서는 재개 직후 첫 완전한 시도가 성공(2.3초) | 관찰(1회 재현 실패) |
| 합산 | 비계획 실패 3건/144 시도 ≈ 2.1% (+ 초기 2건). **합격선 ≥99%(제안값) 미달**, 원인 미상 | 실측 |

### ② 유휴 타임아웃
| 시험 | 서버 시계 | 의미 |
|---|---|---|
| `hb=0`(서버가 아무것도 안 보냄) | **960.0초에 서버(Bun `idleTimeout: 960`)가 끊음** (`1006`, `WebSocket timed out from inactivity`) | Funnel 구간은 **무 ping 유휴를 960초 이상 견딘다.** 실제 상한은 서버 설정이 막아 알 수 없다 |
| `hb=25` | 900초(관찰 상한)까지 유지, 하트비트 38개 수신 | 25초 하트비트로 최소 15분 유지 |

처음 해석(‘889초에 Funnel 이 끊었다’)은 틀렸다. 클라이언트 시계가 서버 시계보다 약 7% 느려(0.926·0.934) 960초를 889초로 쟀다. **지속 시간은 서버 시계로 판정한다.**

### ③ 대역폭
| 시험 | 결과 | 표기 |
|---|---|---|
| 단일 다운로드(HTTP) | 0.41~0.78MB/s (회차 간 변동 큼) | 실측, 변동 큼 |
| 4개 병렬 | 합계 2.28MB/s (개별 0.57~0.83) | 실측 |
| 16개 병렬 | 합계 2.55MB/s (개별 0.16~0.29) | 실측 |
| WS 64KB 메시지 10연결 | 3.33MB/s 합계, 왕복 p50 339ms · p95 736ms | 실측 |
| **대조**: 서버 → 중립 호스트 직접 업로드 | 12.1MB/s (약 97Mbps), 1회 | 실측(반복 미실시) |
| **대조**: 개발 PC → 중립 호스트 다운로드 | 62MB/s | 실측 |

- 집 회선(약 12MB/s)과 클라이언트(62MB/s)는 병목이 아니다. **병목은 Funnel 경로**이고, 흐름당 약 0.4~0.8MB/s, **합계 상한 약 2.5MB/s(약 20Mbps)** 로 보인다.
- 상한이 Funnel 정책인지, 경로상의 문제인지, **출발지별 제한인지 서버 전체 제한인지**는 이 데이터로 구분되지 않는다(출발지 1곳).

### ④ 클라이언트 IP
| 항목 | 결과 |
|---|---|
| `X-Forwarded-For` | Funnel 이 **실제 클라이언트 공인 IP 하나**를 넣는다. 클라이언트가 보낸 위조값(`203.0.113.7`)은 **덮어써져** 서버에 도착하지 않았다 |
| `X-Real-IP` | 클라이언트가 보낸 위조값이 **그대로 통과**했다 → 신뢰 불가 |
| 그 외 | `Tailscale-Funnel-Request: ?1`, `X-Forwarded-Host`, `X-Forwarded-Proto: https` |
| 소켓 주소 | `172.17.0.1`(Docker 게이트웨이, docker-proxy 경유) → 사용 불가 |
| WS 업그레이드 경로 | 같은 헤더가 붙는다 |
| 미확인 | IPv6 클라이언트, 클라이언트가 `X-Forwarded-For` 를 여러 값·긴 값으로 보낼 때의 정규화 |

### ⑧ 단일 출발지 동시 연결 (HTTP 500요청/회, 각 2~3회)
| 동시 | 오류(ECONNRESET) | 비고 |
|---|---|---|
| 10 · 20 · 30 | 0 | |
| 40 | 3/500 · 8/500 (0.6~1.6%) | |
| 50 | 2.4~5.0% (7회 중 7회 발생) | 로컬 대조(Funnel 없음)는 50 에서도 오류 0 |

오류는 429 가 아니라 연결 리셋이다(오류 분류를 넣기 전 첫 회차 파일은 ‘error’ 한 항목으로만 집계됐다). 지연 p50 은 70~110ms 로 오류와 무관하고 p95 는 회차별로 100ms~1.9초로 요동쳤다.

### 측정하지 못한 것
⑤ 재시작 후 주소 유지, ⑥ 인증서 갱신, ⑦ 다른 회선에서의 종단 성능과 LCP, 다른 출발지 동시 접속, IPv6. 이 ADR 이 Proposed 인 이유이기도 하다.

## 결정 (제안 — 사용자 확인 대기)
1. **WebSocket 은 Funnel 경유로 유지한다.** SSE 등 대체(ADR-003 ① 후속)는 필요 없다. 다만 접속 성공률이 합격선에 못 미치고 연결 시간이 3~5초로 튀는 구간이 있으므로, **클라이언트 재접속(지수 백오프)과 접속 지연 허용을 필수 요건**으로 삼는다(기존 설계에 있는 재접속·snapshot 복구가 근거를 얻는다).
2. **서버 하트비트는 25초 유지.** 무 ping 유휴가 960초 이상 견디므로 Funnel 은 하트비트 간격의 제약이 아니다. 간격은 우리 `proxy`(nginx) `proxy_read_timeout`(기본 60초)보다 짧아야 한다는 조건(G7)으로 정한다.
3. **원 접속 주소는 `X-Forwarded-For` 만 신뢰한다.** `X-Real-IP` 와 클라이언트가 지정할 수 있는 나머지 주소 헤더는 `proxy` 가 폐기한다. 소켓 주소는 쓰지 않는다. nginx 는 Funnel 쪽 홉(compose 네트워크 게이트웨이)에서 온 `X-Forwarded-For` 를 `realip` 로 받는다. 전제: 앱 진입 포트는 `127.0.0.1` 바인딩이므로 Funnel 외 경로로는 닿지 않는다(공유 호스트의 다른 로컬 프로세스는 신뢰한다). 이 결정으로 **G14 ④ ‘IP 미확보’ 조건이 해소**되어 ADR-049 HC-8(앱 읽기 bucket)은 발동하지 않는 쪽으로 판정한다. IPv6·다중값 시험 전에는 ‘제안’이다.
4. **측정 방법론:** 지속 시간은 서버 시계로 판정하고, 클라이언트 `performance.now()` 수치는 ±7% 불확실성을 적는다. 병렬 실행 결과 파일이 충돌하지 않도록 pid 를 붙이고, `dirty` 판정 버그를 고쳤다.

## 사용자 결정 (2026-11-10)

5. **동시 접속자 상한 50명 + 접속자 수에 따라 전송량을 나눈다.** 사용자 결정 원문: “동시 접속자 수 제한 50명 및 접속자 수에 따라서 전송량을 분할해야한다.” 정적 자산을 Funnel 밖으로 분리하는 안은 **확정하지 않는다**(다른 출발지에서 합계 상한이 출발지별인지 전체인지 가른 뒤 재판단).
   - **근거 계산(추정):** 2.5초 창에 합계 2.5MB/s 로 보낼 수 있는 총량은 약 6.25MB 이므로, 동시 첫 방문자가 N명이면 1인당 전송량 상한은 약 `6.25MB ÷ N` 이다.
   - **단계표(제안 — 해석 확인 필요):**

     | 동시 접속자 N | 1인당 첫 화면 전송량 상한(압축 기준) | 비고 |
     |---|---|---|
     | ≤ 10 | ≤ 600KB | design/18 가정과 같음 |
     | 11 ~ 20 | ≤ 300KB | |
     | 21 ~ 50 | ≤ 125KB | |
     | > 50 | 받지 않음 | ADR-049 의 `overloaded`(503, `Retry-After`)와 대기 안내. HC-2 |

   - **구조적 함의:** 단계와 무관하게 임계 경로(HTML + 필수 JS)는 가장 낮은 단계 상한(125KB) 안이어야 한다. 단계 차이는 **지연 로딩 자산**(이미지 해상도, 폰트 subset, 3D 씬, 장식 자원)이 만든다.
   - **접속자 수의 정의·전달(제안):** 서버가 ‘활성 WS 세션 + 최근 수 초 내 첫 방문 HTTP 세션’으로 N 을 계산하고, HTML 응답 시점에 단계(`payloadTier`)를 정해 클라이언트에 알린다. 경계 진동을 막는 히스테리시스는 ADR-049 사다리와 같은 장치를 쓴다.
   - **열린 설계:** (a) Next.js + R3F 로 임계 경로 125KB 가 가능한가(3D 는 지연 로딩이 필수), (b) 상한 50 초과 시 대기 UX, (c) 이 상한과 단계를 새 FR/AC 로 올릴지 — 명세 변경은 사용자 결정 사항이라 아직 하지 않았다, (d) design/18 §8·§12 와 S6-12 에 반영(후속).
6. **AC-013 은 원점/종단을 분리해 판정한다.** 합격 기준은 **원점 API p95 ≤ 300ms**(호스트 쪽에서 동시 50 부하를 만들고 nginx `$upstream_response_time` 으로 측정)다. Funnel 경유 종단 p95·LCP 는 **출발지당 동시 연결 ≤ 30** 으로 측정해 조건과 함께 공개하되 판정에서는 뺀다(목표: LCP ≤ 2.5초·종단 p95 ≤ 800ms, 제안값). 근거는 단일 출발지 동시 연결 40 개부터 Funnel 이 연결을 리셋하는 실측(⑧)이다. **반영:** 명세 AC-013·A-012·NFR(원문은 A-012 문장에 병기), design/08 §9 합격선, design/11 S9-2.

## 대안과 기각 이유
- **WebSocket 을 SSE 로 바꾼다**: 통과가 확인됐고 접속 성공률 문제는 SSE 도 같은 경로를 쓰므로 해결되지 않는다.
- **IP 를 소켓 주소로 얻는다**: 항상 Docker 게이트웨이(`172.17.0.1`)가 나온다.
- **`X-Real-IP` 도 신뢰한다**: 위조값이 그대로 통과했다.
- **지금 대역폭 때문에 Funnel 을 포기한다**: 무료·도메인 없음이라는 전제(ADR-003)에서 대안이 없고, 합계 상한이 서버·출발지 중 어느 것에 걸려 있는지 아직 모른다.

## 결과 (얻는 것 / 치르는 것)
- 얻는 것: ‘미검증 🔴’ 세 건 중 WebSocket 통과와 클라이언트 IP 가 실측으로 닫혔다. 대역폭은 숫자가 생겨 첫 방문 전송량 설계에 근거가 생겼다. 증거가 저장소에 남는다(ADR-050).
- 치르는 것: 대역폭 상한이 낮다는 불편한 사실을 문서에 적어야 하고, 접속 성공률 미달이 재접속 요건으로 설계를 늘린다.

## 위험과 완화
| 위험 | 완화 |
|---|---|
| 합계 상한이 출발지별이 아니라 서버 전체라면 방문자가 몰릴 때 모두가 느려진다 | 다른 출발지 동시 측정(다음 단계), 정적 자산 분리 검토, ADR-049 사다리(과부하 단계)가 대역폭 지표를 포함하게 함 |
| 출발지가 1곳이라 일반화할 수 없다 | 폰 테더링 등 다른 회선 측정을 같은 스크립트로 반복하고 결과를 추가 |
| 클라이언트 시계 편차·결과 덮어쓰기 같은 측정 도구 결함 | `ENV.md` 에 한계를 적고 도구를 수정했다. 핵심 수치는 최종 커밋 버전으로 재측정 |

| 에코 서버를 공개 주소로 노출한 시험 | 토큰 없으면 404, 시험 후 `funnel reset`·컨테이너 중지, 토큰 폐기 |

## 재검토 조건
다른 출발지 측정에서 합계 상한이 다르게 나올 때, Tailscale 이 Funnel 정책(대역폭·WebSocket)을 바꿀 때, 도메인을 확보해 Funnel 이 아닌 경로가 생길 때, 접속 성공률 합격선(≥99%)을 못 맞추는 원인이 밝혀질 때.
