# ADR-051: Tailscale Funnel 관문(G14) 실측 결과와 설계 반영
- 상태: **Proposed** (2026-11-10) — 측정 ①②③④⑤⑥(만료일)⑦⑧은 끝났다. 남은 것은 ⑥ 갱신 관찰, 호스트 재부팅 후 주소, 대역폭 시간 변동의 원인, 출발지별/전체 상한 구분이다. 결정 5·6 은 **사용자 결정(2026-11-10)**, 결정 1~4 는 제안(사용자 확인 대기).
- 날짜: 2026-11-10
- 근거: tech-stack §11 G14 ①~⑧ · ADR-003(Funnel 노출, 미검증 🔴 세 건) · ADR-008(원 접속 주소 신뢰) · ADR-022(관문 G14) · ADR-049(대역폭이 먼저 터질 가능성, HC-8) · ADR-050(증거 규칙) · ADR-033(호스트 프로필·공유 호스트)

## 맥락
공개 경로는 전부 Tailscale Funnel 하나이고(ADR-003), 그 성질 세 가지(WebSocket 통과, 대역폭, 클라이언트 IP)가 문서에서 확인되지 않아 ‘미검증 🔴’로 남아 있었다. 설계의 여러 결정(실시간 방식, 속도 제한 키, 첫 방문 전송량, AC-013 판정 방법)이 이 세 가지에 걸려 있다. 2026-11-10 에 실제 집 서버(`qd.tail91f132.ts.net`)에서 에코 서버를 Funnel 로 노출하고 개발 PC 에서 측정했다.

## 측정 결과
**조건:** 서버 = Xeon Bronze 3204, 62GB, Ubuntu 24.04(공유 호스트, 측정 시 로드 0.02~0.22), Funnel 443 → `127.0.0.1:28080` → `oven/bun:1` 컨테이너. 클라이언트 = 개발 PC WSL2(1차 01:35~02:00 UTC, 2차 04:14~04:44 UTC), 2차에는 휴대폰(iPhone Safari, 모바일 데이터)과 서버 자신(자기 공개 주소로 돌아오는 경로)을 출발지로 더했다. **같은 항목을 두 시간대에 쟀더니 값이 크게 달랐다**(③). 표기: **실측**(ADR-050 범례).

### ② 유휴 타임아웃
| 시험 | 서버 시계 | 의미 |
|---|---|---|
| `hb=0`(서버가 아무것도 안 보냄) | **960.0초에 서버(Bun `idleTimeout: 960`)가 끊음** (`1006`, `WebSocket timed out from inactivity`) | Funnel 구간은 **무 ping 유휴를 960초 이상 견딘다.** 실제 상한은 서버 설정이 막아 알 수 없다 |
| `hb=25` | 900초(관찰 상한)까지 유지, 하트비트 38개 수신 | 25초 하트비트로 최소 15분 유지 |

처음 해석(‘889초에 Funnel 이 끊었다’)은 틀렸다. 클라이언트 시계가 서버 시계보다 약 7% 느려(0.926·0.934) 960초를 889초로 쟀다. **지속 시간은 서버 시계로 판정한다.**

### ③ 대역폭 — 출발지·시간별
| 출발지 | 시각(UTC) | 단일 흐름 | 병렬 4 합계 | 병렬 16 합계 |
|---|---|---|---|---|
| 개발 PC | 01:4x | 0.41~0.78MB/s | **2.28** | **2.55** |
| 개발 PC | 04:34 (서버 쪽이 끊긴 동시 시도 중) | — | **0.64** | — |
| 개발 PC | 04:36 (단독, 같은 조건) | — | **0.50** | — |
| 휴대폰 1회차 | 04:19 | 0.44 | `Load failed` 로 중단 | — |
| 휴대폰 2회차 | 04:20~04:26 | 0.08 | 0.21 | 0.23 |
| 서버 자신(돌아오는 경로) | 04시대 | 0.28 | 1.26 | 15MB×16 에서 `ECONNRESET` 으로 중단 |
| 개발 PC, WS 64KB 10연결 | 01:40 | 합계 3.33, 왕복 p50 339ms · p95 736ms | | |

**대조(회선):** 서버 → 중립 호스트 직접 업로드 12.1MB/s(01시대) → 12.13·12.14MB/s(04시대 2회). 개발 PC → 중립 호스트 다운로드 62MB/s(01시대) → 48·57·58MB/s(04:43). 모두 실측.

- **두 회선은 하루 내내 그대로인데 Funnel 경유 처리량만 변했다.** 같은 개발 PC, 같은 조건(병렬 4)의 합계가 2.28 → 0.64 → 0.50MB/s 로 4.5배 낮아졌다. 병목은 집 회선도 클라이언트도 아닌 **Funnel 경로**이고, 그 성능이 **시간에 따라 크게 변한다.**
- 앞 판의 ‘합계 상한 약 2.5MB/s’는 **관찰된 최대**일 뿐 상한이 아니다. 계획에는 **0.5~2.5MB/s 범위**를 쓴다(단일 흐름은 좋을 때 0.3~0.8MB/s, 나쁠 때 0.1MB/s 안팎).
- 흐름을 늘리면 합계가 늘어나는 경향(단일 0.41 → 병렬 4 2.28)은 좋은 시각에 한해 보였다.
- **원인은 모른다.** 가설(미검증): ① 사용량에 따른 제한(오늘 수백 MB 를 흘린 뒤 낮아졌다), ② 입구 노드·경로 변경, ③ 혼잡. 구분 시험: 한 시간 이상 쉰 뒤 같은 조건으로 다시 재서 회복되는지 본다.
- **합계 상한이 출발지별인가 서버 전체인가는 미결이다.** 동시 시험이 서버 쪽 `ECONNRESET` 으로 성립하지 않았다.
- 서버 자신을 출발지로 한 값은 한 장비가 송수신·암호화를 모두 해서 다른 출발지와 같은 조건이 아니다. 병렬 16 에서 오래 도는 흐름이 리셋되는 현상은 개발 PC 의 5MB×16(31초)에서는 없었고, 원인은 모른다.

### ④ 클라이언트 IP
| 항목 | 결과 |
|---|---|
| `X-Forwarded-For` | Funnel 이 **실제 클라이언트 공인 IP 하나**를 넣는다. 클라이언트가 보낸 위조값(`203.0.113.7`)은 **덮어써져** 서버에 도착하지 않았다 |
| `X-Real-IP` | 클라이언트가 보낸 위조값이 **그대로 통과**했다 → 신뢰 불가 |
| 그 외 | `Tailscale-Funnel-Request: ?1`, `X-Forwarded-Host`, `X-Forwarded-Proto: https` |
| 소켓 주소 | `172.17.0.1`(Docker 게이트웨이, docker-proxy 경유) → 사용 불가 |
| WS 업그레이드 경로 | 같은 헤더가 붙는다 |
| 다른 출발지 | 서버 자신(자기 공개 주소)을 출발지로 했을 때 `X-Forwarded-For` 는 서버의 공인 IP 였다 → 출발지가 바뀌면 값도 그 출발지로 바뀐다 |
| 미확인 | IPv6 클라이언트, 클라이언트가 `X-Forwarded-For` 를 여러 값·긴 값으로 보낼 때의 정규화 |

### ⑦ 다른 회선(휴대폰)
iPhone Safari, 모바일 데이터. 1회차(04:19)는 단일 다운로드까지 정상(0.44MB/s)이었고 병렬 4 에서 `Load failed` 로 중단, 2회차(04:20~04:26)는 끝까지 갔지만 회선이 나빴다(작은 메시지 왕복 p50 141ms → 950ms, 단일 다운로드 0.44 → 0.08MB/s).
- 같은 기기·장소에서 5분 사이 5~7배 차이가 나 Funnel 한도와 모바일 회선 품질을 가를 수 없다. **휴대폰 수치는 판정에 쓰지 않고** 기록만 한다(실측, 판정 제외).
- 쓸 수 있는 것: 600KB 전송(첫 방문 흉내)은 회선이 좋을 때 약 0.9~1.0초(첫 회는 TLS 포함 2.85초), 나쁠 때 1.0~4.8초였다. **모바일 방문자에게는 LCP 2.5초가 보장되지 않는다.**
- 다음에 하려면 lab 페이지에 중립 호스트 대조 다운로드를 짝으로 넣어 그 순간의 휴대폰 회선 용량을 같이 잰다.

## 결정 (제안 — 사용자 확인 대기)
1. **WebSocket 은 Funnel 경유로 유지한다.** SSE 등 대체(ADR-003 ① 후속)는 필요 없다. 다만 개발 PC 기준 접속 성공률이 합격선에 못 미치고(계획 밖 실패 5/217) 연결 시간이 0.3초에서 1.8초(p50)까지, 간헐적으로 3~5초까지 변하므로, **클라이언트 재접속(지수 백오프)과 접속 지연 허용을 필수 요건**으로 삼는다(기존 설계에 있는 재접속·snapshot 복구가 근거를 얻는다).
2. **서버 하트비트는 25초 유지.** 무 ping 유휴가 960초 이상 견디므로 Funnel 은 하트비트 간격의 제약이 아니다. 간격은 우리 `proxy`(nginx) `proxy_read_timeout`(기본 60초)보다 짧아야 한다는 조건(G7)으로 정한다.
3. **원 접속 주소는 `X-Forwarded-For` 만 신뢰한다.** `X-Real-IP` 와 클라이언트가 지정할 수 있는 나머지 주소 헤더는 `proxy` 가 폐기한다. 소켓 주소는 쓰지 않는다. nginx 는 Funnel 쪽 홉(compose 네트워크 게이트웨이)에서 온 `X-Forwarded-For` 를 `realip` 로 받는다. 전제: 앱 진입 포트는 `127.0.0.1` 바인딩이므로 Funnel 외 경로로는 닿지 않는다(공유 호스트의 다른 로컬 프로세스는 신뢰한다). 이 결정으로 **G14 ④ ‘IP 미확보’ 조건이 해소**되어 ADR-049 HC-8(앱 읽기 bucket)은 발동하지 않는 쪽으로 판정한다. IPv6·다중값 시험 전에는 ‘제안’이다.
4. **측정 방법론:** 지속 시간은 서버 시계로 판정하고, 클라이언트 `performance.now()` 수치는 ±7% 불확실성을 적는다. 병렬 실행 결과 파일이 충돌하지 않도록 pid 를 붙이고, `dirty` 판정 버그를 고쳤다.

## 사용자 결정 (2026-11-10)

5. **동시 접속자 상한 50명 + 접속자 수에 따라 전송량을 나눈다.** 사용자 결정 원문: “동시 접속자 수 제한 50명 및 접속자 수에 따라서 전송량을 분할해야한다.” 정적 자산을 Funnel 밖으로 분리하는 안은 **확정하지 않는다**(합계 상한이 출발지별인지 전체인지 가른 뒤 재판단). 다만 2차 측정에서 처리량이 시간에 따라 4~5배 변하는 것이 드러나 이 보류의 전제(‘상한이 2.5MB/s 로 일정하다’)가 흔들렸다 — **재확인을 요청한다**(아래 열린 설계 (e)).
   - **근거 계산(추정):** 2.5초 창에 합계 C MB/s 로 보낼 수 있는 총량은 `C × 2.5MB` 이므로, 동시 첫 방문자가 N명이면 1인당 전송량 상한은 약 `C × 2.5 ÷ N` 이다. C 는 관찰 범위 0.5~2.5MB/s 다.

     | N | C = 2.5 (좋을 때) | C = 0.5 (나쁠 때) |
     |---|---|---|
     | 10 | 625KB | 125KB |
     | 20 | 312KB | 62KB |
     | 50 | 125KB | 25KB |
   - **단계표(제안 — 해석 확인 필요, C = 2.5MB/s 낙관 기준이므로 나쁠 때는 위 표의 오른쪽 열로 한 단계씩 내려가야 한다):**

     | 동시 접속자 N | 1인당 첫 화면 전송량 상한(압축 기준) | 비고 |
     |---|---|---|
     | ≤ 10 | ≤ 600KB | design/18 가정과 같음 |
     | 11 ~ 20 | ≤ 300KB | |
     | 21 ~ 50 | ≤ 125KB | |
     | > 50 | 거절하지 않고 **대기실** | 도착 순서대로 입장(ADR-049 HC-12, design/18 §6.8). 대기열 한도(200) 초과분만 `overloaded` |

   - **구조적 함의:** 단계와 무관하게 임계 경로(HTML + 필수 JS)는 가장 낮은 단계 상한(125KB) 안이어야 한다. 단계 차이는 **지연 로딩 자산**(이미지 해상도, 폰트 subset, 3D 씬, 장식 자원)이 만든다.
   - **접속자 수의 정의·전달(제안):** 서버가 ‘활성 WS 세션 + 최근 수 초 내 첫 방문 HTTP 세션’으로 N 을 계산하고, HTML 응답 시점에 단계(`payloadTier`)를 정해 클라이언트에 알린다. 경계 진동을 막는 히스테리시스는 ADR-049 사다리와 같은 장치를 쓴다.
   - **열린 설계:** (a) Next.js + R3F 로 임계 경로 125KB(나쁠 때 25KB)가 가능한가(3D 는 지연 로딩이 필수), (b) 상한 50 초과 시 대기 UX — **결정함: 대기실(순서 입장)**, 2026-11-11 HC-12(권장이었던 ‘즉시 503’에서 사용자가 변경), (c) 이 상한은 **FR-123·AC-040 으로 명세에 올렸다**(2026-11-10, 상한 50 과 503 동작만; 전송량 단계화는 ‘제안’으로 남겨 판정에 넣지 않았다), (d) design/18 §8·§12 와 S6-12 에 반영(후속), (e) **단계 기준을 상수로 두지 말고 서버가 관찰한 최근 송신 처리량(EWMA)에서 `C` 를 구해 동적으로 정하는 안**(제안). 처리량이 시간에 따라 4~5배 변하므로 상수 기준은 좋을 때 맞춰 두면 나쁠 때 틀린다. (f) 임계 경로 25KB 는 사실상 불가능하므로 나쁠 때는 ‘정적 텍스트 폴백(design/16)’으로 내리는 것이 현실적이다 — 정적 자산 분리 여부와 함께 결정이 필요하다.
6. **AC-013 은 원점/종단을 분리해 판정한다.** 합격 기준은 **원점 API p95 ≤ 300ms**(호스트 쪽에서 동시 50 부하를 만들고 nginx `$upstream_response_time` 으로 측정)다. Funnel 경유 종단 p95·LCP 는 **출발지당 동시 연결 ≤ 30** 으로 측정해 조건과 함께 공개하되 판정에서는 뺀다(목표: LCP ≤ 2.5초·종단 p95 ≤ 800ms, 제안값). 근거는 단일 출발지 동시 연결 40 개부터 Funnel 이 연결을 리셋하는 실측(⑧)이다. **반영:** 명세 AC-013·A-012·NFR(원문은 A-012 문장에 병기), design/08 §9 합격선, design/11 S9-2. 결정 5 의 상한 50 은 FR-123·AC-040·A-037 로 반영(design/11 S6-12, design/08 §AC 표, 추적표).

## 대안과 기각 이유
- **WebSocket 을 SSE 로 바꾼다**: 통과가 확인됐고 접속 성공률 문제는 SSE 도 같은 경로를 쓰므로 해결되지 않는다.
- **IP 를 소켓 주소로 얻는다**: 항상 Docker 게이트웨이(`172.17.0.1`)가 나온다.
- **`X-Real-IP` 도 신뢰한다**: 위조값이 그대로 통과했다.
- **지금 대역폭 때문에 Funnel 을 포기한다**: 무료·도메인 없음이라는 전제(ADR-003)에서 대안이 없고, 합계 상한이 서버·출발지 중 어느 것에 걸려 있는지, 시간 변동이 일시적인지 아직 모른다.

## 결과 (얻는 것 / 치르는 것)
- 얻는 것: ‘미검증 🔴’ 세 건 중 WebSocket 통과와 클라이언트 IP 가 실측으로 닫혔고, 재시작 후 설정 유지와 인증서 만료일도 확인했다. 대역폭은 **단일 숫자가 아니라 시간에 따라 변하는 범위(0.5~2.5MB/s)** 라는 것을 알게 되어 첫 방문 전송량 설계가 상수 기준으로 가면 안 된다는 근거가 생겼다. 증거가 저장소에 남는다(ADR-050).
- 치르는 것: 대역폭 상한이 낮다는 불편한 사실을 문서에 적어야 하고, 접속 성공률 미달이 재접속 요건으로 설계를 늘린다.

## 위험과 완화
| 위험 | 완화 |
|---|---|
| 합계 상한이 출발지별이 아니라 서버 전체라면 방문자가 몰릴 때 모두가 느려진다. 처리량이 시간에 따라 4~5배 변한다 | 동시 시험을 다시 하고(서버 쪽 리셋 원인 해소), 한 시간 이상 쉰 뒤 회복 여부를 잰다. 정적 자산 분리 검토, ADR-049 사다리(과부하 단계)가 관찰 송신 처리량을 입력으로 쓰게 함 |
| 출발지가 적고(개발 PC·휴대폰·서버 자신) 휴대폰·서버 자신은 조건이 불안정/비동등하다 | 안정적이고 서로 다른 공인 IP 를 가진 출발지를 하나 더 확보해 같은 스크립트로 반복하고 결과를 추가 |
| 클라이언트 시계 편차·결과 덮어쓰기 같은 측정 도구 결함 | `ENV.md` 에 한계를 적고 도구를 수정했다. 핵심 수치는 최종 커밋 버전으로 재측정 |
| 켠 직후 첫 연결 실패(원인 미상)가 운영에서 재발 | 클라이언트 재접속 필수(결정 1). `ws-watch` 로 정지→재개 시험을 추가 반복 |
| 에코 서버를 공개 주소로 노출한 시험 | 토큰 없으면 404, 시험 후 `funnel reset`·컨테이너 중지, 토큰 폐기 |

## 검증 방법
- 이 문서의 수치는 `spikes/g14-funnel/results/*.json` 과 1:1 로 대조된다. 재현: `spikes/g14-funnel/README.md`.
- 남은 항목(⑥ 갱신, 호스트 재부팅 후 주소, 대역폭 변동의 원인, 출발지별/전체 상한) 측정 후 이 ADR 을 갱신하고 상태를 Accepted 로 올린다.

## 재검토 조건
다른 출발지·다른 시각의 측정에서 처리량이 다르게 나올 때, 쉰 뒤 회복 여부가 가려졌을 때, Tailscale 이 Funnel 정책(대역폭·WebSocket)을 바꿀 때, 도메인을 확보해 Funnel 이 아닌 경로가 생길 때, 접속 성공률 합격선(≥99%)을 못 맞추는 원인이 밝혀질 때.
