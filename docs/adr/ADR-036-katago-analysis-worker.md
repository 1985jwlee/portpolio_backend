# ADR-036: KataGo 분석 워커 — 별도 프로세스, 2단계 분석, 선점·임대 큐
- 상태: **Accepted** (2026-11-05, 사용자 일괄 확정 U1)
- 날짜: 2026-11-04
- 근거: ADR-009(사후 분석)·006(전달 계층)·021(선점·임대)·024(Redis 이음새)·023(백오프) / KataGo 공식 문서 조사(2026-11-04)
- 구현 순서(P0 D24): Phase 2 — Phase 1 다음. 선행: Phase 1(`game.finished`), Phase 3(`ledger`). KataGo 실행 가능성 스파이크는 Phase 1 착수 전에 앞당겨 실행하는 것을 제안한다(P0 §1.4 G14).
- 관련 문서: [phases/01-baduk.md](../design/phases/01-baduk.md) §9

## 맥락
승패는 룰 엔진이 즉시 판정하고(ADR-009), KataGo 는 부정행위 의심을 사후에 분석해 **보상 상태만** 바꾼다. 무료 호스팅의 CPU·메모리에서 현실적으로 돌려야 한다.

조사(2026-11-04, 공식 저장소·문서): KataGo 는 MIT 라이선스이고 분리된 프로세스로 쓸 수 있다. **Analysis Engine** 은 표준 입력에 JSON 한 줄씩 질의를 받고 결과를 표준 출력에 비동기로 낸다(질의: `id`, `moves`, `rules`, `komi`, `boardXSize/YSize`, `analyzeTurns`, `maxVisits`; 응답: `moveInfos[]`(`move`·`order`·`winrate`·`scoreLead`·`prior`·`pv`), `rootInfo`). 순수 CPU 빌드(`-DUSE_BACKEND=EIGEN`, AVX2 변형 있음)와 작은 신경망이 있다. **CPU 에서의 초당 방문 수는 문서에 없어 미확인** — 스파이크로 측정한다.

## 결정 (제안)
1. **KataGo 워커는 별도 프로세스(컨테이너)** 로 분리한다 — 이 시스템의 첫 번째 서비스 분리. 언어/런타임은 KataGo 바이너리 + 얇은 TS 어댑터(분석 엔진 stdin/stdout 프로세스 관리).
2. **큐는 Postgres inbox 선점(DB 큐)이다**(P0 D4·D6·D23, [ADR-031](ADR-031-event-transport-streams.md)). 소비 순서는 **의존 체인**이다: `game.finished` → `ledger` 의 `reward-settler` 가 `EligibilityPolicy`(ledger 소유)로 자격을 판정해 통과하면 reward `PENDING` 을 만들고 `reward.pending_created {gameId, rewards[{rewardId,userId,color}]}` 를 발행 → **`analysis` 의 소비자가 이 이벤트로 `analysis_job`(`UNIQUE (game_id)`)을 멱등 생성**한다. 자격 미달 대국은 보상이 없으므로 분석하지 않고, 분석 작업은 reward 행이 이미 존재할 때만 생기므로 "분석이 보상보다 먼저 끝나는" 순서 의존이 없다. `game.review.requested` 는 폐기(ADR-009 개정).
3. **분석은 트랜잭션 밖**에서: 선점(`processing`, `claim_token`, `lease_until`) → 분석 → 토큰 일치 조건으로 **색별 결과 저장 + 색별 보상 전이를 한 트랜잭션**에서 한다. 판정 단위는 **색(참가자)** 이다 — `analysis_result` 는 `(game_id, color)`, 판정 대상 색은 `rewards[]` 의 색(패자 보상 0 이라 보통 승자 한 색, D4), 보상은 자기 색의 판정으로 `ledger.ConfirmRewardInTx`/`FlagRewardInTx`(**`rewardId` 키**, B12 허용 쌍 #6, `analysis`→`ledger`)를 호출한다. 분석이 길어 **임대는 토큰 조건으로 연장**한다(ADR-021 의 적용이며 ADR-023 의 예외가 아니다): 연장 간격은 임대의 1/3, ADR-023 의 "임대 ≥ p99×10, 핸들러 제한시간 ≤ 임대/2" 는 연장 간격과 한 번의 연장 단위에 적용하고 총 분석 시간에는 적용하지 않는다. 2단계 후에도 `INCONCLUSIVE` 이면 `CLEAN` 취급으로 `CONFIRMED`(감사·지표 기록).
4. **2단계 분석**: 1단계 정책 일치율(전 수 `maxVisits` 매우 작게, 신경망 한 번 평가) → 의심 구간만 2단계(방문 수 확대). 비용을 줄이고 CPU 에서도 현실적으로 만든다. 방문 수·분석 수 범위는 스파이크 후 결정(미확인).
4a. **`rules` 파라미터 (U11)**: 대국 규칙이 중국식·일본식 둘이 되었으므로 질의의 `rules` 는 대국에 스냅샷된 `rules`·`komi` 에서 만든다. **KataGo 가 지원하는 규칙 이름·옵션은 공식 문서로 확인하지 못했다 — 착수 시(S0 스파이크) 확인한다**(문서에 예시가 있는 것은 `tromp-taylor` 뿐). 확인 전 임시 방침은 `tromp-taylor` 근사 + `scoreLead` 지표 미사용이고 `analysis_result.report.rules_mapping`(`exact`/`approx`)에 기록한다. 질의 `moves` 는 항상 `game_event` 를 접은 **유효 수열**이다(분석은 레이팅 대국만 하고 레이팅 대국은 무르기 불허이므로 정상 시 전체 수열과 같고, 달라지면 불변식 위반으로 `failed`). 매핑 표는 [phases/01 §9.1](../design/phases/01-baduk.md).
5. **의심도**는 일치율·승률 손실 분포 등 여러 지표로 계산하고, 임계값은 실제 데이터로 보정하기 전까지 **자동 박탈 없음** — `FLAGGED` 까지만(ADR-009).
6. **자원 상한**: 워커는 **라이브 호스트에서 CPU 저우선순위로, 코어 2~3개로 제한**해 돌린다(U12 확정 2026-11-05; 집 서버는 Xeon Bronze 3204 6코어·62GB 라 Phase 2 스파이크에서 재측정). **'저우선'은 컨테이너에서 `nice` 로 보장되지 않으므로**(3차 검토 B18) compose 에 `cpus: "2"` + `cpuset: "4-5"`(전용 코어, 사이트용 0–3) + `cpu_shares: 128` 을 함께 두고 KataGo 탐색 스레드는 2 다 — **값의 정본은 ADR-033 결정 2**이고, 3코어(`cpuset: "3-5"`)는 S0 의 '분석 중 착수 p95' 와 사이트 부하 시험이 여유를 보인 뒤에만. 워커 컨테이너 메모리 제한을 두고, 분석은 대국 종료 후 큐 순서대로 **하나씩(동시 1, ADR-033 정본; 스파이크에서 CPU 여유가 확인되면 2 로 상향 검토)**. 메모리 한도는 P0 자원 추정(0.5–3GiB, 가정 1.5GiB)과 S0 스파이크 결과로 확정한다(잠정 2GB 는 OOM 여지가 있음). 분석 워커의 DB 권한은 `analysis` 스키마와 B12 쌍 #6 을 통한 `ledger` 전이에 한정하고, 이미지는 서버 래퍼 이미지와 분리된 `pf-analysis` 다. 실패·지연은 보상 `PENDING` 유지(자동 확정 유예는 두지 않음).
7. **분석 자체의 CPU 소비를 줄인다 (제안, 2026-11-13 추가).** 결정 6 은 ‘얼마나 쓸 수 있는가’(상한)이고, 이 결정은 ‘얼마나 덜 쓰는가’다. 서버에서 돌리기로 했고(브라우저 구동은 판정에 쓸 수 없다 — 사용자 기기의 결과는 위조 가능) 호스트는 GPU 없는 6코어 1.9GHz 공유 서버이므로 **분석량·신경망 크기·실행 시각**을 줄인다. 값은 모두 **제안**이고 사전 실측(아래 ‘검증 방법’)과 S0 스파이크 전에 확정하지 않는다.
   - **(a) 분석량 축소 — 효과가 가장 크고 판정 의미를 바꾸지 않는다.** ① 판정 대상 색이 둔 시점만 평가한다(`analyzeTurns` 를 그 색의 차례로 한정 → 전체 수의 약 절반). ② 초반 N수(정석 구간)·패스·합법 수가 하나뿐인 수·종반 계가 단계의 수를 제외한다(N 은 제안, 데이터로 보정). ③ 1단계 평가 수에 상한 K 를 둔다. ④ **조기 종료**: 표본 크기 규칙(phases/01 §9.5)으로 이미 `CLEAN` 임이 충분히 확실해지면 나머지 수를 평가하지 않는다. 결론이 안 나면 `INCONCLUSIVE`(= `CLEAN` 취급)이므로 줄여도 박탈 방향의 오류는 늘지 않고 **놓칠 가능성**만 는다(‘기술 시연’이라는 B8 의 범위와 같은 방향). 대략적 산술(가정, 미측정): 250수 대국 → 승자 색 약 125수 → 제외 후 약 100수 → 1단계 평가 횟수가 전 수 평가의 약 40%.
   - **(b) 신경망 계층화.** 1단계(정책 일치율, `maxVisits` 1 수준)는 **작은 신경망**(b6c96·b10c128 급), 2단계(의심 수만 방문 수 확대)만 큰 신경망(b18 급)을 쓴다. 사전 실측(6스레드, Eigen)으로 초당 방문 수는 b6c96 약 600·b10c128 약 265·b18c384nbt 약 16 이라 1단계에 b18 을 쓰면 250수에 약 25초(코어 3개 추정), b10 이면 1초 안쪽이다. **주의**: 정책 일치율의 임계는 모델에 종속이므로 임계 보정은 모델을 고정한 채 하고, 모델·버전은 `analysis_result.report` 에 기록한다.
   - **(c) 중복 평가 제거.** 국면 키(규칙 + 덤 + 수열 해시 + 모델 버전)로 평가 결과를 저장해 같은 국면의 재평가를 건너뛴다(초반 정형 국면에서 효과를 기대하나 적중률은 미측정). 같은 대국의 재분석은 이미 `UNIQUE (game_id)` 로 막혀 있다. KataGo 내부 신경망 캐시(`nnCacheSizePowerOfTwo`)는 메모리와 맞바꾸는 값이라 크기는 스파이크에서 정한다.
   - **(d) 실행 시각과 부하 연동 (큐 적체는 허용 — 지연은 보상 `PENDING` 유지일 뿐 CPU 비용이 아니다).** ① 작업 선점을 **오프피크 창**(예: 01~06시 KST, 제안)으로 한정한다. ② 선점 전에 호스트 부하(loadavg)와 앱 지연 지표를 보고, 임계를 넘으면 선점을 미루고 백오프한다(ADR-023). ③ 실행 중에도 임계를 넘으면 현재 작업을 **수 단위 체크포인트**(1단계 완료 수 인덱스)까지 저장하고 임대를 반납해 일시정지한다. 재개는 처음부터 다시 하지 않는다. ④ **일일 CPU 예산**(CPU-초/일, 값은 스파이크 후)을 넘으면 남은 작업을 다음 창으로 넘긴다.
   - **(e) 프로세스 수명.** 큐가 비면 KataGo 프로세스를 **종료**(예: 유휴 10분 후)해 유휴 CPU·메모리를 돌려주고, 작업이 생기면 다시 띄운다. 모델 로딩 시간(b18 약 95MB)이 비용이므로 상시 상주와의 선택은 스파이크에서 측정한다(미측정).
   - **(f) 하드 제한은 그대로 둔다**: `cpus`·`cpuset`·`cpu_shares`(ADR-033 결정 2), 탐색 스레드 = `cpus`, 동시성 1, AVX2 Eigen 빌드. (a)~(e)는 이 제한 안에서 소비량을 줄이는 층이다.
   - **(g) 분리**: 사용자의 **복기·형세 판단** 요청(판정 용도 아님)은 서버 분석 큐에 넣지 않는다. 브라우저 측 구동 가능성은 별도 스파이크 후보로 두고(미결, phases/01 §19) 레이팅·보상 판정 경로와 섞지 않는다.
   - **열어 둔 질문(채택하지 않음)**: 일부 대국만 분석하는 **표본 분석**은 CPU 를 가장 많이 줄이지만 ‘분석되지 않은 대국의 보상을 어떻게 확정하는가’라는 **보상 정책 변경**(ADR-009)이 필요하다. 이 ADR 에서는 채택하지 않고 phases/01 §19 에 질문으로 남긴다.
   - **관측**: `pf_analysis_cpu_seconds_total{stage}`·`pf_analysis_positions_total{stage, cache}`·`pf_analysis_deferred_total{reason=window|load|budget}`·`pf_analysis_model_load_seconds`(phases/01 §13 지표표). 대국당 CPU-초 목표는 사전 실측 후에 정한다.

## 설계 상세
모듈 이름은 `analysis`(P0 §2.1)다. 초기 초안의 `review` 모듈·`review.requested` 이벤트·`review.completed/failed` 는 각각 `analysis`·(없음)·`analysis.completed/failed` 로 통일했다.

상태 머신(`analysis_job`), 의심도, 결과 포맷, 지표는 [phases/01-baduk.md](../design/phases/01-baduk.md) §9 가 정본이다.

## 대안과 기각 이유
- **룰 엔진/WS 서버와 같은 프로세스**: 분석이 CPU 를 점유해 실시간 지연을 해친다.
- **GPU 전제**: 무료 호스팅에서 불가. 선택 사항으로만 남긴다.
- **외부 분석 서비스(SaaS)**: 외부 의존·비용(ADR-015 무료 원칙).
- **분석 없이 휴리스틱만**: 서사와 ADR-009 의 취지를 잃는다. 대안으로 1단계만 쓰는 축소 운영은 허용.

## 결과
- 얻는 것: 실시간 경로와 분리된 CPU 격리. Phase 2 는 Redis 없이 Postgres 만으로 end-to-end 가 닫힌다. **솔직한 범위(3차 검토 B8)**: 보정 데이터가 없는 동안 이 분석은 부정행위를 실제로 잡는 장치라기보다 **기술 시연**(서비스 분리·선점 큐·트랜잭션 밖 분석)이고, 보상 파밍 방어의 실질은 자격 규칙(패자 보상 0·색당 최소 수·기권 축소·일일 한도, phases/01 §10.3)이 맡는다. Phase 2 설계 재검토에서 1단계만 운영하는 범위 축소를 함께 검토한다.
- 치르는 것: 컨테이너·모델 파일(수십 MB~수백 MB, 미확인) 관리, 방문 수 튜닝, 모의 데이터로는 임계값 보정 불가.

## 위험과 완화
| 위험 | 완화 |
|---|---|
| CPU 에서 너무 느림 | 2단계 분석, 분석 수 제한, 작은 신경망, 스파이크로 사전 측정 |
| ARM(Oracle, 미추진) 에서 최적 빌드 부재 | 집 PC(AVX2) 우선, ARM 은 측정 후 판단(미확인) |
| 모델 파일 라이선스·크기 | 모델 출처·라이선스 확인 후 저장소 밖(볼륨)에 보관 |
| 임계값 오탐 | 자동 박탈 금지, 수동 검토 |
| 분석이 사이트 CPU 를 점유 | 결정 6 의 하드 제한 + 결정 7 의 분석량 축소·오프피크·부하 연동 일시정지 |
| 분석량을 줄여 부정행위를 놓침 | 놓침은 허용 방향(`INCONCLUSIVE` = `CLEAN`), 보상 파밍의 실질 방어는 자격 규칙(phases/01 §10.3) |
| 큰 신경망 임계가 작은 신경망에 그대로 맞지 않음 | 모델 고정 상태에서 임계 보정, 모델·버전을 결과에 기록 |

## 검증 방법
S0 스파이크: 후보 신경망별 초당 방문 수, 250수 대국 정책 일치율 소요 시간, 메모리, **분석 중 착수 p95**(분석을 돌리는 동안 대국 명령 응답·push 지연이 P0 D10 예산을 지키는지 — `cpuset` 분리의 실효 검증). 선점·임대·재시도 카오스(워커 강제 종료 후 회수). **결정 7 의 효과 검증**: 같은 대국 집합에서 ‘전 수 평가’ 대비 (a) 분석량 축소·(b) 신경망 계층화·(c) 국면 캐시 적중률의 **대국당 CPU-초**와 판정 결과 일치율(CLEAN/SUSPECT 가 달라지는 비율), (e) 모델 로딩 시간, (d) 일시정지·재개의 체크포인트 정확성(재개 후 결과가 처음부터 한 결과와 같은가).

**사전 실측 (2026-11-05, 개발 PC i5-12400 6코어·AVX2, KataGo v1.18.1 Eigen(CPU) 빌드, `katago benchmark`, 19×19, 다른 작업이 조금 도는 상태)**: 초당 방문 수 — b6c96: 6스레드 약 600 · 4스레드 약 420 · 2스레드 약 250 / b10c128: 약 265 · 205 · 110 / b18c384nbt(모델 약 95MB): 약 16 · 14 · 8. 즉 **GPU 없이 CPU 로 돌아간다.** 250수 대국 추정(코어 3개, 측정값 보간이며 직접 잰 값이 아님): 1단계(수당 신경망 1회) b18 약 25초·b10 1초 안쪽, 2단계(의심 20수 × 100 방문) b18 약 3분·b10 약 10초. 큐 처리(동시 1)라 b18 도 감당 가능하나 대국이 몰리면 대기열이 길어진다. **미측정**: 메모리 사용량, 집 서버 실제 CPU, 웹·DB 동시 부하 하의 값, 모델별 부정행위 탐지력(임계값 보정 데이터 필요). **집 서버는 Linux, Intel Xeon Bronze 3204(6코어, 1.9GHz, 하이퍼스레딩 없음), RAM 62GB, AVX2 지원 확인(사용자 `lscpu` 결과, 2026-11-05)**: 위 수치는 AVX2 빌드이고 AVX2 가 있으므로 **AVX2 Eigen 빌드를 쓸 수 있다**(구형 Xeon 이라는 우려는 해소). 다만 개발 PC(i5-12400, 최대 4GHz대·12스레드) 대비 클럭이 낮고 스레드가 6개뿐이라 **개발 PC 수치의 대략 절반 안팎을 예상한다(추정, 미측정)** — 외부 자료상 AVX2 빌드가 약 1.4~1.6배 빠르다(검색 요약, 직접 검증 아님). 코어당 클럭도 낮을 수 있어 **집 서버에서 `katago benchmark` 를 다시 재야 한다**(이 PC 수치의 절반 이하까지 열어 두고 모델을 고른다). 잠정 방침: 기본 b18c384nbt, 대기열 지연 시 b10c128 로 내리는 설정(`KATAGO_MODEL`).

## 실서비스라면
GPU 분석 풀과 분석 결과 캐시, 모델 버전 관리, 이의 제기 절차를 둔다.

## 재검토 조건
KataGo 규칙 매핑이 근사(`approx`)로만 가능해 의심도 지표가 규칙별로 크게 흔들릴 때. 스파이크에서 CPU 분석이 비현실적일 때(분석 범위 축소 또는 외부 GPU 옵션). 임계값 보정 데이터가 쌓였을 때.
