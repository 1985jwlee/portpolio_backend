# ADR-004: 기술 스택 — Bun+Elysia / Next.js+R3F / WebSocket 단일 / 공유 타입
- 상태: Accepted
- 날짜: 2026-11-03
- 근거: 원 계획안 모순 #8·#13 / 명세 Overview, FR-004·050 / 인터뷰 R4-Q2·Q3

## 맥락
타깃은 백엔드 중심 풀스택 엔지니어 서사다. 원 계획안은 프론트에 Unity WebGL 임베딩을 두었다가 three.js 로 교체했고, 통신에서 TCP/IP 와 WebSocket 이 섞여 있었다(실제 설계는 WebSocket 만 다룸).

## 결정
- 백엔드: **TypeScript + Bun + ElysiaJS**, DB 는 **Postgres**.
- 프론트엔드: **Next.js(App Router)**. 게임 화면은 **three.js(React Three Fiber)**. Unity WebGL 은 쓰지 않는다.
- 통신: **WebSocket 단일 프로토콜**(공개/비공개 채널 분리).
- **메시지 프로토콜은 공유 타입 패키지**(`packages/protocol`)로 정의해 서버·클라이언트가 같은 타입을 쓴다.
- 표시 언어는 한국어+영어.

## 설계 상세

### 공유 프로토콜 패키지
- 모든 WebSocket 메시지는 공통 봉투를 가진다: 종류(`type`), 메시지 식별자, 시각, 순번(재접속 시 놓친 것 복구용), 페이로드.
- 서버는 수신 메시지를 스키마로 검증한 뒤에만 처리한다. 클라이언트는 같은 타입으로 송수신한다.
- 버전 필드를 두어 비호환 변경을 감지한다.

### 채널
| 채널 | 용도 | 인증 |
|---|---|---|
| `/ws/public` | 공개 브로드캐스트(집계, 흐름 요약, 이후 재고·관전) | 익명 세션 허용 |
| `/ws/private` | 개인 대상(내 이벤트 상세, 이후 대국·채팅) | 세션 또는 로그인 |

### 프론트엔드
- 소개·아키텍처 페이지는 서버 렌더링(첫 화면 속도, 검색 노출). 데모는 클라이언트 컴포넌트.
- 3D 게임 화면(Phase 1)은 클라이언트 전용 컴포넌트로 SSR 에서 제외한다. 서버 확정 후 반영하는 단방향 동기화를 쓰고 낙관적 UI 는 쓰지 않는다(서버 권위 유지).
- ko/en 은 경로 기반 전환. 번역 라이브러리는 구현 시 선정(미결).
- ORM/쿼리 도구는 구현 시 선정(미결). 후보로 Drizzle 이 있고 이 저장소에 관련 스킬이 있다.

## 대안과 기각 이유
- **Nest/Spring 등 JVM 생태계**: JD 가 그쪽이면 지원 비중을 낮추거나 이력서에서 "TS 기반 설계 역량"을 강조한다. 이 프로젝트의 서사와 타입 공유 이점이 줄어든다.
- **Go 백엔드**: 동시성 서술은 좋으나 프론트와 타입 공유가 안 된다.
- **Unity WebGL**: 보드게임에는 과하다. 빌드 용량·로딩·브릿지 비용이 크고 서버와 타입 공유가 안 된다. 경력 9년은 이력서·README 배경 문단으로 어필한다.
- **TCP 직접 소켓**: 브라우저 클라이언트에 맞지 않는다.

## 결과
- 얻는 것: 한 언어·한 타입 체계, 낮은 자원 사용(무료 호스팅에 유리).
- 치르는 것: Elysia 는 JVM 생태계보다 사례가 적다. 필수 라이브러리의 Bun 호환성을 계속 확인해야 한다.

## 위험과 완화
| 위험 | 완화 |
|---|---|
| 라이브러리가 Bun 에서 동작하지 않음 | 도입 전 호환성 확인(ADR-012 에서 먼저 확인) |
| 프로토콜 변경 시 서버·클라 불일치 | 공유 패키지 + 버전 필드 + 타입 검사 CI |

## 검증 방법
CI 타입 검사가 서버·클라 양쪽 컴파일을 요구한다. 프로토콜 변경 PR 이 한쪽만 고치면 실패한다.

## 실서비스라면
동일하게 TypeScript 로 가되, 팀이 크면 서비스 경계를 스키마 계약 기반으로 나눈다.

## 재검토 조건
Bun 런타임 문제가 운영에서 반복되거나 필수 라이브러리가 Bun 에서 동작하지 않을 때.
