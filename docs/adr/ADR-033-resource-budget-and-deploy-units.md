# ADR-033: 자원 예산과 배포 단위 — 상시 60% 이하, CPU 예산 분리, 같은 이미지 유지
- 상태: **Accepted** (2026-11-05, 사용자 일괄 확정 U1)
- 날짜: 2026-11-04
- 근거: 무료 호스팅 제약(집 PC 16GB 기준 / Oracle 24GB 는 미추진, 참고용) / M1 실측(Bun 서버 36–90MB, Next 164MiB, Envoy 17–54MiB) / 이번 유휴 측정(postgres 56MiB, nginx 7.5MiB, prometheus 46MiB, grafana 440MiB, redis 6.8MiB, valkey 5.9MiB) / ADR-002
- 관련 문서: [phases/00 §10~11](../design/phases/00-platform-evolution.md)

## 맥락
Phase 가 올라가며 컨테이너와 레플리카가 늘고, KataGo 는 CPU·메모리를 크게 쓴다. 상한 없이 늘면 라이브 사이트가 위험해진다.

## 결정
1. **라이브 상시 메모리 합은 호스트 RAM 의 60% 이하**로 유지한다(16GB 면 9.6GiB).
2. **KataGo 분석은 메모리와 별도로 CPU 시간 예산**을 둔다: 스레드·동시성 1·방문 수 상한·낮은 우선순위, 사이트용 코어와 분리. **'저우선'은 컨테이너에서 `nice` 만으로 보장되지 않는다**(`nice` 는 같은 cgroup 안에서만 의미가 있고, `cpu_shares` 는 경합할 때만 작동하며, `cpus` 는 상한(쿼터)일 뿐 사이트 코어를 비워 두지 않는다). 그래서 세 개를 **함께** 명시한다(제안값, 62GB·6코어 호스트 기준, U12 의 '코어 2~3개'와 같은 범위): compose `analysis-worker` 에 `cpus: "2"`(쿼터 상한) + `cpuset: "4-5"`(코어 4·5 전용 — **하드 분리**, 사이트용은 0–3) + `cpu_shares: 128`(기본 1024 대비 경합 시 가중치). KataGo 탐색 스레드는 `cpus` 와 같은 2. 3코어로 올리는 것은 S0 스파이크의 '분석 중 착수 p95(P0 §10.2 의 대국 지연 예산)' 와 사이트 부하 시험이 여유를 보인 뒤에만(`cpuset: "3-5"`, 사이트 0–2). 정본 값은 이 항이고 P0 §11.2·P1 §9·ADR-036 은 이 값을 따른다.
3. 컨테이너 수 증가는 **Redis 1개(Phase 3, 단일 인스턴스)와 analysis-worker 1개(Phase 2, 별도 이미지 `pf-analysis`)** 뿐이다. 분석 동시성은 **1** 이고(늘리려면 CPU 예산을 다시 산정), 메모리 한도는 S0 스파이크 실측 후 정한다. 나머지는 같은 이미지의 엔트리포인트·레플리카로 푼다(ADR-002).
4. **Phase 4 배포 단위**: `api`, `ws-gateway`, `worker`, `web`(+ 레플리카). `ws-gateway(site|room)` 분화는 `/ws/room`(6a) 이후 재평가, `analysis-worker` 는 Phase 2 에 합류(구현 순서 D24: 바둑 마지막). 롤링은 M1 G8 패턴(readyz 503 → bye/1001 → preStop 5초)을 재사용한다.
5. 총합 추정과 그 근거는 phases/00 §11 에 두고, **측정값과 추정값을 구분**해 Phase 시작 때마다 실측으로 갱신한다.

## 설계 상세
구현 순서(D24) 기준 누적: M1 약 1.12–1.54GiB(구성요소 합: phases/00 §11.1 의 하한/상한을 직접 더함, 추정), Phase 3 약 1.40–1.84GiB(redis 상한 256MiB 로 계산), Phase 4 약 1.60–2.14GiB — 이력서 제출 가능 시점(M1+3+4)의 합이다. 이후 5·6a~6d·1 은 컨테이너 추가 없이 약 1.7–2.3GiB, Phase 2 에서 KataGo(1.5GiB 가정) 합류로 약 3.2–3.8GiB. 16GB 호스트 대비 각각 약 7–10%, 9–12%, 10–13%, 최종 20–24%. KataGo 메모리는 **미확인**(모델·스레드 선택 후 측정). Grafana 유휴 440MiB 가 단일 최대 항목이므로 Phase 시작 때 유지 필요성을 점검(공개 대시보드 필수 아님이면 부하 시 기동 조정).

**12GB(2 OCPU) 열 — 참고용(Oracle 미추진, 2026-11-05)** — 호스트가 12GB 일 때의 같은 합계(MiB, 12GB = 12,288MiB 로 환산, 추정):

| 시점 | 합계 (MiB) | 16GB 대비 | 12GB 대비 |
|---|---|---|---|
| M1 | 1,148–1,582 | 약 7–10% | 약 9.3–12.9% |
| Phase 3 | 1,434–1,884 | 약 9–12% | 약 11.7–15.3% |
| Phase 4 | 1,638–2,191 | 약 10–13% | 약 13.3–17.8% |
| 5·6a~6d·1 | 1,741–2,355 | 약 11–14% | 약 14.2–19.2% |
| 최종(Phase 2 의 KataGo 합류) | 3,280–3,924 | 약 20–24% | 약 26.7–31.9% |

메모리 60% 규칙은 12GB 에서도 통과한다. **그러나 2 OCPU 에서는 CPU 예산이 먼저 걸린다**: 결정 2 의 `cpuset` 분리가 KataGo 에 코어를 하나 내주면 사이트용(api·ws-gateway·worker·web·postgres·redis)에 코어 1개 안팎만 남아 D14 의 CPU 분리가 사이트 지연을 오히려 키울 수 있다. 완화: 12GB/2 OCPU 에서는 KataGo 를 오프피크·큐 적체 허용으로만 돌리고 방문 수 상한을 낮추며, 실측 전에는 분리를 확정하지 않는다.

## 대안과 기각 이유
- **상한 없이 운영**: 사고 위험.
- **KataGo 를 외부 호스트로**: 무료·무카드 원칙과 단순성 훼손. 필요 시 재검토.
- **Grafana 제거**: 공개 지표 대시보드가 이 사이트의 핵심 볼거리(FR-061)라 유지.

## 결과
- 얻는 것: 단계마다 자원 위험이 숫자로 보이고, 분리 시 사이트 보호 규칙이 있다.
- 치르는 것: Phase 시작 때 실측 갱신 작업, CPU 분리 설정 관리.

## 위험과 완화
| 위험 | 완화 |
|---|---|
| KataGo 가 예상보다 큼 | 작은 모델/스레드 제한, 큐 적체 허용, 오프피크 실행 |
| (참고용, Oracle 미추진) 2 OCPU(12GB)에서 CPU 분리가 사이트 코어를 거의 남기지 않음 | 메모리보다 CPU 예산이 먼저 걸린다. 분리 전에 사이트 부하 시험으로 코어 배분을 실측, 불가하면 분석을 오프피크 전용으로 |
| 개발 PC(WSL2)와 라이브 호스트의 자원이 다름(Oracle 은 미추진) | 라이브 호스트는 네이티브 Ubuntu 24.04·6코어 1.9GHz·62GB 로 실측 확인(위 '호스트 프로필'). 병목은 메모리가 아니라 코어당 클럭이므로 관문·부하 시험을 호스트에서 다시 측정 |
| 레플리카 증가로 DB 커넥션 한도 | 커넥션 풀 상한 표 작성(영역 설계에서) |

## 검증 방법
Phase 시작·종료 때 `docker stats` 스냅샷을 문서에 기록, 부하 시험 중 호스트 RAM 60% 경보(F17).

## 실서비스라면
오토스케일·전용 노드 풀·리소스 쿼터로 워크로드를 격리하고 비용 지표를 둔다.

## 재검토 조건
호스트 변경, KataGo 실측 결과, Grafana 대체/제거 결정.

## 관련 ADR
ADR-002, ADR-014, ADR-022, ADR-024, ADR-030

## 호스트 프로필 (실측, 2026-11-05 — 사용자 `lscpu`/`free` 결과)
- **CPU**: Intel Xeon Bronze 3204, 6코어(하이퍼스레딩 없음, `CPU(s)=6`), 기본 1.9GHz, **AVX2 지원 확인**(`grep -c avx2` = 6). Bun x64 기본 빌드가 동작할 전제(SIGILL 위험 없음)가 충족된다.
- **메모리**: 총 62GB(사용 9GB, 페이지 캐시 49GB). 이 문서의 12GB·24GB 열은 모두 이 호스트에 비해 보수적이다. 병목은 메모리가 아니라 **코어당 클럭이 낮은 6코어**(D14 의 CPU 분리 예산)다.
- **OS·디스크(사용자 출력, 2026-11-05)**: Ubuntu 24.04.2 LTS(네이티브 리눅스, WSL2 아님). NVMe SSD 3개 — 시스템 238.5GB(사용 99GB, 여유 123GB, 루트 `/`)와 각 1.9TB 2개(용도 미정). **모두 SSD(`ROTA=0`)이므로 HDD 전제의 I/O 우려는 낮다.** 시스템 디스크 여유가 123GB뿐이므로 이미지·로그·백업이 쌓이는 위치는 대용량 NVMe 쪽으로 분리하는 것이 안전하다(백업은 **다른 물리 디스크**에 둔다 — 설계 검토 6번).
- 관문(G2·G3·G14)과 k6 부하 시험은 **이 호스트에서 다시** 측정한다(개발 PC 수치는 참고용).

## 공유 호스트와 포트 배치 (사용자 실측 출력, 2026-11-10)
- **이 호스트는 포트폴리오 전용이 아니다.** 다른 서비스(호스트 서비스와 컨테이너)가 이미 동작한다. 구성 목록은 외부에 노출 면 정보가 되므로 이 저장소에 적지 않는다. 따라서 위 자원 수치는 "전용 호스트"가 아니라 **배경 부하가 있는 공유 호스트**에서 해석한다 — 관문·부하 시험은 측정 시점의 호스트 부하(`uptime`, 상시 CPU 사용 프로세스)를 원시 결과와 함께 기록한다(ADR-050).
- **포트폴리오가 쓰는 호스트 포트는 둘뿐이고 모두 루프백 전용이다.**

  | 용도 | 호스트 바인딩 | 공개 경로 |
  |---|---|---|
  | 앱 진입 nginx(컨테이너) | `127.0.0.1:28080` → 컨테이너 80 | Funnel 443 → `qd.tail91f132.ts.net` |
  | Grafana 공개 대시보드 | `127.0.0.1:28081` | Funnel 8443 (다른 origin) |

  - compose 의 `ports:` 는 반드시 `127.0.0.1:` 접두를 붙인다(생략하면 `0.0.0.0` 에 열린다). 앱·Postgres·Redis·워커는 `ports:` 를 쓰지 않고 compose 네트워크 안에서만 통신한다.
  - 포트는 구현 시작 시 `ss -ltn | grep <포트>` 로 비어 있음을 다시 확인한다(이 서버는 다른 서비스가 포트를 점유한다).
  - Funnel 연결: `tailscale funnel --bg --https=443 http://127.0.0.1:28080`, `--https=8443 http://127.0.0.1:28081`. Funnel 은 서버의 인바운드 포트를 열지 않으므로 공유기·호스트 방화벽 변경이 필요 없다.
- **방화벽 전제:** 호스트 방화벽은 firewalld 이고 **Docker 가 게시한 포트는 firewalld 의 허용 목록을 우회한다**(허용 목록에 없는 포트도 열림을 접속 시험으로 확인). 포트폴리오는 컨테이너 포트를 루프백에만 게시해 이 문제를 구조적으로 피한다.
- **디스크:** 위 대용량 NVMe 2개는 **RAID1(미러)** md 배열(`/dev/md127`, `/raid`, 약 1.9TB, 2/2 미러 정상 — 사용자 `dmesg` 출력, 2026-11-10)이다. 월 1회 `data-check` 가 정상 종료된다. 미러는 디스크 한 개 고장에 대한 가용성일 뿐 **백업이 아니다**(실수 삭제·랜섬웨어는 두 디스크에 동시에 반영된다). 따라서 Postgres 데이터는 `/raid` 에 두되 **백업은 다른 물리 디스크**(루트 NVMe 또는 외부 저장소)에 둔다는 원칙을 유지한다. 부팅 로그에 비정상 종료 뒤 파일시스템 복구(`recovery complete`) 기록이 있어 정전에 취약할 수 있으므로, WAL 보관·fsync 설정과 복구 절차를 S0 호스트 준비에서 다시 확인한다.
- **도구:** 호스트의 Docker 는 Ubuntu 패키지(29.1.3)이고 `docker compose` 플러그인이 **설치돼 있지 않다**(실측). 구현 시작 전 `docker-compose-v2` 패키지 설치가 필요하다(S0 호스트 준비).
- **Tailscale:** 머신 이름 `qd`, Funnel 활성화 확인(2026-11-10). WebSocket 통과·대역폭·클라이언트 IP 는 G14 에서 측정한다.
