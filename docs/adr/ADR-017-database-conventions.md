# ADR-017: 데이터베이스 규약 — 모듈별 스키마, 스키마 간 FK 없음, 사본은 재구성 가능
- 상태: Accepted
- 날짜: 2026-11-03
- 근거: ADR-001·005·008, 명세 FR-080·AC-011 / 상세 구조는 [database-schema.md](../domains/database-schema.md)

## 맥락
테이블 구조를 잡기 전에 **모든 테이블에 공통으로 적용되는 규칙**을 정해야 한다. 이 규칙이 없으면 모듈 경계(ADR-001)가 DB 에서부터 무너지고, 보관 정책(ADR-008)과 프라이버시 요구가 테이블마다 제각각 구현된다. 또한 이 프로젝트는 "정합성을 증명한다"가 목적이므로 정본과 사본의 관계가 설계에서 명시돼야 한다.

## 결정

| # | 규약 | 이유 |
|---|---|---|
| 1 | **모듈마다 Postgres 스키마 하나, 단독 소유.** 남의 테이블을 읽지 않는다 | 모듈 경계를 DB 에서 강제 |
| 2 | **스키마 간 FK 를 두지 않는다.** 다른 모듈의 행은 id 값으로만 참조 | FK 는 모듈 간 마이그레이션·배포 순서를 묶는다 |
| 3 | 기본키는 **앱이 생성하는 시간순 정렬 가능한 uuid(v7)** | 순번 노출·추측 방지, 목록 페이지네이션을 id 순으로 가능, 분산 생성 가능 |
| 4 | 시각은 전부 `timestamptz`(UTC) | 시간대 혼선 방지 |
| 5 | 열거형은 Postgres `enum` 대신 `text` + `CHECK` | 값 추가 시 마이그레이션 부담 감소 |
| 6 | 금액·수량은 **정수 최소 단위**, 환율만 `numeric` | 부동소수 오차 배제 |
| 7 | 사용자 콘텐츠는 **상태 변경으로 숨기고 물리 삭제는 보관 정책 작업만** | 사후 숨김 모델(ADR-008), 감사 가능 |
| 8 | 관리자 조치·원장·감사 로그는 **추가 전용** | 이력 변조 방지 |
| 9 | **읽기 모델(프로젝션)은 `<m>_read` 스키마에 두고, 정본에서 재구성 가능해야 하며 주기적으로 대조한다.** 명령은 읽기 모델을 직접 쓰지 않는다(ADR-018) | 결과적 일관성을 시험 가능하게 |
| 10 | 보관 기간이 **테이블 설계의 일부**다(보관 정책 표를 문서에 둔다) | 프라이버시·디스크 제약 |
| 11 | 마이그레이션은 앞으로만(forward-only) | 롤백 스크립트의 신뢰 문제 회피 |
| 12 | 메시지를 받는 모듈은 자기 스키마에 **`inbox_message`** 를 둔다(공통 형태, ADR-020) | 정확히 한 번 효과, 수신/처리 분리 |
| 13 | "한 번만" 처리할 항목은 **선점 공통 컬럼**(`status`·`claim_token`·`claimed_by`·`lease_until`·`attempts`)을 갖는다. 선점 상태 이름은 `processing`(비즈니스 `PENDING` 과 구분) | 처리 전 선점, 임대·토큰(ADR-021) |
| 14 | 사용자가 동시에 수정하는 엔티티는 **`version`** 컬럼을 갖는다 | 낙관적 갱신(ADR-021) |
| 15 | 읽기 모델 행은 **`last_seq`** 를 가져 오래된 이벤트를 무시한다 | 재전달·역전에도 같은 결과 |

## 설계 상세

### 스키마 간 참조의 책임
FK 가 없으므로 무결성은 **앱 코드와 이벤트**가 진다. 예: 세션이 만료되면 `guestbook.entry.author_session_id` 가 가리키는 대상이 사라진다 → 정리 작업이 같은 시점에 NULL 로 익명화한다(database-schema.md §8). 이런 참조마다 "누가 정리하는가"를 문서에 표로 둔다(§6).

### uuid v7 를 앱에서 만드는 이유
DB 함수 지원 여부가 Postgres 버전에 달려 있어 버전 선택과 묶이지 않도록 앱에서 생성한다. 앱 생성은 outbox 이벤트 id 와 글 id 를 **트랜잭션 전에** 알 수 있다는 부수 이점도 있다.

### 프로젝션 대조
`guestbook_read.entry_view.reactions` 같은 사본은 정본(`reaction`)에서 재계산해 비교하는 점검을 주기 작업으로 둔다. 어긋남은 지표(`projection_drift`)로 노출한다.

## 대안과 기각 이유
- **bigserial 기본키**: 단순하고 빠르지만 개수·순서가 외부에 노출되고, 분산 생성과 이벤트 사전 식별에 불리하다.
- **스키마 하나에 모든 테이블**: 경계가 이름 규칙에만 의존해 무너지기 쉽다.
- **스키마 간 FK 허용**: 무결성은 쉽지만 모듈 분리를 포기하는 것이다.
- **Postgres enum**: 값 제거·변경이 번거롭다.
- **물리 삭제 위주**: 사후 숨김·감사 모델과 맞지 않는다.

## 결과
- 얻는 것: 경계가 DB 수준에서 보인다. 보관·프라이버시가 설계 단계에서 확정된다. 사본의 건강을 측정할 수 있다.
- 치르는 것: FK 가 주는 자동 무결성을 포기해 점검 코드가 늘어난다. 조인이 필요하면 모듈 공개 함수를 거쳐야 한다.

## 위험과 완화
| 위험 | 완화 |
|---|---|
| 참조 대상이 지워져 고아 id 가 남음 | 참조별 정리 책임 표(§6)와 점검 시험 |
| 편의상 다른 스키마를 직접 조인 | 임포트 경계 검사 + 쿼리 리뷰 항목화. **DB 역할 분리는 설계로 확정**(2026-11-05, design/10 §5.1 — 서비스별 로그인 역할, 소유자는 `pf_migrator`) |
| uuid v7 생성 시계 의존 | 서버 시계 동기화 전제. 순서 보장이 필요한 곳은 `seq` 를 쓴다 |

## 검증 방법
- 스키마 간 FK 가 없는지 마이그레이션 검사(스키마 메타데이터 조회)로 CI 에서 확인.
- 보관 정리 시험(AC-011), 프로젝션 대조 시험.

## 실서비스라면
서비스별 DB 역할(`pf_api_rw`·`pf_worker_rw`·`pf_gateway_ro` 등, design/10 §5.1)은 이 설계에서 이미 둔다. 실서비스에서는 여기에 모듈(스키마) 단위 역할을 더해 모듈 스키마 접근까지 권한으로 막고, 서비스가 갈라질 때 스키마를 그대로 별도 DB 로 옮긴다.

## 재검토 조건
조인 필요가 반복돼 모듈 공개 함수가 병목이 될 때. uuid v7 의 DB 기본 지원이 안정화돼 앱 생성의 이점이 사라질 때.
