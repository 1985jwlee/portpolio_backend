# 코드 해설 — S1-6 CI 골격(PR 검사 배선) + G9 결정 기록

## TL;DR — 이 변경을 한 문장으로
- PR·main push 마다 lint·typecheck·arch·unit·integration·audit·migration-immutable 7개 잡을 돌리는 GitHub Actions 워크플로(`ci.yml`)와 공용 설치 액션(`setup-bun`)을 새로 만들고, 시험 DB 를 서비스 컨테이너 `postgres:18` 로 확정해 문서 6개 13곳에 반영했다.
- 러너에서 실제로 돌려 본 적은 없다(L4 미실행). 잡 명령의 로컬 재현(L2)과 통합 시험의 로컬 postgres 실행(L3)까지만 확인했다.

## 전체 그림
- 이 저장소에는 `.github/` 가 없었다. 로컬에서만 돌던 검사 스크립트를 PR 마다 자동으로 걸어 주는 것이 S1-6 이다(`docs/design/11-implementation-plan.md` S1-6 행).
- 잡 7개는 `docs/design/09-ci-cd.md` §2 의 이름을 그대로 쓴다. 잡 id 가 브랜치 보호의 필수 상태 검사 이름이 되므로, 이름을 바꾸면 저장소 설정도 함께 고쳐야 한다.
- 의존 순서: `lint`·`typecheck`·`arch` 가 먼저 → `unit` → `integration`. `audit`·`migration-immutable` 은 독립이다.
- 사용자가 고른 것(전부 추천안): 잡 7개 + 공용 액션(Q1) · Bun 전역 설치 캐시(Q2) · 모든 대상 브랜치의 PR(Q3). 시험 DB 는 서비스 컨테이너(0단계 Q1).

## 코드 블록별 해설

### .github/workflows/ci.yml — 최상단(트리거·권한·동시성)
- **목적**: 모든 잡이 공유하는 보안·실행 조건을 한 곳에 둔다.
- **한 줄 해설**: `pull_request`(브랜치 필터 없음)와 `push: main` 에서 돈다. `permissions: contents: read` 가 파일 최상단 한 곳뿐이고, `concurrency` 는 PR 이면 이전 실행을 취소하고 main push 는 취소하지 않는다.
- **수정 포인트**: 대상 브랜치를 좁히려면 `on.pull_request` 에 `branches:` 를 추가한다(Q3 변경안). 어떤 잡이 쓰기 권한을 요구하게 되면 잡 단위로 올리지 말고 설계(09 §1)부터 다시 본다.

### .github/workflows/ci.yml — 보안 규칙 6개(파일 전체에 흩어져 있음)
- **목적**: 이 작업의 본체이고, 그래서 구현 등급이 `sonnet/high` 였다.
- **한 줄 해설**: 액션은 40자 SHA 로 고정(`# v7.0.1` 식 주석 병기) · `permissions` 최상단 한 곳 · `run:` 안에 `${{ }}` 없음(`BASE_REF` 를 `env:` 로 받음) · checkout 은 `persist-credentials: false` 7/7 · `secrets.*` 0개 · `pull_request_target` 없음.
- **수정 포인트**: 액션을 올릴 때는 태그가 아니라 SHA 를 `git ls-remote` 로 확인해 바꾼다. 리뷰가 이 6개를 grep 으로 다시 확인했고 전부 기대값이었다.
- **함정**: 머리말 주석에 `secrets.`·`pull_request_target` 같은 토큰을 쓰면 그 grep 검사가 주석에 걸려 자기 무효화된다. 구현 중에 한 번 걸려 주석을 고쳤다.

### .github/workflows/ci.yml — `integration` 잡
- **목적**: DB 가 필요한 통합 시험(`packages/db/test/integration/`)을 CI 에서 돌린다.
- **한 줄 해설**: `services.postgres`(`postgres:18`) + 헬스체크(5초 간격·5초 타임아웃·10회)를 두고 `TEST_DATABASE_URL` 하나만 `env` 로 준다. 시험이 이 URL 하나만 받으므로(`support.ts`) Testcontainers 를 쓰지 않는다. 비밀번호 `ci-throwaway` 는 잡과 함께 사라지는 값이라 비밀이 아니다.
- **수정 포인트**: DB 버전은 `image:`(부 버전 미고정, 로컬 실측은 18.6). 헬스체크 수치와 비밀번호는 구현이 임의로 고른 값이다(판단 보류 1). 통합 시험 실행 방식은 `bun run test:integration` 한 줄이고, 단위 시험은 `bunfig.toml` 이 통합 시험을 제외하므로 두 잡이 겹치지 않는다.
- **함정**: 4파일 31시험은 S1-4 의 L3 가드 30건을 포함한다(KB #38). 그래서 별도 설정 없이 이 잡이 그 가드를 자동으로 돌린다.

### .github/workflows/ci.yml — `migration-immutable` 잡
- **목적**: 이미 적용된 마이그레이션 파일이 PR 에서 바뀌지 않았는지 검사한다.
- **한 줄 해설**: `fetch-depth: 0` 으로 전체 이력을 받아 merge-base 를 구하고, 기준을 `origin/$BASE_REF`(PR 대상 브랜치)로 준다. PR 체크아웃은 분리 HEAD 라 로컬 브랜치 `main` 이 없어서, 스크립트 기본값 `main` 은 해석되지 않는다.
- **수정 포인트**: 이 잡은 `if: github.event_name == 'pull_request'` 라서 main push 에서는 건너뛴다. 필수 상태 검사로 걸어도 skip 은 통과로 처리된다고 알려져 있으나 러너에서 확인하지 않았다.

### .github/actions/setup-bun/action.yml — 공용 composite 액션
- **목적**: 7개 잡이 같은 설치 절차를 한 곳에서 공유한다.
- **한 줄 해설**: ① `.bun-version` 의 Bun 설치 ② `~/.bun/install/cache` 캐시(키: os·arch·`bun.lock` 해시, `restore-keys` 없음) ③ 캐시 적중 여부와 상관없이 `bun install --frozen-lockfile` 항상 실행.
- **수정 포인트**: `node_modules` 를 캐시하지 않는 이유는 isolated 링커의 `node_modules` 가 심볼릭 링크 트리라 복원본이 lock 과 어긋나도 설치를 건너뛰면 모르기 때문이다(Q2). 캐시 경로를 바꾸려면 ② 의 `path` 한 곳. Bun 버전은 `.bun-version` 이 정본이며 `package.json` 의 `packageManager` 와 같은 값을 유지해야 한다.
- **함정**: 7개 잡이 같은 키로 동시에 캐시 저장을 시도한다. 첫 실행에서 `Unable to reserve cache` 류 경고가 날 수 있으나 실패는 아닐 것으로 본다(미실측).

### docs/ 6개 파일 — 13곳 반영
- **목적**: 설계 문서가 구현과 어긋나지 않게 한다.
- **한 줄 해설**: 11(S1-6 행·완료 기준) · 09(통합 시험 DB 확정·`migration immutable` 배선됨·잡 7개 열거) · tech-stack(G9 결정) · 08(G9 행) · tech-debt(TD-4 H-1~H-6 처리 표 등 5곳) · deviation-log(DV-018). 위치는 `git diff` 로 본다.
- **수정 포인트**: TD-4 는 닫지 않고 `배선됨 — CI 첫 실행 확인 대기` 로 남겼다. 첫 PR 에서 확인된 뒤 닫는다. DV-018 은 "의도적 위반 PR 에서 빨강" 을 로컬 재현으로 갈음한 범위 조정이고 분류·발견자 칸(`범위 조정`·`G`)은 구현이 임의로 골랐다(판단 보류 2).

## 바뀐 과정에서 배울 것
- 리비전은 모든 단계에서 1개씩이라 재작성은 없었다. 다만 두 가지가 정정됐다.
- **통합 시험 수**: 계획은 "4파일 7시험·7 pass" 라고 썼으나 실측은 31이다. 7 은 DB 없이 돌릴 때의 실패 수를 시험 수로 오해한 것이다. 리뷰 m-1 이 파일별 `grep -cE '^\s*(test|it)\('` 로 9+5+8+9=31 을 교차 확인했고, 문서에는 31 로 기록됐다.
- **0단계 Q4 의 전제**: "S1-4 L3 가드 30건은 넣지 않고 통합 시험 4개만" 이라는 답은 '4개'(파일 4개)를 시험 4건으로 오해한 위에 서 있었다. 그 30건은 이 4파일 안에 있어 `integration` 잡이 이미 돌린다. 리뷰 m-2 가 올렸고 체크포인트 B 에서 사용자가 "포함으로 확정" 했다. 코드는 바뀌지 않았다.

## "이제 혼자 수정하려면"
- **잡을 더하거나 이름을 바꿀 때**: `.github/workflows/ci.yml` 의 `jobs:` 아래 잡 id. 바꾸면 main 브랜치 보호의 필수 상태 검사 이름도 같이 고친다. 09 §2 의 잡표와 11 의 S1-6 행도 맞춘다.
- **Bun 버전을 올릴 때**: 저장소 루트 `.bun-version` 과 `package.json` 의 `packageManager` 를 함께. 워크플로는 건드리지 않는다.
- **액션 버전을 올릴 때**: `ci.yml`·`action.yml` 의 `uses:` SHA 와 뒤 주석 버전. 입력 이름이 바뀌었는지 해당 태그의 `action.yml` 로 대조한다.
- **DB 버전·헬스체크·비밀번호**: `ci.yml` `integration` 잡의 `env`·`services`.
- **검사 대상 브랜치**: `ci.yml` 최상단 `on.pull_request`.
- **타임아웃**: 모든 잡의 `timeout-minutes: 15`. 성능 게이트가 아니라 매달림 검출용이다.
- **새 보안 규칙 위반을 막고 싶을 때**: 보안 6규칙은 저장소에 시험으로 남아 있지 않다(일회성 grep). 자동화하려면 별도 작업이다.
- **첫 PR 에서 사람이 확인할 것**: 7잡 초록 · `arch` 로그에 `Your node version` 경고 없음 · 캐시 키에 os·arch·해시 · `integration` 통과 · `migration-immutable` 변경 0. 이후 main 브랜치 보호에 필수 검사 7개 등록, `.claude/verification.json` 에 `audit`·`migration:immutable` 항목을 더할지 결정(런 중에는 `.claude/**` 를 고치지 않아 미뤘다).

## 남은 질문 (사용자가 이어서 물어보면 좋은 것)
- 첫 PR 이 빨강이면 어느 잡부터 의심해야 하는가(캐시 경로·서비스 컨테이너 네트워킹이 가장 약한 고리).
- 공개 저장소 비밀 스캔(S1-15)이 `TEST_DATABASE_URL` 의 리터럴 비밀번호를 오탐하면 어떻게 처리하는가.
- "의도적 위반 PR 에서 빨강" 을 로컬 재현 대신 실제 PR 로 실증하는 시점은 언제가 적절한가(DV-018 이 미실증으로 남아 있다).
