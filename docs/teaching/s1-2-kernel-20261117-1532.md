# 코드 해설 — S1-2 `packages/kernel` (Result · AppError 계층 · 도메인 기반 · 공통 포트)

> 기준: 작업 트리(미커밋), 브랜치 `feat/s1-2-kernel`. 줄번호는 이 시점의 `packages/kernel/src/` 기준이다.
> 코드 블록 해설은 7개다(상한 7). 판단이 들어간 자리만 골랐고, 나머지는 `그 밖의 변경` 한 줄로 넘긴다.

## TL;DR — 이 변경을 한 문장으로

- 저장소의 첫 제품 패키지 `@pf/kernel` 을 만들었다. 모든 모듈이 공유할 **성공/실패 값(`Result`)**, **오류 분류(`AppError` 21개 클래스 + HTTP 상태 표)**, **도메인 기반 클래스(`ValueObject`·`Entity`·`AggregateRoot`)**, **공통 포트(`Clock`·`IdGenerator`·`UseCase` 계열)** 를 한 진입점(`index.ts`)으로 내보낸다.
- 첫 구현이 리뷰에서 둘을 지적받아(오류 표가 쓰기 가능한 타입 / `message` 가 열거되는 불일치) 고쳤고, 영향분석이 찾은 문서 오류 3줄도 같은 런에서 고쳤다. 최종: 시험 44개 통과, `check`·`arch` 위반 0.

## 전체 그림

kernel 은 **의존이 0인 바닥층**이다. 이 패키지의 소스는 다른 어떤 패키지도 임포트하지 못한다(경계 규칙 `B7-kernel`, S1-5 가 만든 `bun run arch` 가 검사). 그래서 시간·난수·환경변수·DB 를 직접 만지지 않고, 그런 것이 필요한 자리는 **인터페이스(포트)만** 선언한다 — `Clock.now()`·`IdGenerator.next()` 가 그것이다. 구현체(시스템 시계, uuid v7 생성기)는 이 패키지 밖의 몫이고 아직 담당 작업이 문서에 없다(계획 R13).

왜 필요한가: 앞으로 만들 모듈(방명록 등)이 전부 "usecase 는 예외를 던지지 않고 `Result` 로 돌려준다 / 실패는 `AppError` 하위 클래스로 분류한다 / 상태 변화는 `AggregateRoot` 가 이벤트로 모은다"는 같은 약속 위에 서야 한다. 이 약속이 설계 문서 세 곳에 서로 다른 값으로 적혀 있었고(DV-010), 코드가 처음으로 **하나의 정본**을 정한 것이다.

사용자가 체크포인트에서 고른 설계 4건(전부 추천안): 진입점 `"."` 하나 · 평면 유니온 `Result` · `Instant = Date` · 전부 AI 작성(`Authorship: G`).

## 코드 블록별 해설

### [packages/kernel/src/result.ts:4-50] — `Result` 평면 유니온과 이름공간 함수

- **목적**: 성공(`Ok`)과 실패(`Err`)를 예외 없이 값으로 운반하고, 이어 붙이는 함수(`map`·`mapErr`·`andThen`·`unwrapOrThrow`)를 제공한다.
- **핵심 개념**: *판별 유니온* — `ok: true | false` 라는 꼬리표 하나로 타입이 갈린다. `if (r.ok)` 안에서는 `r.value`, 밖에서는 `r.error` 가 타입 검사를 통과한다.
- **코드**:
  ```ts
  export type Result<T, E> = Ok<T> | Err<E>;          // result.ts:6
  export const Result = { ok, err, map, mapErr, andThen, unwrapOrThrow };  // :50
  ```
- **한 줄 해설**: 타입 `Result` 와 값 `Result` 가 같은 이름이다. TypeScript 는 타입과 값을 다른 공간에 두므로 공존하고, 호출부가 `Result.ok(1)` 으로 쓰면서 `Result<number, E>` 로 타입도 적는다. `map` 은 `Err` 를 새로 만들지 않고 받은 것을 그대로 돌려준다(`:18`) — `Err<E>` 는 성공 타입 `T` 를 갖지 않아서 `Result<U, E>` 에도 맞기 때문이다.
- **의도한 동작**: 문서(16 §3.1)는 `Ok`/`Err` 를 **메서드를 가진 클래스**로 그렸다. 그 형태에서는 usecase 에서 가장 흔한 `if (!r.ok) return r;` 가 반환 타입이 다른 `Result` 로 흐르지 못해 `TS2322` 가 난다(계획 단계 실측). 그래서 메서드 없는 평면 값으로 바꿨고 문서를 고쳐 DV-009 에 남겼다.
- **수정 포인트**: 함수를 추가하려면 함수를 만들고 `:50` 객체에 이름을 넣는다. `index.ts` 는 `Result` 하나만 내보내므로 거기는 안 건드려도 된다. 비동기(`Promise<Result>`) 합성은 이 파일의 책임이 아니다(파일 머리 주석).
- **엣지케이스/주의**: `unwrapOrThrow`(`:39-47`)는 시험·조립 루트 전용이다. `Error` 인 오류는 그 객체를 그대로 던지고, 아니면 `cause` 에 담은 새 `Error` 를 던진다. "조기 반환이 되는가"는 런타임 시험이 아니라 **tsc 가 판정**한다(`result.test.ts:5` 주석) — `bun test` 만 돌리면 그 가드는 안 돈다.

### [packages/kernel/src/errors.ts:34-85] — `APP_ERROR_TABLE` (오류 → 상태·코드·재시도 표)

- **목적**: "이 오류는 HTTP 몇 번, 기본 code 는 무엇, 시스템이 자동 재시도해도 되는가"를 **한 곳**에 둔다.
- **핵심 개념**: *전수 매핑 레코드* — 키 타입이 `AppErrorKind`(18개 문자열 리터럴 유니온) 전부라서 행을 하나라도 빼면 tsc 가 실패한다. 새 오류 종류를 추가하면 표를 안 채울 수가 없다.
- **코드**:
  ```ts
  export const APP_ERROR_TABLE: { readonly [K in AppErrorKind]: ErrorRow } = { ... };  // :34
  ```
- **한 줄 해설**: 처음엔 `= { ... } satisfies Record<...>` 였다. `satisfies` 는 값을 검사만 하고 타입은 추론된 그대로 둬서 각 필드가 **쓰기 가능**했다. 지금은 `readonly` 타입을 직접 주석으로 붙였다. (아래 `바뀐 과정에서 배울 것` 참조)
- **의도한 동작**: `AppError` 생성자가 이 표를 읽어 `httpStatus`·기본 `code`·`retryable` 을 채운다(다음 블록). 표의 18행 값은 `00 §4.3` 의 클래스 행을 정본으로 하고, 빈 칸은 부모 클래스 값으로 채웠다(예: `DuplicateRequestError` → 409). `retryable` 의 뜻은 "워커·재시도 정책이 같은 작업을 다시 시도해도 되는가"이며 클라이언트에게 주는 `Retry-After` 안내와 다르다(`:31-32` 주석).
- **수정 포인트**: 상태·코드를 바꾸려면 이 표의 해당 행과 `errors.test.ts` 의 기대표(`ROWS`)를 **같이** 고친다 — 시험이 표와 기대표를 대조한다. 새 오류를 추가하려면 `AppErrorKind` 유니온 → 표 행 → 클래스 → `index.ts` 열거 → 시험 기대표 순서다.
- **엣지케이스/주의**: 읽기 전용은 **타입 수준일 뿐** 실행 시에는 객체가 얼려 있지 않다(`Object.freeze` 없음). 이 가드는 `errors.test.ts:234-240` 의 `@ts-expect-error` 로 걸려 있고 `bun run check`(tsc) 에서만 판정된다. 또 `kind` 를 추가하면 표가 공개 표면이라 버전 상승 사안이 된다(영향분석 H-3).

### [packages/kernel/src/errors.ts:94-127] — `AppError` 생성자와 `kind` 디스패치

- **목적**: 하위 클래스가 `kind` 한 줄만 선언하면 `name`·`code`·`httpStatus`·`retryable` 이 자동으로 채워지게 한다.
- **핵심 개념**: *생성자 안에서 하위 클래스 값 읽기의 함정* — 부모 생성자가 도는 동안 자식 클래스의 **인스턴스 필드는 아직 초기화 전**이다. 그래서 `kind` 를 인스턴스 필드가 아니라 **프로토타입 접근자(getter)** 로 둔다(`:97`, 하위 클래스마다 `override get kind()`).
- **코드**:
  ```ts
  const kind = new.target.prototype.kind;     // :105
  const row = APP_ERROR_TABLE[kind];
  const code = options?.code ?? row.code;
  super(options?.message ?? code, "cause" in options ? { cause: options.cause } : undefined);
  ```
- **한 줄 해설**:
  - `new.target` 은 `new` 로 실제 만든 클래스(예: `NotFoundError`)다. `this.kind` 는 추상 접근자라 생성자에서 TS2715 로 막히므로, 그 클래스의 `prototype` 에서 읽는다. 접근자가 상수 문자열만 돌려주니 안전하다.
  - `super()` **앞**에서 `kind`·`code` 를 구하는 이유: 기본 메시지를 `Error` 생성자에 넘기기 위해서다. 처음 구현은 `super()` 뒤에 `this.message = code` 로 **대입**했고, 대입된 속성은 열거 가능이라 메시지를 직접 준 경우(비열거)와 안 준 경우(열거)가 갈렸다.
  - `"cause" in options` 로 키가 있을 때만 `cause` 를 넘긴다. 안 준 오류에 `cause` 속성이 생기면 안 되고, `exactOptionalPropertyTypes` 가 켜져 있어 `{ cause: undefined }` 와 "키 없음"이 구분되기 때문이다.
- **의도한 동작**: `new NotFoundError()` → `name = "NotFoundError"`, `code = "not_found"`, `message = "not_found"`, `httpStatus = 404`, `retryable = false`.
- **수정 포인트**: 이 생성자의 줄 순서는 의미가 있다. `super` 앞에서는 `this` 를 못 쓰고, `super` 뒤에서 `this.code` 등을 채운다. 새 필드를 더하려면 `:98-101` 선언 → `:116-120` 대입 → `errors.test.ts` 속성 시험 순서다.
- **엣지케이스/주의**: 부수 효과 하나가 알려져 있다 — 메시지가 비열거가 되었으므로 `JSON.stringify(오류)` 에 `message` 가 안 나온다. `name`·`code`·`httpStatus`·`retryable`·`details` 만 나오고 `kind`·`cause` 도 없다(프로토타입 접근자라서). 응답·로그에 오류를 실을 때는 필드를 **명시적으로 골라 직렬화**해야 한다(영향분석 H-4·H-5).

### [packages/kernel/src/errors.ts:123-127, 235-253] — `isRetryable` 훅과 `GithubUpstreamError`

- **목적**: 대부분의 오류는 `retryable` 이 표의 값 하나지만, GitHub 상류 오류는 **code 에 따라** 갈린다(`github_unavailable` 은 재시도, `github_rejected` 는 거절이라 재시도 무의미).
- **핵심 개념**: 읽기 전용(`readonly`) 필드는 하위 클래스가 나중에 못 바꾼다. 그래서 값을 정하는 **보호 메서드(훅)** `isRetryable(code)` 를 부모가 생성자에서 부르고, 필요한 하위 클래스만 덮어쓴다.
- **코드**: `this.retryable = this.isRetryable(this.code);`(`:119`) / `GithubUpstreamError` 의 `return code === "github_unavailable";`(`:251`).
- **한 줄 해설**: 훅이 부모 생성자 **안에서** 불리므로 인스턴스 필드를 읽으면 안 되고 **인자 `code` 만** 봐야 한다 — 리뷰 m-2 가 이 계약을 주석으로 못박게 했다(`:123`). `GithubUpstreamError` 의 생성자는 `code` 를 `"github_unavailable" | "github_rejected"` 로 **필수·제한**해(`:236-243`) 이 두 값 밖은 컴파일에서 막는다.
- **수정 포인트**: 다른 오류도 code 별로 갈려야 하면 같은 방식으로 `isRetryable` 을 덮어쓴다. 훅에서 `this.어떤필드` 를 읽는 순간 `undefined` 를 읽는다.
- **엣지케이스/주의**: `GithubUpstreamError` 의 표 행(502, `github_unavailable`, `retryable: true`)은 기본값이고 `github_rejected` 일 때도 `httpStatus` 는 502 다. `github_rejected` 에 맞는 상태가 따로 필요한지는 코드만으로 단정할 수 없고 16 §6.5 순서도와 00 표의 충돌이 미판정이다(계획 `점검하지 못한 것` 3, CM-03 몫).

### [packages/kernel/src/domain.ts:24-73] — `ValueObject` · `Entity` · `AggregateRoot`

- **목적**: 도메인 객체의 공통 뼈대. 값 객체는 값으로 같고, 엔터티는 `id` 로 구분되며, 애그리거트 루트는 일어난 일(도메인 이벤트)을 모았다가 한꺼번에 내준다.
- **핵심 개념**: *`#` 비공개 필드* — `#version`·`#pending` 은 클래스 밖은 물론 하위 클래스도 직접 못 건드린다. 하위 클래스는 `record(event)` 로만 이벤트를 쌓는다.
- **코드**: `equals`(`:31-37`): `other.constructor === this.constructor && Object.is(this.value, other.value)` / `pullEvents`(`:67-72`): 현재 배열을 내주고 `this.#pending = []`.
- **한 줄 해설**: `equals` 가 `constructor` 까지 비교해서 같은 값이라도 클래스가 다르면 다르다. `pullEvents` 는 배열을 비우지 않고 **새 배열로 교체**해, 받은 쪽이 쥔 배열이 이후 기록과 얽히지 않는다.
- **의도한 동작**: `record` → `pullEvents()` → 기록 순서대로 반환 → 다시 부르면 빈 배열. `version` 은 생성자에서 받은 값을 읽기만 한다 — **버전을 언제 올리는지는 이 파일이 정하지 않는다**(파일 머리 주석).
- **수정 포인트**: 이벤트 검증이나 버전 증가 규칙을 넣고 싶으면 `record` 안(`:62`)이 자리지만, 그 규칙의 정본은 설계(외부 시각 I-12 가 "말해지지 않은 규칙"으로 짚음)에서 먼저 정해야 한다.
- **엣지케이스/주의**: **리뷰 잔여 m-3 이 코드에 그대로 있다.** `Object.is` 는 참조 비교라 `ValueObject<Instant>`(= `Date`)는 같은 시각의 두 `Date` 를 **다르다고** 판정한다. 값이 `Date` 인 값 객체는 `equals` 를 덮어써야 하는데 주석에는 그 말이 없다(`:20-23`). 사용자가 닫지 않기로 했고(Q8·Q12) 처음 시각 값 객체를 만드는 S2 모듈이 걸린다(H-7). 또 `Object.is(0, -0)` 은 거짓이다.

### [packages/kernel/src/ports/use-case.ts:6-18] 외 `clock.ts`·`id-generator.ts` — 공통 포트

- **목적**: usecase 가 지켜야 할 모양(`execute(ctx, input): Promise<Result<Out, AppError>>`)과 시간·식별자의 출처를 **인터페이스로만** 고정한다.
- **핵심 개념**: *포트* — "나는 이런 기능이 필요하다"는 선언만 두고 구현은 밖에서 주입한다. 시험에서는 고정 `Clock`·`IdGenerator` 를 넣어 결과를 결정적으로 만든다(`domain.test.ts:102`).
- **한 줄 해설**: `Ctx = unknown` 기본값은 아직 `ActorContext` 가 없어서 열어 둔 자리다(`:4-5` 주석). `EventHandler<E>` 는 `DomainEvent` 로 묶지 않았다 — 소비자가 받는 것은 이벤트 자체가 아니라 봉투라서다(`:15`).
- **수정 포인트**: 보조 포트 4종(S1-8)·`FieldCipher`(S1-12)·`AuditWriter`(S1-14)·`UnitOfWork`(S1-4)는 일부러 **여기 없다**. 해당 작업에서 `ports/` 에 파일을 추가하고 `index.ts` 에 한 줄 더한다.
- **엣지케이스/주의**: `CommandHandler`·`QueryHandler` 는 `UseCase` 를 그대로 확장한 **빈 인터페이스**라, TypeScript 의 구조적 타입 규칙상 컴파일러는 둘을 구분하지 못한다. 구분은 이름과 B3(`check-cqrs`) 경계 검사가 맡는 설계인데, B3 가 이 인터페이스를 실제로 어떻게 잡는지는 이 코드만으로는 단정할 수 없다.

### [packages/kernel/package.json:6-8, src/index.ts:1-39] — 공개 표면

- **목적**: kernel 이 내보내는 이름의 **유일한 목록**을 한 파일에 둔다.
- **한 줄 해설**: `exports: { ".": "./src/index.ts" }` 하나뿐이라 소비자는 `import ... from "@pf/kernel"` 만 쓴다(하위 경로 임포트 불가). `index.ts` 는 `export *` 를 쓰지 않고 이름을 하나씩 나열해 39개를 센다 — 의도치 않게 새는 이름이 없다. 타입은 `export type`, 값은 `export` 로 가른다(`verbatimModuleSyntax`).
- **의도한 동작**: 시험이 자기 자신을 `@pf/kernel` 로 불러 이 해석이 tsc·`bun test`·`arch` 셋 모두에서 동작함을 보였다(자기 참조 실측). 다른 패키지가 쓸 때는 `dependencies` 에 `"@pf/kernel": "workspace:*"` 를 **선언해야** 해석된다(영향분석 실측, 이 규약은 아직 문서에 없다 — H-2).
- **수정 포인트**: 새 이름을 공개하려면 소스 파일에 `export` 후 `index.ts` 에 한 줄 더한다. **이름을 추가하는 것도 공개 표면 변경**이라 버전 정책(ADR-052)의 대상이다. 시험(`errors.test.ts:242-`)이 `kernel` 의 내보낸 클래스 전부를 훑으므로 오류 클래스를 빠뜨리면 거기서 걸린다.

### 그 밖의 변경 (해설 생략)

- 설정: 루트 `tsconfig.json` 의 `references` 에 `./packages/kernel` 추가, `bun.lock` 에 워크스페이스 항목, `packages/kernel/tsconfig.json`(`composite`·`types: ["bun"]` — 시험이 `bun:test` 를 임포트하는데 `types` 를 안 주면 `TS2307`).
- 문서: 편차 로그 DV-009~012, `tech-debt.md` TD-5(담당을 S1-3 으로)·TD-6(자기 참조 실측 기록), 설계 문서 `16 §3.1`·`00 §4.1·§4.3`·`01 §4`, 그리고 `11-guestbook-write.md:634·807·808`(아래).

## 바뀐 과정에서 배울 것

리비전이 구현 3개(최초·r2·r3), 리뷰 3개다. 계획과 영향분석은 한 번에 통과했다.

**1. `satisfies` → 타입 주석 (리뷰 M-1, r2).**
- 처음: 계획 작업 목록에 "값의 좁힘은 `satisfies` 로"라는 줄이 있었고 구현이 그것을 따랐다. 같은 계획의 시그니처는 `readonly` 타입이었다 — 계획 안에서 두 문장이 어긋났다.
- 지적: 리뷰가 `APP_ERROR_TABLE.NotFoundError.httpStatus = 200` 이 tsc 를 통과하고 이후 오류가 200 으로 나가는 것을 실측했다. 공개 표면이 버전 경계(ADR-052)라 소비자가 생기기 전에 닫는 편이 싸다고 🔴 로 판정했다.
- 교정: `readonly` 타입 주석으로 바꾸고 `@ts-expect-error` 시험을 더했다. 수정 전에는 `TS2578`("쓰이지 않은 expect-error")로 실패하는 것을 확인했다.
- 교훈: **`satisfies` 는 "검사만 하고 타입은 넓게 둔다".** 공개 상수가 불변이어야 하면 `satisfies` 가 아니라 `readonly` 타입 주석을 쓴다. 그리고 계획에서 같은 항목의 알고리즘 줄과 시그니처 줄이 다르면 구현자가 아니라 계획이 먼저 고쳐져야 한다(계획 문서는 이번에 안 고쳤다 — 보고만).

**2. 생성자 순서 (리뷰 m-1, r2).**
- 처음: `super()` 뒤에서 `this.message = code` 대입.
- 지적: 대입한 속성은 열거 가능이고 `Error` 가 만드는 `message` 는 비열거라서, 같은 클래스인데 옵션 유무에 따라 `JSON.stringify` 결과가 달랐다(실측).
- 교정: `new.target.prototype.kind` 로 `super` **앞**에서 `code` 를 구해 메시지로 넘긴다. 열거 시험을 추가해 수정 전 실패(`Received: true`)를 확인했다.
- 2차 효과: 메시지 없는 오류의 JSON 에서 `message` 키가 사라졌다. 구현자가 이를 질문으로 올렸고 사용자는 "그대로 둔다"(Q9)를 골랐다. 표준 동작이 비열거라서다.
- 교훈: **"어떤 경로에서나 같은 모양" 불변식은 값이 들어오는 입구를 하나로 모을 때 지켜진다.** 같은 속성을 대입으로도 생성자로도 만들면 한쪽이 어긋난다. 그리고 국소 수정의 2차 효과(직렬화 표면)는 수정한 자리 밖에서 나오므로 구현자가 "이 수정으로 바깥에 달라지는 것"을 따로 적게 돼 있다.

**3. 문서 오류 3줄 (영향분석 H-1, r3).**
- 영향분석이 `11-guestbook-write.md:807`·`:808` 이 kernel 정본과 다른 클래스(`DuplicateRequestError` 계열, `ConflictError`)를 적고 있다고 지적했다. 계획의 문서 대조는 **바뀐 이름만** 셌고, "정본을 선언하면서 어긋나는 기존 문서"는 훑지 않았다.
- 사용자가 "이번 런에서 고친다"를 골랐고, `-high` 구현자가 두 줄에 더해 같은 상황·같은 틀린 클래스의 `:634` 다이어그램 라벨도 고쳤다. 리뷰 r3 가 문서의 `code` 언급 32줄을 전수 대조해 남은 불일치가 없음을 확인했다.
- 교훈: **정본을 새로 정하는 변경은 "이름이 바뀌는 곳"뿐 아니라 "그 정본을 이미 서술한 곳"도 훑어야 한다.**

## 더 학습하면 좋은 개념

- **판별 유니온(discriminated union)**: 꼬리표 필드(`ok`)로 타입을 좁히는 TypeScript 기법.
- **`satisfies` 대 타입 주석**: 검사만 하는가, 타입을 정하는가의 차이.
- **`new.target`**: 생성자가 어떤 클래스로 호출됐는지 알려 주는 식. 부모 생성자에서 하위 정보를 읽을 때 쓴다.
- **포트와 어댑터(헥사고날)**: 바깥 의존(시간·DB)을 인터페이스 뒤로 숨기는 구조.
- **구조적 타입 시스템**: 이름이 달라도 모양이 같으면 서로 대입된다는 TypeScript 규칙.
