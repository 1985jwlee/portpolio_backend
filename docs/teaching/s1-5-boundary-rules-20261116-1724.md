# 코드 해설 — S1-5 경계 검사 (`bun run arch`)

> 기준: 커밋 전 작업 트리(HEAD `bacf2e2` 위). 상한 초과 사유: 문서가 25,000자를 넘는다 — 사용자 지시로 `## 기술부채` 절을 항목마다 6칸(무엇·왜 지금 안 했나·언제·누가·닫는 방법·완료 판정)으로 자세히 썼기 때문이다. 코드 블록 해설은 7개, 절은 9개로 상한 안이다.

## TL;DR — 이 변경을 한 문장으로

- **`bun run arch` 한 명령이 모듈 경계 규칙(B1~B14)을 검사하고, 위반이거나 검사가 0건을 본 경우 종료 1 을 낸다.** 그래프 규칙은 dependency-cruiser(swc 파서, 규칙 21개), CQRS 는 `check-cqrs.ts`, 호출·문자열 규칙은 `check-purity.ts` 가 맡고 `arch.ts` 가 합친다.
- 상태: `bun test` 106 pass(arch 12 · check-cqrs 20 · check-purity 71 · 기존 AC-032 3), `bun run check` 종료 0, `bun run arch` 위반 0(열거 7 · purity 대상 0). 제품 소스가 아직 없어 실저장소에서는 거의 빈 검사다.
- **가장 큰 사실: `check-purity.ts` 의 정규식 방식은 5단계가 계획 결정 9 자체의 오류로 판정했다.** 리뷰·재작성이 네 번 돌았고 우회가 매번 새로 나왔다. 사용자는 swc AST 전환(A)을 방향으로 확정했으나 이번 런에서는 구현하지 않고 기술부채로 넘겼다(아래 `## 기술부채` TD-1).
- 그 밖에 문서 어긋남 4건(D-1~D-4), 리뷰 잔여 3건(m-1~m-3), S1-6 인계 4건, 이전 런의 `.env` 자동 로드가 미반영으로 남았다.

## 전체 그림

**이 코드는 "아키텍처 규칙을 사람이 기억하지 않아도 기계가 지키게 하는" 자리다.** 모듈러 모놀리스(ADR-001)는 모듈 사이 경계가 무너지면 의미가 없다. 규칙이 문서(01 §5)에만 있으면 어긋나도 아무도 모른다. 그래서 규칙을 실행 가능한 검사로 옮겼다.

```
bun run arch → scripts/arch.ts (파일을 읽는 유일한 곳)
  ├─ dependency-cruiser API 1회 (.dependency-cruiser.cjs, parser: swc)  → 그래프 규칙 21개
  ├─ 독립 열거 (Bun.Glob) ⊆ cruise 결과?                                 → GUARD-empty·GUARD-uncruised
  ├─ 파일 간선을 패키지로 접어 순환 탐색 (Tarjan)                         → B5
  ├─ check-cqrs.ts   (순수 함수)                                         → B3
  └─ check-purity.ts (순수 함수, 파일 텍스트)                            → B9·B2 시간·난수·B11
→ 위반을 합쳐 정렬·출력, 하나라도 있으면 종료 1
```

왜 이런 모양인가. 이전 런에서 dependency-cruiser 18.7 이 TypeScript 7.0.2 에서 `.ts` 를 0건 검사하고 종료 0 으로 끝난다는 것이 드러났다(KB #3). 사용자는 "TS 7.0.2 하나로 끝낸다(두 번째 TS 없음)"를 골랐다. 1단계 실측으로 `@swc/core` 를 설치하면 swc 가 `.ts` 를 읽는다는 길이 나왔고 그것을 채택했다. 그래도 swc 가 빠지면 다시 조용히 0건이 되므로, cruise 결과를 믿지 않는 **두 번째 눈**(독립 열거)을 두어 0건 통과를 실패로 만든다.

사용자가 정한 범위(ANSWERS): `arch` 는 로컬에서 실패하면 되고 CI 배선은 S1-6, `check` 에는 편입하지 않는다(Q2 A). B3 는 선언 형식·usecase 방향까지만, 어댑터 스키마 대조는 S2-1(DV-005). B14 의 SQL 절은 S1-18.

## 코드 블록별 해설

### scripts/arch.ts — `runArch`·`findUncruised`·`enumerateSources`

- **목적**: 여러 검사를 한 번에 돌리고, 검사가 비었을 때 통과하지 않게 한다.
- **핵심 개념 — 비공허성 가드**: "아무것도 검사하지 않았는데 통과" 를 실패로 보는 장치. 도구가 고장 나도 종료 0 으로 끝나는 검사는 없는 것과 같다.
- **한 줄 해설**:
  - `arch.ts:229` 설정은 항상 저장소의 `.dependency-cruiser.cjs` 를 읽는다. 픽스처는 `baseDir: root`(`:237`) 만 바꾼다. 그래서 실저장소와 시험이 같은 규칙으로 돈다.
  - `arch.ts:239` 위반이 있어도 `result.exitCode` 는 0 이다. 판정은 `summary.violations` 에서 읽는다.
  - `arch.ts:46-66` 가드는 개수가 아니라 **집합 포함**(열거 ⊆ cruise 결과)이다. `totalCruised` 가 내장·npm 모듈까지 세기 때문이다.
  - `arch.ts:172` 열거는 JS·TS 8종 확장자에 `dot: true` 다. 문자열 규칙이 cruise 보다 좁으면 `.mts`·`.hidden/` 아래 파일이 문자열 규칙만 조용히 피한다(리뷰 r1 m-3).
- **의도한 동작**: 위반 목록은 `byViolationOrder` 로 정렬해 안정적으로 출력하고 `process.exitCode` 로 종료한다. 예외는 잡지 않는다(`:314`) — 고장이면 Bun 이 종료 1 로 끝낸다.
- **수정 포인트**: 검사 루트 `ROOTS`(`:36`) · 새 검사 합산 `:284-290` · 제외 패턴은 `.dependency-cruiser.cjs` 의 `options.exclude` 한 곳(`excludePatterns` `:149` 가 열거에도 같은 제외를 쓴다).
- **주의**: 루트 다섯 개가 모두 있어야 한다(없으면 cruise 가 ENOENT). 빈 자리는 `.gitkeep` 으로 유지된다.

### .dependency-cruiser.cjs — 그래프 규칙과 설정

- **목적**: "어느 폴더가 어느 폴더를 임포트하면 안 되는가" 를 정규식으로 적는다.
- **핵심 개념**: `from.path`·`to.path` 는 경로 정규식이고, 괄호 그룹 `$1` 을 to 쪽에서 되받아 "같은 모듈" 을 표현한다(`:33-34` `B1-domain`: 같은 모듈의 service·usecase·port·adapter 로 못 간다).
- **한 줄 해설**:
  - `:124-135` `B7-packages-up` 은 B4 가 `packages/db` 에 허용한 스키마 진입만 예외로 둔다. 두 규칙이 글자대로는 서로 모순이었다(DV-007 — 통과 트리 첫 실행에서 드러남).
  - `:217-223` `unresolvable`: 해석 안 되는 지정자는 경로 규칙을 조용히 피하므로 그 자체를 위반으로 본다.
  - `:226` `parser: "swc"` · `:229` 픽스처 제외 · `:232-235` `exports` 하위 경로 해석(없으면 `dependency-cruiser/config-utl/…` 임포트가 해석 실패로 찍힌다).
- **의도한 동작**: 규칙 name 이 위반 ID 가 되어, 빨강을 본 사람이 01 §5 표의 같은 ID 로 곧장 간다.
- **수정 포인트**: 규칙을 더하면 ① 위반 픽스처 ② `arch.test.ts` 의 `EXPECTED_VIOLATING` 줄 ③ 01 §5 표 한 줄이 함께 필요하다. 하나라도 빠지면 T4 가 빨강이 된다.
- **주의**: `:6-8` 주석("기본 파서가 0건")은 낡았다 — 기술부채 D-4. `parser: "swc"` 는 해법이 아니라 **고정**이다(`@swc/core` 가 있으면 어느 parser 값이든 결과가 같다는 것이 구현 r1 실측).

### scripts/check-purity.ts — 규칙 구조와 엔진

- **목적**: 임포트가 아니라 호출·문자열이라 dependency-cruiser 가 못 잡는 규칙(`process.env`·시간·난수·쓰기·raw SQL)을 본다.
- **핵심 개념**: 규칙 하나가 `patterns`(정규식 배열, 갈래 하나 = 정규식 하나)를 갖고, **파일 전체 텍스트**에 `matchAll` 로 돌린다(`:123`). 줄 단위가 아니다.
- **한 줄 해설**:
  - `:45` `\bprocess\s*\.\s*env\b` — `.` 앞뒤의 `\s*` 는 줄바꿈을 건넌다. Biome 가 `crypto⏎.randomUUID()` 처럼 `.` 앞에서 줄을 나누기 때문이다.
  - `:89-111` `lineStarts` + `lineOf`: 줄 시작 오프셋 배열을 한 번 만들고 이분 탐색한다. 처음에는 매치마다 앞부분을 잘라 줄을 셌고 매치 수 × 파일 크기로 느려졌다(r3 m-2).
  - `:120-130` 규칙마다 `Set` 으로 줄 번호를 모아 같은 줄의 같은 규칙은 한 건이다.
- **의도한 동작**: `scanPurity(path, text)` 는 순수 함수다. 보고하는 줄은 **매치가 시작한 줄**이다.
- **수정 포인트**: 새 표기는 해당 규칙의 `patterns` 에 정규식을 더한다(`g` 플래그 필수). 시험은 양성·음성을 한 줄씩. **단 이 파일은 TD-1 에서 교체될 예정이라 크게 늘리지 않는다.**
- **엣지케이스**: 주석·문자열 안의 표기도 위반으로 센다(`:13`, 보수적). `job.process?.()` 같은 멤버 접근도 오탐이다 — 앞의 `.` 을 빼면 `globalThis.process?.env` 를 놓치므로 오탐 쪽을 택했다(오탐은 눈에 보이고 미탐은 조용하다).

### scripts/check-purity.ts — 구조분해 갈래 (`:25-30`, `:47-55`)

- **목적**: `const { env } = process` 처럼 `process.env` 라는 글자 없이 환경을 읽는 우회를 잡는다.
- **핵심 개념**: 정규식은 재귀를 못 하므로 중괄호 짝을 두 겹까지 펼쳐 썼다(`BRACE_1`·`BRACE_2`·`INSIDE`). 전방 탐색 `(?=…)` 은 읽기만 하고 위치를 소비하지 않는다.
- **한 줄 해설**: 먼저 "닫는 `}` 뒤가 `= process|Bun` 인가" 를 전방 탐색으로 한 번 본 뒤, 통과한 중괄호 안에서만 키 위치의 `env` 를 찾는다. 순서가 반대면 같은 키가 많은 객체에서 후보마다 중괄호 끝까지 다시 훑어 이차로 늘어난다(`env:` 8천 개 70KB 가 2.1초였다).
- **수정 포인트**: 중첩을 더 허용하려면 `BRACE_2` 위에 한 겹을 더 쌓는다 — 되추적 비용이 늘고, 첫 시도(`(?:ENTRY,)*`)는 수십만 자에서 엔진 한도에 걸려 `(?:INSIDE,)?` 로 돌아왔다(r4 판단 보류 13).
- **주의**: 구조분해 하나가 약 350KB 를 넘으면 조용히 못 잡는다(`:49` 주석에만 있다 — TD-3 m-1). 이 블록이 "정규식이 구조를 흉내 낼 때의 비용" 의 전형이고 TD-1 의 근거다.

### scripts/check-cqrs.ts — `checkCqrs`

- **목적**: CQRS 를 지킨다 — `usecase/command` 는 읽기 포트를, `usecase/query` 는 쓰기 포트를 쓰지 않는다.
- **핵심 개념**: 포트의 종류(쓰기/읽기)는 파일명이 아니라 그 포트가 건드리는 스키마 표로 정하고, 선언을 `modules/<m>/port-kinds.json` 에 둔다(쓰기 스키마 `<m>`, 읽기 스키마 `<m>_read`). 예외는 `modules/cqrs-exceptions.json`.
- **한 줄 해설**: `checkCqrs`(`:265`)는 선언 검증(`parseModuleDeclaration`)을 먼저 하고 그다음 간선을 돈다. 선언이 깨진 모듈은 `"broken"` 표식으로 두어 같은 원인을 간선마다 반복해 내지 않는다(`:294-301`). 방향 판정은 `checkDirection`(`:240`) — 걸린 표를 **전부** 예외가 덮어야 통과한다.
- **수정 포인트**: 선언 형식을 바꾸면 픽스처 4종·`check-cqrs.test.ts`·01 §5 가 함께 바뀐다. **계획이 스스로 가장 약한 고리로 적었다** — 실제 모듈 없이 형식을 정했으므로 S2-1 에서 바뀔 수 있다.
- **엣지케이스**: `usecase/command|query` 바로 아래 파일이 같은 모듈의 포트를 **직접** 임포트하는 간선만 본다. 서비스·헬퍼를 거친 간접 경로는 못 본다(01 §5 B3 칸에 한계로 적혀 있다).

### scripts/arch.test.ts — T1~T8 과 픽스처

- **목적**: 검사가 "정말 위반을 잡는지" 를 증명한다. 검사가 조용히 비는 것이 이 작업의 핵심 위험이라, 시험이 그 위험을 직접 겨눈다.
- **한 줄 해설**:
  - T1(`:99`)은 위반 트리의 위반 집합이 `EXPECTED_VIOLATING`(`:43`)과 **정확히 같다**고 단언한다. 많이 떠도 적게 떠도 빨강이라, "잡은 것만 남고 놓친 것은 안 남는" 함정을 피한다. 한 파일이 규칙 둘을 띄우는 곳은 의도한 겹침이고 `:38-42` 주석에 적었다.
  - T2 통과 트리 무위반, T3 빈 트리는 `GUARD-empty` 하나. T4 는 낼 수 있는 규칙 ID 전부가 기대 표나 가드 시험에 나오는지 확인한다(픽스처 없는 규칙이 생기면 빨강).
  - T7 은 실저장소에서 가드 위반이 0 이고 `scripts/fixtures/` 가 열거되지 않음을 본다.
  - T8(`:214`)은 `typescript` 트랜스파일러가 꺼져 있고 `swc` 가 켜져 있음을 단언하는 **카나리**다. 계획은 이것을 "기본 파서가 0건" 재현 시험으로 설계했으나, 구현 r1 실측이 그 전제를 바꿨다(아래 `바뀐 과정`).
- **수정 포인트**: 기대 표의 값은 **최종 설정으로 실제로 돌려 확인한 값만** 적는다(KB #7). 픽스처 94개는 의도적 위반이라 `biome.json`(`!scripts/fixtures`)과 `scripts/tsconfig.json`(`exclude`)에서 제외했다.
- **주의**: 픽스처만 고쳐서는 실저장소 `arch` 를 빨강으로 만들 수 없다 — 설정이 `^scripts/fixtures/` 를 제외한다(TD-4 H-4).

### scripts/check-purity.test.ts — 71개 시험의 세 갈래

- **목적**: 정규식 규칙의 미탐·오탐 균형을 입력으로 고정한다.
- **한 줄 해설**:
  - **양성·음성 시험**(`:17-323`): 잡아야 하는 표기와 잡으면 안 되는 표기. `wrong()` 헬퍼(`:9-13`)는 기대와 다른 결과를 낸 입력만 모아, 빨강일 때 어느 입력이 틀렸는지가 실패 값에 그대로 나온다.
  - **Biome 출력 고정 33개**(`:325-713`): 포매터 Biome 2.6.8 이 **실제로 만든** 줄바꿈 모양을 문자열 상수로 박았다. 합성 3개(`:715-750`)는 "나뉜 적은 없지만 같은 갈래" 표기다.
  - **한계 고정**(`:119`·`:752-770`): 못 잡는 표기를 일부러 "못 잡는다" 로 단언한다. 누가 정규식을 고쳐 잡게 되면 시험이 빨강이 되어 문서(01 §5)를 함께 고치게 만든다.
  - **규모 3개**(`:802-826`): 실시계로 재는 상한 2,000ms. 이차 복잡도 회귀를 막는다. 실시계를 읽으므로 L2 가 아니라 L3 다.
- **의도한 동작**: 각 갈래를 하나씩 지워 빨강이 되는지로 증명했다(r3 36종 변이 전부 빨강, r4 19종 중 18종 빨강·1종 동치).
- **수정 포인트**: 새 표기는 해당 `describe` 에 양성 한 줄과 음성 한 줄. 한계를 풀면 `:119`·`:753`·`:762` 시험의 기대를 뒤집는다.
- **주의**: Biome 33개는 문자열 상수라 **Biome 를 올려도 계속 초록**이다 — 가드가 못 되는 자리(TD-3 m-3). 규모 3개는 CPU 한 개에 12개를 겹치면 여유가 약 1.3배로 줄어든다(TD-4 H-3).

그 밖의 변경(해설 생략): `package.json`(`arch` 스크립트, `dependency-cruiser` 18.7.2·`@swc/core` 1.16.22 정확 고정)·`bun.lock`·`biome.json`·`scripts/tsconfig.json`, 문서 13개(01 §5 규칙 수단 표 신설 · 08·09·11·tech-stack·architecture·00·features/10 · ADR-001·022 상태 줄 · 편차 로그 DV-003~007 · 추적표).

## 바뀐 과정에서 배울 것

**구현이 네 번, 리뷰가 네 번 돌았고 같은 파일(`check-purity.ts`)에서 우회가 매번 새로 나왔다.** 끝에 5단계가 "사이클이 아니라 결정이 틀렸다" 고 판정했다.

| 사이클 | 구현 | 리뷰가 지적한 것 |
|---|---|---|
| 최초 | 줄 단위 정규식, 규칙당 한 정규식 | M-1 `import { env } from "bun"`·`process?.env`·구조분해가 B9 를 우회 · M-2 01 §5 가 B11 에 적은 "쓰기 `execute`" 가 검출 안 됨 · m-1 시간·난수 다른 표기 · m-2 check-cqrs 시험 단언이 약해 변이 16종 중 2종 생존 |
| r2 | 갈래를 더했다 | M-3 Biome 가 긴 SQL 인자를 다음 줄로 내려 줄 단위 `execute` 갈래가 정상 코드에서 안 걸림 · M-4 `[^}]*` 가 중첩 구조분해를 놓침 · m-5 `Bun["env"]` · m-6 `Date()` |
| r3 | **엔진 교체** — 줄 단위 → 파일 전체 텍스트 + 갈래별 `patterns` | M-1 B2 갈래가 `.` 앞뒤 공백을 불허해 `crypto⏎.randomUUID()` 가 샌다 · m-2 이차 복잡도(63KB 2.2s · 406KB 11.5s) |
| r4 | 모든 `.` 앞뒤 `\s*`, 줄 번호 이분 탐색, 구조분해 전방 탐색. **Biome 줄바꿈 모양을 생성기로 53,930건 열거** | 통과 가능 — 잔여 m-1~m-3 |
| 5단계 | — | **계획 결정 9·원장 D10 이 반증됨(P1)** |

**r3 의 전환점**: r2 까지는 지적된 입력만 막았다. r3 는 코드를 고치기 전에 같은 부류 입력 130건을 만들어 r2 구현에 한꺼번에 돌렸고, 107건 중 21건이 어긋났다. 뿌리가 둘이었다 — 줄 단위 매칭, 그리고 갈래를 한 정규식에 OR 로 이은 구조. 그래서 입력을 막는 대신 엔진을 바꿨다.

**r4 의 전환점**: 리뷰가 "우회가 생기는 자리는 엔진이 아니라 **포매터의 줄바꿈 규칙**이 정한다" 는 가설을 냈다. r4 는 한 입력씩 추측하지 않고 생성기로 열거했다(r3 코드의 양성 미탐 2,641 / 47,087 → r4 0, 음성 오탐 0 / 6,843). 열거 안에서 **리뷰 r3 의 "B9 직접 접근은 바꾸지 않는다" 판단이 틀렸음**도 드러났다 — 줄이 가득 찬 기본 매개변수 자리에서는 `process⏎.env` 로 나뉜다. 리뷰도, 구현의 신고(r3 의 "`.` 앞뒤 공백이 필요 없다"·"최악 입력 약 300ms")도 정정됐다.

**5단계의 판정**: 문제는 사이클이 아니라 **설계 결정 9("`check-purity` 는 원문 텍스트 정규식")와 D10("Biome 로 표현할 수 없다 → 확정")** 이다.
- 같은 계획이 `@swc/core` 를 들이면서도 AST 대안을 평가하지 않았다(계획·조사 산출물에 AST 0건).
- Biome 평가는 내장 규칙 `noRestrictedGlobals` 하나였다. 5단계가 설치된 Biome 2.6.8 로 직접 재니, GritQL 플러그인이 `Date⏎.now()` 와 주석이 낀 `Date /* c */ .now()` 를 잡았다. `noProcessEnv` 는 `process⏎.env`·`globalThis.process.env`·`process["env"]` 를 잡았다.
- 리뷰가 낸 미예견 14건이 전부 이 한 자리(텍스트 매칭)에 몰렸다.
- 사용자는 체크포인트 B 에서 "m-2 를 정규식 3곳으로 닫을지" 만 받았고 메커니즘을 바꿀지는 한 번도 묻지 않았다.

**두 번째 이야기 — 전제가 구현에서 정정됐는데 하류가 따라가지 않았다.** 계획은 "기본 파서가 TS 7 에서 0건 → swc 가 해법" 이라 보고 T8 을 그 수치의 재현 시험으로 정했다. 구현 r1 이 파서 값을 바꿔 보니(`tsc`·`acorn`·생략) 결과가 전부 swc 와 같았다 — 0건은 `@swc/core` 가 없을 때만 나온다. T8 은 "가용성 단언" 으로 바뀌었는데, 그 수치를 'ADR-050 실측' 으로 적은 문서(D-1)와 설정 주석(D-4)은 고쳐지지 않았다.

**일반화된 교훈**
1. 메커니즘을 고를 때 **이미 설치된 도구**(여기서는 `@swc/core`)로 구조를 볼 수 있는지 먼저 본다. 정규식으로 구조를 흉내 내기 시작하면 갈래마다 새 틈이 난다.
2. 문서에 "확정" 을 적을 때는 **무엇을 확인했는지**를 같은 문장에 적는다("Biome 로 표현할 수 없다" 가 아니라 "`noRestrictedGlobals` 로는").
3. 같은 부류의 우회가 두 번 나오면 입력을 하나씩 막지 말고 **부류 전체를 생성기로 열거**한다(r3·r4).
4. 정확성이 외부 도구의 출력(Biome 2.6.8)에 기댄다면, 그 도구를 올릴 때 깨지는 가드를 같이 둔다. 문자열 상수로 박은 시험은 도구가 바뀌어도 초록이다.
5. 구현이 계획의 전제를 정정하면 그 전제를 인용한 **문서·주석까지** 같은 사이클에서 따라가게 한다.

## 기술부채

**아래 항목은 전부 이번 런에서 닫지 않았다.** 사용자가 체크포인트 C 에서 "6단계로 넘어가면서 기술부채 항목으로 자세하게 작성한다" 를 골랐고, 계획 재수정·코드 재조정은 하지 않았다(재호출 카운터 불변). 근거 없는 수치는 쓰지 않았고 측정하지 못한 것은 "미측정" 으로 표시했다(ADR-050).

### TD-1 (P1) — `check-purity` 를 swc AST 로 교체

**지금 정규식이 남기는 우회(현행 코드·시험이 고정한 것 + 리뷰 r4 m-2)**
- 포매터 밖 표기: `` sql<number>`…` ``, `.execute<Row>(`, `.execute?.(`, `crypto?.`, `performance?.`, 괄호 없는 `new globalThis.Date`.
- 토큰 사이 주석(`new Date(/* now */)`), 구조분해 안 문자열·주석의 짝 안 맞는 중괄호, 중괄호 네 겹 이상, 따옴표·계산식 키, 타입 주석(`check-purity.test.ts:119`·`:752-770` 이 고정).
- 엔진 한도: 구조분해 하나가 약 350KB 를 넘으면 조용한 미탐(`check-purity.ts:49`).
- 결합: 정확성이 Biome 2.6.8 출력에 묶여 있고 올릴 때 깨지는 가드가 없다.
- **AST 로도 안 사라지는 것**: 이름공간·기본 임포트의 `b.env`, 별칭 `const p = process`, `require("bun")`. 스코프·데이터 흐름 추적 없이는 구조만으로 못 잡는다. (A) 가 이것까지 닫는다고 쓰지 않는다.

**기존 시험 71개를 수용 기준으로 쓰는 법**
- **가. 미탐을 단언하던 시험은 빨강이 되는 것이 개선이다.** `:119`(주석·타입 주석·따옴표 키)·`:753`(토큰 사이 주석)·`:762`(짝 안 맞는 중괄호·네 겹)와 오탐을 단언하는 `:133-137`(`job.process?.()`)이 해당한다. 기대를 뒤집고 01 §5 의 한계 문장을 지운다.
- **나. 의미가 바뀌는 것 — 주석·문자열.** 지금 규칙은 주석·문자열 안도 위반으로 센다(`check-purity.ts:13`, 계획 가정 A-6). AST 는 주석·문자열 속 `process.env` 를 코드로 보지 않는다. 좋은 점은 설명 주석에 쓴 `process.env` 오탐이 사라지는 것이다. 위험은 "문자열 속 표기" 를 위반으로 기대하던 시험이 있는지인데, 작성자가 쓴 입력 중 큰따옴표·백틱 문자열 안에서 `//`·`/*` 를 포함한 것은 위 네 줄뿐임을 grep 으로 확인했다(작은따옴표 입력은 전수 확인 못 함). 쓰기 `execute` 의 문자열 **인자**는 AST 에서 StringLiteral 노드로 본다.
- **다. 진짜 회귀.** 가·나 어디에도 속하지 않는 빨강은 구현 결함이다.
- **줄 번호와 오프셋 단위**: swc 가 주는 위치를 줄 번호로 바꾸는 방법과, 한글 주석이 섞인 파일에서 오프셋이 UTF-16 인지 바이트인지는 이 단계에서 **확인하지 못했다** — 탐침 항목에 넣는다. 시험이 "매치가 시작한 줄" 로 보고하고 한 줄 같은 규칙은 한 건이다.

**규모 시험 3개와 Biome 출력 고정 시험 33개의 운명 (제안 — 결정은 사용자)**
- **규모 3개(`:802-826`)**: 이차 복잡도를 막는 시험이다. AST 구현에서는 그 이유가 약해진다. 삭제하거나 대형 입력 1개짜리 smoke 로 줄인다. 삭제하면 L3 시험이 L2 파일에서 빠져 D-3·H-3(시계 시험 CI 안정성)이 함께 사라진다.
- **Biome 33개(`:325-713`)**: AST 는 줄바꿈과 무관하게 같은 노드를 보므로 "포매터 결합을 지킨다" 는 목적은 사라진다. 비용이 0 이라 포매터 모양에서도 잡는 **회귀 입력**으로 남기고 묶음 이름을 "Biome 2.6.8 고정" 에서 바꾸는 쪽을 권한다. 이 33개가 AST 에서 통과하는지가 수용 기준의 일부다.
- 열거 생성기(m-3)는 AST 로 가면 반입할 이유가 없어진다.

## 더 학습하면 좋은 개념

- **정적 분석의 두 층**: 텍스트 매칭(정규식)과 구문 트리(AST). 구조를 물으면 AST, 이름만 물으면 텍스트로 충분하다.
- **비공허성(vacuity) 가드**: 검사가 대상을 하나도 안 봤을 때 실패시키는 장치.
- **정규식의 전방 탐색·되추적**: `(?=…)` 와 이차 복잡도가 생기는 조건.
- **변이 검증(mutation testing)**: 규칙을 하나씩 지워 시험이 빨강이 되는지로 시험의 감도를 증명하는 방법. r3·r4 가 손으로 했다.
- **회귀 시험의 방향**: "통과한다" 가 아니라 "고치기 전에는 실패한다" 로 검증한다.
