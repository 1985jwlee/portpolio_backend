# 코드 해설 — S1-1 저장소 골격 (Bun 워크스페이스 · tsconfig · Biome · .env.example · AC-032)

> 기준: 브랜치 `feat/s1-1-repo-skeleton` 의 미커밋 작업 트리(HEAD `5280c17`). 제품 실행 코드는 0줄이고, 설정 파일과 시험 1개가 전부다.

## TL;DR — 이 변경을 한 문장으로

- 저장소 루트에 **"검사가 실제로 무언가를 보는 빈 골격"** 을 세웠다: Bun 워크스페이스(`package.json`) + 타입 검사 3층(`tsconfig*.json`, TypeScript 7.0.2) + Biome 허용 목록(`biome.json`) + 비밀 파일 무시 규칙과 견본(`.gitignore`·`.env.example`) + 라이선스 고지 시험(`scripts/check-license.test.ts`).
- `bun run check`(lint + typecheck)와 `bun test` 가 종료 0 이다. 후속 작업(S1-2~)이 이 골격 위에 앱·패키지를 얹는다.
- 설계 문서 5개를 코드보다 먼저 고쳤다(편차 로그 DV-001·DV-002 포함).

## 전체 그림

이 저장소는 설계 문서·ADR·스파이크(`spikes/*`)만 있고 제품 구조가 없었다. S1-1 은 그 위에 후속 작업이 공유할 **계약 네 개**를 처음 깐다 — ① 어떤 디렉토리가 워크스페이스인가(`package.json`), ② 어떤 엄격도로 타입을 검사하는가(`tsconfig.base.json`), ③ 어떤 파일을 린트하는가(`biome.json`), ④ 무엇을 커밋하지 않는가(`.gitignore`). 이후 모든 앱·패키지가 이 넷을 상속하므로 지금 값이 곧 전원의 기본값이다.

핵심 난제는 **빈 골격은 검사가 0건이라 실패한다**는 것이다. 참조할 타입 단위가 0개면 `tsc -b` 가 TS18002 로, 빈 단위는 TS18003 으로 종료 1 이 되고, Biome 도 처리 파일 0건이면 오류다. 억제 옵션(`--no-errors-on-unmatched` 등)으로 0건 통과를 기본값으로 만들면 이후에 검사가 조용히 비어도 모른다. 그래서 **실제로 검사할 대상을 하나 만들었다** — 이미 커밋돼 있던 라이선스 파일을 확인하는 AC-032 시험(`scripts/check-license.test.ts`)이 그 대상이고, 동시에 첫 타입 검사 단위(`scripts/tsconfig.json`)가 된다.

## 코드 블록별 해설

### [package.json] — 워크스페이스·스크립트·고정 버전

- **목적**: Bun 워크스페이스 범위, 루트 검사 명령, 도구 버전을 한 파일에 고정한다.
- **핵심 개념**: *워크스페이스* — 한 저장소 안에 여러 패키지를 두고 `bun install` 한 번으로 묶어 설치하는 구조. `workspaces` 배열이 "어느 디렉토리의 하위 폴더를 패키지로 볼지"를 패턴으로 정한다.
- **코드**: `package.json:5-9`(워크스페이스), `:10-15`(스크립트), `:16-20`(개발 의존)
- **한 줄 해설**
  - `package.json:5-9` — `apps/*`·`modules/*`·`packages/*` 세 패턴. `package.json` 이 없는 하위 폴더는 문제 삼지 않아서 지금처럼 비어 있어도 `bun install` 이 통과한다(계획 실측 M8).
  - `package.json:14` — `check` 는 `lint && typecheck`. `&&` 라서 lint 가 실패하면 typecheck 는 돌지 않는다. 01 §6 의 "순서" 문구를 따랐고 후속 작업이 뒤에 ` && bun run <검사>` 를 이어 붙이도록 설계됐다.
  - `package.json:17-19` — `^` 없이 정확 고정. Biome 는 설정의 `$schema` 버전과 CLI 버전이 다르면 `biome check` 가 실패해서, 도구 세 개를 같은 원칙으로 못박았다.
  - `package.json:4` `"packageManager": "bun@1.4.4"` 와 `.bun-version`(`1.4.4`) 은 같은 값을 두 방식으로 적은 것이다.
- **의도한 동작**: `bun install` → `bun run check` → `bun test` 가 처음 클론한 상태에서 통과한다.
- **수정 포인트**
  - 앱·패키지를 추가할 때 → `workspaces` 패턴은 이미 덮고 있으니 건드릴 것은 아래 "범위 목록 셋"이다.
  - 검사를 추가할 때 → `check` 문자열 끝에 ` && bun run <새검사>`.
- **엣지케이스/주의**
  - 설치 후 `bun.lock`(87줄, `configVersion: 1`)이 생성돼 커밋 대상이다. 손으로 고치지 않는다.
  - 지금은 워크스페이스 패키지가 0개라 끌어올림 배치고, 첫 패키지가 생기면 격리 배치(`node_modules/.bun`)로 바뀐다(계획 M8).

### [tsconfig.json · scripts/tsconfig.json · tsconfig.base.json] — 타입 검사 3층

- **목적**: "엄격 옵션은 한 곳, 무엇을 검사하는가는 단위마다, 한꺼번에 돌리는 곳은 루트" 로 역할을 나눈다(설계 01 §4).
- **핵심 개념**
  - *솔루션형 루트*: 루트 `tsconfig.json` 은 자기 파일을 검사하지 않고(`files: []`) `references` 로 단위를 나열만 한다. `tsc -b` 가 그 목록을 따라간다.
  - *`composite`*: references 의 대상이 되려면 켜야 하는 옵션. 증분 정보 `*.tsbuildinfo` 를 쓴다.
- **코드**: `tsconfig.json:2-3` · `scripts/tsconfig.json:3-7`
- **한 줄 해설**
  - `tsconfig.json:3` `references: [{ "path": "./scripts" }]` — 참조 대상이 정확히 1개. 0개면 TS18002, 내용 없는 단위를 넣으면 TS18003 이라서 **빈 디렉토리(`apps/` 등)를 여기에 넣지 않았다**.
  - `scripts/tsconfig.json:5` `"types": ["bun"]` — **빼면 안 된다.** TypeScript 6 부터 `types` 기본값이 빈 목록이라, 빼면 `bun:test`·`Bun` 을 해석하지 못해 종료 1 이다(구현 단계 V4 ⓒ 로 실측). 이 값을 기반이 아니라 **단위**에 둔 이유는 기반에 두면 나중에 웹(DOM) 단위까지 bun 타입이 섞이기 때문이다.
  - `scripts/tsconfig.json:4` `composite: true` — 루트가 이 단위를 reference 로 거는 데 필요하다. `noEmit` 과 함께 써도 7.0.2 에서 동작한다.
  - `package.json:13` `tsc -b --noEmit` — `-b`(빌드 모드)로 references 를 따라가되 `--noEmit` 으로 산출물은 만들지 않는다.
- **의도한 동작**: 루트 → `./scripts` → 기반 옵션 + bun 타입으로 `scripts/**/*.ts` 검사. 성공하면 `scripts/tsconfig.tsbuildinfo` 가 생기고 `.gitignore` 가 가린다.
- **수정 포인트**
  - 새 타입 검사 단위(앱·패키지) → 그 폴더에 `tsconfig.json`(extends base + 필요한 `types`/`lib`) 추가 후 `tsconfig.json:3` 에 reference 한 줄.
  - 단위끼리 `references` 를 걸지 않는다 — 아래 엣지케이스.
- **엣지케이스/주의**
  - **단위 사이 `references` 는 `tsc -b --noEmit` 아래에서 TS6310 으로 크게 실패한다**(영향분석 I2, 단위가 emit 을 켜도 같다). 단위끼리는 워크스페이스 패키지명(`@pf/...`)으로 원본을 가져오는 형태(I1)가 동작하고, 교차 타입 오류도 잡는다. 후속 작업이 단위에 references 를 쓰려 하면 여기서 막힌다.
  - 터미널에서 `bun check` 는 Bun 내장 검사기가 아니라 이 저장소의 `check` 스크립트로 가로채진다(계획 M6). 문서에 "`bun check` 로 타입 검사"라고 쓰지 않는다.
  - TypeScript 7.0.2 에는 JS API 가 없다(계획 M5). 이 버전 선택의 결과는 아래 "바뀐 과정" 절과 `docs/domains/tech-stack.md:105` 에 있다.

### [tsconfig.base.json] — 기반 옵션 15개 (Q5 B)

- **목적**: 모든 단위가 상속하는 엄격도와 언어 수준.
- **코드**: `tsconfig.base.json:3-17`
- **한 줄 해설**
  - 앞 7개(`strict`·`noUncheckedIndexedAccess`·`exactOptionalPropertyTypes`·`noImplicitOverride`·`verbatimModuleSyntax`·`isolatedModules`·`noEmit`)와 `moduleResolution: bundler` 는 설계 01 §4 표의 값이다.
  - `target: ESNext`·`module: Preserve`(`:11-12`) 와 `lib`·`moduleDetection`·`allowImportingTsExtensions`·`skipLibCheck`·`noFallthroughCasesInSwitch`(`:13-17`) 는 **Bun 문서의 권장 tsconfig 에서 합쳐 온 것**이다(사용자 답 Q5 (B)). 01 §4 원안의 `target ES2023` 이면 `Object.groupBy` 같은 ES2024 API 가 TS2550 오류가 되기 때문이다(계획 M14).
  - `noUncheckedIndexedAccess`(`:4`) 때문에 `arr[0]` 은 `T | undefined` 다. 시험 코드가 `license.split("\n")[0]?.trim()` 으로 `?.` 를 쓴 이유다.
- **수정 포인트**: 옵션 하나가 모든 단위에 번진다. 값을 바꾸면 `docs/design/01-repository-structure.md` §4 표(159행 이하)와 같이 바꾸고 `docs/deviation-log.md` 에 행을 남긴다.
- **엣지케이스/주의**
  - `lib: ["ESNext"]` 에는 DOM 이 없다. S5 의 웹 단위는 `lib` 를 다시 적어 DOM 을 더해야 한다(01 §4 그림의 `lib: DOM·ESNext` 주석이 그 뜻).
  - `skipLibCheck` 는 선언 파일(`.d.ts`) 안의 오류를 보지 않는다. 대신 `@types/bun` 1.4.4 는 그것 없이도 통과했다(계획 M2).
  - `paths`(경로 별칭)는 기반에 두지 않는다(01 §4 "paths 사용하지 않는다").

### [biome.json] — 린트 대상 허용 목록

- **목적**: Biome 가 볼 파일을 **허용 목록**으로 정한다. 규칙·포맷은 기본값(탭·큰따옴표·세미콜론)이다.
- **코드**: `biome.json:2-12`
- **한 줄 해설**
  - `biome.json:2` `$schema` 를 `./node_modules/...` 로컬 경로로 둔다. URL 로 두면 URL 의 버전과 CLI 버전이 어긋날 때 실패하기 때문에(계획 실측) 그 결합을 끊었다. 이 경로는 `bun install` 후에만 존재한다.
  - `biome.json:4-11` `files.includes` — `docs/**`·`spikes/**`·`.claude/**`·`infra/**`·`bun.lock` 이 목록 밖이라 검사하지 않는다. 현재 `Checked 6 files`(루트 JSON 4 + `scripts/` 2).
  - `*.json`(`:10`) 은 루트의 JSON 파일을 센다. 그 덕에 시험 파일 하나만으로도 검사 대상이 0건이 되지 않는다.
- **수정 포인트**: 새 최상위 디렉토리를 린트하려면 `includes` 에 패턴을 더한다. `--no-errors-on-unmatched` 를 쓰지 않는다 — 대상이 0건이면 실패해야 "검사가 비었다"를 알아챈다.
- **엣지케이스/주의**: 새 JSON·TS 를 쓰고 `bun run lint` 가 포맷 위반으로 실패하면 `bun run format`(`package.json:12`) 한 번이면 된다. 첫 실행에서 6건이 그렇게 걸렸다(구현 V2).

### [.gitignore · .env.example] — 비밀 파일 무시와 견본

- **목적**: 실제 값이 든 `.env*` 는 커밋하지 않고, 키 이름만 있는 견본은 커밋한다. 공개 저장소의 보안 경계라서 이 변경의 구현 등급이 `sonnet/high` 였다.
- **코드**: `.gitignore:26-32` · `.env.example:1-16`
- **한 줄 해설**
  - `.gitignore:27-29` 순서가 중요하다. `.env.*` 는 `.env.example` 까지 덮는다. **예외 `!.env.example` 이 반드시 그 뒤에 와야** 견본이 추적된다. 순서를 바꾸면 견본이 조용히 무시된다. `git check-ignore -v` 로 `:29` 줄이 `.env.example` 에 걸리는 것(예외)을 확인했다.
  - `.gitignore:32` `*.tsbuildinfo` — `tsc -b` 가 남기는 증분 정보.
  - `.env.example:4-16` 은 `docs/design/02-dev-environment.md` §5 발췌 13줄과 한 글자도 다르지 않다(`diff` 동일). `CHANGE_ME`·빈 값은 자리 표시이고 실제 비밀번호가 아니다.
  - `.env.example:1-3` 은 이번에 더한 주석 3줄. 키의 정본은 01 §8 이고 나머지 키는 S1-3(설정 스키마)이 맞춘다고 적었다. 즉 이 견본은 **일부**다(요구 R6 부분 충족).
- **의도한 동작**: `cp .env.example .env` 로 시작해 `.env` 는 git 에 안 올라간다.
- **수정 포인트**: 키를 더하면 `.env.example` 과 설계 문서 02 §5·01 §8 을 함께 고친다. `secrets/` 무시는 S1-15 몫이라 이번에 넣지 않았다.
- **엣지케이스/주의 — 영향분석이 찾은 함정**: **Bun 은 cwd 의 `.env` 를 `bun test`(NODE_ENV=test)에서도 자동 로드한다**(I4). 견본이 안내하는 `cp .env.example .env` 뒤에는 모든 시험이 `DATABASE_URL_*` 를 받는다. 개발 기계(`.env` 있음)와 CI(없음)에서 시험 입력이 갈린다. 이번 변경에는 env 를 읽는 코드가 없어 결함이 아니고, 첫 소비자는 S1-3 의 "필수 누락 시 기동 실패 시험"이다. 닫는 방법은 `bun test --no-env-file` 이거나 최상위 `env = false`(`[test]` 아래의 `env = false` 는 꺼지지 않는다). **이 사실을 이번 변경 안의 문서에 남기지 않기로 사용자가 정했다** — 7단계 KB 로 넘어간다. 그래서 지금은 이 해설 외에 저장소에 기록이 없다.

### [scripts/check-license.test.ts] — AC-032 시험

- **목적**: "LICENSE 가 MIT 이고 README 가 개인 콘텐츠의 권리 유보를 고지하며 두 파일을 가리킨다"(AC-032 + ADR-029 검증 방법)를 **실제 파일로** 확인한다. 이 저장소의 첫 시험이자 회귀 가드다.
- **핵심 개념**: `bun:test` 의 `describe`/`test`/`expect`. `describe` 이름이 추적표 `시험` 칸에 들어가는 이름이다(`docs/traceability.md:44`).
- **코드**: `scripts/check-license.test.ts:6`(루트 경로), `:13-22`(`licenseSection`), `:25-54`(시험 3건)
- **한 줄 해설**
  - `:6` `new URL("../", import.meta.url)` — 이 파일 위치 기준으로 루트를 정한다. 어느 cwd 에서 실행해도 같은 파일을 읽는다(리뷰가 cwd 를 바꿔 확인).
  - `:15` `trimEnd() === "## 라이선스"` — 정확히 이 머리 줄을 찾는다. `:20` `startsWith("## ")` 은 다음 `##` 머리에서 끊되 `###` 는 경계가 아니다(`###` 는 `"## "` 로 시작하지 않는다).
  - `:28` `license.split("\n")[0]?.trim()` — CRLF 로 체크아웃돼도 `\r` 이 떨어지게 `trim()`. `?.` 는 `noUncheckedIndexedAccess` 대응이다.
  - `:40-44` `toBeDefined()` 는 TypeScript 가 타입을 좁혀 주지 않는다. 그래서 `if (section === undefined) return;` 분기로 직접 좁힌다. `!`·`as` 로 덮지 않는 것이 `typescript-strict` 규약이다.
  - `:45-51` 다섯 문자열이 절 텍스트에 **모두** 있어야 통과: `](LICENSE)`·`](CONTENT-LICENSE.md)`·`MIT`·`개인 콘텐츠`·`모든 권리 유보`.
- **의도한 동작**: 읽기만 한다. 쓰기·네트워크·시계·서브프로세스를 쓰지 않는다(`:1-2` 주석).
- **수정 포인트**: README 라이선스 문구를 바꾸면 `:45-51` 의 목록을 같이 바꾼다. 검사 항목을 늘리면 `describe` 안에 `test` 를 더하고 `traceability.md:44` 의 이름은 `describe` 이름을 유지한다.
- **엣지케이스/주의**
  - **한계를 알고 쓸 것**: 부분 문자열 검사라 절 안의 엉뚱한 위치에 단어가 있어도 통과한다. AC-032 의 Then 이 "존재 검사"라서 계획이 정한 수준이다(구현·리뷰 모두 "가장 약한 고리"로 인정).

  - **통과한 시험 이름은 기본 출력에 안 나온다**(Bun 1.4.4, I9). 추적표가 요구하는 "출력에 나타나는 이름"은 `--reporter=junit` 으로 확인한다(`describe` = `classname`).
  - 회귀 가드로서의 증명: README 문구 삭제·README 헤더 변경·`LICENSE` 1행 변경·`CONTENT-LICENSE.md` 이동을 각각 조작했을 때 **해당 시험 하나만** 실패했고 원복 후 `3 pass` 였다.

## 바뀐 과정에서 배울 것

**계획이 두 번 나왔다(`02-plan` → `02-plan-r2`). 계기는 체크포인트 A 에서의 사용자 결정이었다.**

- **r1 의 선택**: TypeScript 를 `6.0.3` 으로 추천했다. 근거는 7.0.2 에 JS API 가 없고(실측), dependency-cruiser 가 7.1 이후부터 지원한다고 적어서였다. 기반 옵션은 설계 01 §4 표 10개 그대로였다. 사용자가 질문에 답하지 않아 잠정 해석 6.0.3 이 유지된 상태였다.
- **무엇이 바꿨나**: 사용자가 "typescript 7 의 사용법은 https://bun.com/docs/typescript-6 으로 정의되어있어. typescript 7 을 우선한다" 고 답했다. 이는 계획 승인이 아니라 **재계획 지시**였다.

  - 7.0.2 정확 고정으로 바꾸고, **r1 의 실측을 승계하지 않고 TS 7.0.2 로 14건을 전부 다시 쟀다.** 그래서 r1 에 없던 사실이 나왔다 — dependency-cruiser 가 에러 없이 `.ts` 0건을 검사하고 종료 0 이라는 조용한 실패(M12), 터미널 `bun check` 가 스크립트로 가로채지는 것(M6), ES2024 API 의 TS2550(M14).

  - 사용자가 "이 문서가 정의한다" 고 한 정본은 **열어 보고** 기존 설계와 값을 대조한다. 한쪽을 임의로 정본으로 삼지 않고 갈리는 곳을 질문으로 올린다.

## "이제 혼자 수정하려면"

- **앱·패키지를 추가한다** → ① 그 디렉토리에 `package.json`(`@pf/<디렉토리명>`)과 `tsconfig.json`(extends `../../tsconfig.base.json`) ② `tsconfig.json:3` references 한 줄 ③ `biome.json:4-11` 허용 목록에 패턴이 있는지. **이 셋(워크스페이스 패턴·references·Biome 허용 목록)은 수동 동기**라 한 곳만 고치면 검사에서 빠진다(계획 위험 R-5). `.gitkeep` 은 지운다.
- **단위 tsconfig 가 다른 단위를 쓴다** → `references` 를 걸지 않고 워크스페이스 패키지명으로 import 한다. 걸면 TS6310.
- **타입 엄격도·언어 수준을 바꾼다** → `tsconfig.base.json:3-17` + `docs/design/01-repository-structure.md` §4 표 + `docs/deviation-log.md`. 단위별 차이는 단위 tsconfig 에서 덮는다.
- **bun 타입이 필요한 단위가 늘었다** → 단위 `tsconfig.json` 에 `"types": ["bun"]`. 빼면 `bun:test`·`Bun` 이 해석되지 않는다.
- **검사를 `check` 에 추가한다** → `package.json:14` 문자열 끝에 ` && bun run <검사>`. 지금 `bun test` 는 `check` 에 들어 있지 않다(결정 A9 — 확인 명령은 `bun test ./scripts`).
- **환경 변수 키를 추가한다** → `.env.example`(`:4-16`) + 설계 02 §5·01 §8. 실제 값은 넣지 않는다. 시험이 env 를 읽기 시작하면 `.env` 자동 로드(위 주의) 때문에 `bun test --no-env-file` 을 검토한다.
- **라이선스 문구를 고친다** → README `## 라이선스` 절과 `scripts/check-license.test.ts:45-51` 목록을 같이.
- **TypeScript 를 올리거나 내린다** → `package.json:19`, `docs/domains/tech-stack.md:24`·`:110`. dependency-cruiser 를 도입하는 S1-5 는 `:105` 의 경고를 먼저 읽는다.
- **런이 끝난 뒤 사람이 할 일(영향분석 권고)**: `.claude/verification.json` 에 `bun run check`·`bun test` 를 넣는다. 지금은 새 가드를 자동으로 돌리는 것이 0개다. 런 중 `.claude/**` 수정 금지라 이번에는 못 했다.

## 더 학습하면 좋은 개념

- **TypeScript project references / `tsc -b`**: 단위별 증분 빌드와 `composite`. TS6310 이 왜 나는지의 배경.
- **`types` 자동 포함**: TS 5.x 는 `node_modules/@types` 를 전부 끌어오고 6 이상은 빈 목록이다. spike g3(TS 5.7.2)가 루트 `@types/bun` 73파일을 새로 끌어온 것이 그 예(진단 변화는 0, I3).
- **Bun 의 `.env` 자동 로드와 `--no-env-file`**: 시험 입력이 기계마다 갈리는 원인.
- **gitignore 의 순서 규칙**: 뒤 줄이 앞 줄을 이긴다. 부정 패턴(`!`)은 순서가 의미다.
- **시험 등급 L1~L4**: "외부 의존이 있으면 L3" 의 판정 질문(`.claude/agent-rules/pipeline-verification/01-grades.md`).
