# 코드 해설 — S1-4 `@pf/db` (풀·트랜잭션·마이그레이션 실행기·권한 적용) + `db:migrate`·`migration:immutable`

> 기준: 작업 트리(미커밋). 이 문서는 코드를 읽고 쓴 것이다 — 시험은 다시 돌리지 않았고, 아래 통과 수치(`bun test` 333·통합 31)는 구현·리뷰 기록을 옮긴 것이다.

## TL;DR — 이 변경을 한 문장으로

- 모든 모듈이 공유할 DB 기반을 새 패키지 `packages/db` 로 만들었다 — 읽기 전용 풀, 쓰기 단위(UnitOfWork), 모듈별 마이그레이션 실행기(동시 실행 잠금 + 끝에 `roles.json` 권한 적용) — 그리고 이를 부르는 `bun run db:migrate` 와, 이미 적용된 마이그레이션이 바뀌지 않았는지 보는 `bun run migration:immutable` 을 더했다.
- 이 변경에서 가장 크게 배울 것은 코드 양이 아니라 **세 번의 교정**이다 — 권한 회수 범위 구멍(r2), 확장 스키마 오회수 방지(r3), 풀 연결 1개일 때 정지(r4). "바뀐 과정에서 배울 것" 절에 있다.

## 전체 그림

`packages/db` 는 이 저장소의 세 번째 제품 패키지다(`kernel` → `config` → `db`). 소비자는 아직 `scripts/db-migrate.ts` 하나이고, 첫 실사용자는 S1-7(앱 조립)·S2-1(첫 제품 모듈)이다. 그래서 이번 범위는 "후속 작업이 코드로 기대는 계약"까지다 — 재시도·지표·`assertUpToDate` 같은 것은 일부러 뺐고 `docs/domains/tech-debt.md` 의 TD-8 에 이유와 담당을 적었다.

읽는 순서는 이렇다. 앱 코드는 `DbPool.read`(select 만 가능)로 읽고, 쓰려면 `PostgresUnitOfWork.run` 안에서 `tx.db` 를 쓴다. 배포 때는 `db:migrate` 가 `runMigrations` 를 불러 모듈 폴더별 SQL 을 순서대로 적용하고 마지막에 `roles.json` 으로 `GRANT`/`REVOKE` 를 건다. 손으로 쓴 SQL(`set_config`, advisory lock, 권한 문장)은 전부 `src/adapter/postgres/raw/` 세 파일에만 있다 — `check-purity` 의 B11 규칙이 `packages/*/src/` 안의 raw SQL 을 막되 이 경로만 예외로 두기 때문이다(체크포인트 A Q1 (A), DV-016).

공개 표면은 9개다: `createDbPool`·`PostgresUnitOfWork`·`runMigrations` + 타입 `DbPool`·`ReadDb`·`TxContext`·`TxOptions`·`UnitOfWork`·`MigrationModule`(`packages/db/src/index.ts:3`). `export *` 를 쓰지 않고 이름을 하나씩 열거한다.

**블록 해설이 7개(상한)인 이유**: 새 패키지 + 스크립트 둘 + 시험 구조가 한 변경이라서다. 문서 수정 9개와 픽스처는 해설하지 않고 `이제 혼자 수정하려면` 에서 위치만 가리킨다.

## 코드 블록별 해설

### [packages/db/src/pool.ts] — 풀과 "열쇠 없는" 공개 타입

- **목적**: 앱이 DB 에 닿는 입구를 만들되, 쓰기 가능한 핸들이 `UnitOfWork` 를 우회해 새지 않게 한다. ADR-025 가 "`DbPool` 이 밖으로 주는 핸들은 읽기 전용"이라고 못박았다(DV-015 는 이와 충돌하던 옛 설계 문서를 고친 기록).
- **핵심 개념**: *WeakMap 손잡이*. 공개 타입 `DbPool` 은 `{ read, close }` 둘뿐이고, 진짜 클라이언트(`Bun.SQL`)와 쓰기 가능한 Drizzle DB 는 모듈 안 `WeakMap`(`pool.ts:24`)에 풀 객체를 키로 보관한다. 패키지 안에서만 `handleOf` 로 꺼낸다.
- **한 줄 해설**:
  - `readOnly`(`pool.ts:28`)는 원본 DB 를 넘기지 않고 `select`·`selectDistinct`·`selectDistinctOn`·`$count` 네 개만 `bind` 해 `Object.freeze` 한 새 객체를 만든다. 타입으로만 막으면 런타임에 `insert` 가 살아 있으므로 실제로 안 들어 있게 했다. `with(...)` 도 뺀 이유는 CTE 에서 insert·update·delete 를 돌려주기 때문이다(주석 `pool.ts:26`).
  - `createDbPool`(`pool.ts:37`)은 `new Bun.SQL(url)` 로 클라이언트를 만든다. Bun.SQL 은 첫 쿼리 전엔 연결하지 않으므로 풀 생성 자체는 I/O 가 없다.
  - `handleOf`(`pool.ts:50`)는 `createDbPool` 이 만들지 않은 객체(가짜 풀)면 `Err` 를 낸다.
- **의도한 동작**: 소비자가 `pool.read.insert` 를 쓰면 컴파일 에러이고(`@ts-expect-error` 시험), 우회해도 런타임에 메서드가 없다(`packages/db/test/read-db.test.ts`).
- **수정 포인트**: 읽기 메서드를 더하려면 `ReadDb` 타입 `Pick` 목록(`pool.ts:7`)과 `readOnly` 의 `bind` 목록을 **둘 다** 고친다 — 한쪽만 고치면 타입은 통과하는데 런타임에 `undefined` 이거나 그 반대다.
- **엣지케이스/주의**: 시험이 가짜 풀을 쓰려면 `{ read, close }` 만 흉내 내면 되지만 `runMigrations`·`run` 은 거절한다(`validation.test.ts:94`). 이것은 버그가 아니라 설계다.

### [packages/db/src/unit-of-work.ts] — `PostgresUnitOfWork.run`

- **목적**: "트랜잭션을 열고, 시간 제한을 걸고, fn 이 `Ok` 면 커밋·`Err` 면 롤백" 을 한 곳에서 한다. 재시도·지표·로그는 책임이 아니다(TD-8 8-1).
- **핵심 개념**: *Result 와 예외의 분리*. 이 저장소는 예상 가능한 실패를 `Err` 값으로, 예상 못 한 실패를 예외로 다룬다. `run` 의 반환은 `Result<T, E | PermanentError>` 로, fn 이 낸 `Err(E)` 는 그대로 돌려주고 DB 예외는 `PermanentError` 로 감싼다.
- **한 줄 해설**:
  - 롤백(`unit-of-work.ts:85`~`:94`): Drizzle 은 콜백이 예외를 던져야 롤백한다. 그래서 fn 이 `Err` 를 돌려주면 `rolledBack.failure` 에 실제 `Err` 를 보관하고 내부 표지 `RollbackSignal`(`:43`)을 던진다. 바깥 `catch` 가 그 표지를 보면 보관한 `Err` 를 돌려준다. 표지가 아닌 예외는 `PermanentError`(`:99`)다. `tx.rollback()` 은 쓰지 않는다 — 예외가 되어 `PermanentError` 로 오분류된다(주석 `:20`).
  - 중첩 금지(`:71`): `AsyncLocalStorage`(`:40`)로 "지금 run 안인가"를 비동기 맥락 따라 본다. 전역 불리언이면 `Promise.all` 로 동시에 도는 두 `run` 을 중첩으로 오인한다.
  - 시간 제한(`:59`~`:63`): `timeoutMs` 가 안전 정수이고 `0 < t ≤ 2147483647` 이어야 한다. 상한은 `tx-settings.ts:9` 의 `MAX_STATEMENT_TIMEOUT_MS` 이고 Postgres 정수 설정 값의 한계다. DB 까지 가기 전에 `PermanentError` 로 끝난다(r2 에서 추가).
  - `txSettings`(`raw/tx-settings.ts:14`)는 `set_config(이름, 값, true)` 로 `statement_timeout`·`idle_in_transaction_session_timeout`·`lock_timeout` 을 건다. `SET LOCAL` 은 바인드 값을 못 받아서이고, 세 번째 인자 `true` 가 "트랜잭션 로컬"이라 커밋·롤백 뒤 세션 값이 원복된다.
- **수정 포인트**: 기본 5초·10초·2초는 `tx-settings.ts:7`~`:11` 의 상수이고 값의 근거는 F16 §8.2(새 수치를 만들지 않았다). `TxContext` 에 필드를 더하려면 `unit-of-work.ts:29` 와 `:88` 의 `fn({ db: tx, now })` 를 함께 고친다. `tx.db` 는 `rollback`·`setTransaction` 이 제거된 타입(`:25`)이다.
- **엣지케이스/주의**: `now` 는 `run` 시작 때 한 번 고정된다(`:87`) — fn 안에서 시간이 흐르지 않는다. 문서(F16 §3.4)가 옛 이름 `tx.query` 를 쓰던 것을 r4 가 `tx.db` 로 고쳤다.

### [packages/db/src/migrations.ts] — `runMigrations`, 잠금, 풀 상한 검사

- **목적**: 받은 모듈 목록을 받은 순서대로 순방향 적용하고(롤백 없음), 끝에 권한을 적용한다. 동시에 두 실행기가 돌지 않게 막는다.
- **핵심 개념**: *advisory lock 과 예약 연결*. Postgres 의 세션 단위 advisory lock 은 "그 연결(세션)"에 걸린다. 연결 풀에서 아무 연결로 잠그고 풀면 다른 연결이 잡혀 잠금이 새거나 안 풀린다. 그래서 `client.reserve()` 로 연결 하나를 풀에서 빼 그 연결에서만 걸고 푼다(`migrations.ts:139`~`:154`, `raw/migration-lock.ts`). 잠금 키는 `hashtext('pf-migrate')` 로 SQL 에서 만든다 — 코드에 마법 수가 없다.
- **한 줄 해설**:
  - 순서(`:156`~`:197`): 모듈 이름 검증 → 권한 명세 검증 → 풀 확인 → **풀 상한 검사** → 잠금 안에서 `applyModules`(`:78`) → `applyGrants`(`:98`). 앞의 검증은 전부 DB 입출력 전에 끝난다.
  - `applyModules` 는 모듈마다 Drizzle `migrate` 를 부르고 이력 표는 `pf_migrations.<모듈이름>` 으로 갈라 둔다(`:24`, `:86`) — 기본 이력 표를 공유하면 모듈을 건너뛴다. 첫 실패에서 멈추고 뒤 모듈과 권한은 적용하지 않는다.
  - `validatePoolSize`(`:64`): `client.options.max` 가 정해져 있고 2 미만이면 연결 전에 `stage: "pool"` 로 거절한다. 하한 상수는 `MIN_POOL_CONNECTIONS = 2`(`:27`).
- **의도한 동작(왜 2 인가)**: 잠금용으로 연결 1개를 예약하고(`:143`), 그 상태에서 `work()` 안의 `migrate`·`applyGrants` 가 **같은 풀에서 둘째 연결**을 요구한다. 상한이 1 이면 예약이 풀을 다 쥐어 둘째를 영원히 기다린다 — 잠금을 쥔 채 출력도 종료 코드도 없이 멈추고 뒤의 실행기까지 함께 선다. 이것이 r4 가 닫은 결함이다.
- **수정 포인트**: 검사 위치를 `withMigrationLock` 안으로 옮기지 않는다 — 예약(`:143`) **앞**(`:175`)이어야 잠금을 쥐기 전에 끝난다. 하한을 올리거나 내리면 L2 시험 `validation.test.ts:107`(상한 1 거절·2 통과)과 L3 ⑧(`packages/db/test/integration/migrations.test.ts:254`)이 경계 양쪽에서 걸린다.
- **엣지케이스/주의**:
  - `options.max` 는 Bun.SQL 의 공개 속성이다. Bun 이 올라 이름이 바뀌면 검사가 **조용히 통과**하지만 L2 `max=1` 사례가 그날 빨강을 낸다(구현 기록의 논리 — 실제 Bun 업그레이드로 확인한 것은 아니다).
  - `max` 를 안 주면 Bun 기본값(10)이라 통과한다. `?max=1.5` 같은 비정수도 2 미만이라 거절된다.
  - 잠금 대기에는 시간 상한이 없다(TD-8 8-6).

### [packages/db/src/adapter/postgres/raw/grants.ts + migrations.ts `applyGrants`] — 선언적 권한 적용

- **목적**: `packages/db/roles.json`(정본: 관리 역할 3개·표 0개)의 선언대로 권한을 맞춘다. 두 번 돌려도 같고, 명세에서 뺀 권한은 사라지는 것이 계약이다(계획 D-9).
- **핵심 개념**: *회수 먼저, 부여 나중*. `schemaStatements`(`grants.ts:53`)는 스키마마다 `revoke all on schema …`·`revoke all on all tables in schema …` 를 `PUBLIC` + 관리 역할 전부에게 먼저 걸고(`:62`~`:63`), 그다음 `USAGE`·표별 `GRANT` 를 준다. 그래서 반복 적용이 멱등이다.
- **한 줄 해설**:
  - `grantStatements(spec, ownedSchemas)`(`:89`)의 회수 대상은 `접속 역할이 소유한 스키마 ∪ 명세의 스키마` 이름순이다. 명세에 표가 없는 스키마는 회수 두 문장만 나간다.
  - `ownedSchemasQuery`(`:19`)는 카탈로그(`pg_namespace`)에서 접속 역할 소유 스키마를 읽되 `pg_*`·`information_schema`, 그리고 **확장이 관리하는 스키마**(`pg_depend` 의존 종류 `e`, `pg_extension.extnamespace`)를 뺀다.
  - 식별자는 전부 `sql.identifier`, 권한어는 화이트리스트(`SELECT`·`INSERT`·`UPDATE`·`DELETE`)라 명세 문자열이 SQL 에 이어 붙지 않는다(`roles-spec.ts:5`, `:25`).
  - `applyGrants`(`migrations.ts:98`)는 한 트랜잭션에서 ① 접속 역할이 `roles` 에 들어 있으면 거절(소유자가 자기 권한을 회수해 다음 마이그레이션이 막힌다) ② 소유 스키마 조회(`:114`) ③ 문장 실행을 한다.
- **의도한 동작**: 마이그레이션이 만든 스키마도, 명세에서 표를 전부 뺀 스키마도 PUBLIC·관리 역할 권한이 걷힌다.
- **수정 포인트**: 권한을 더하는 평소 작업은 코드가 아니라 `packages/db/roles.json` 의 `tables` 에 `"<스키마>.<표>": { "<역할>": ["SELECT", …] }` 를 적는 것이다. 새 권한어(예: `TRUNCATE`)는 `roles-spec.ts:5` 목록과 시험을 함께 고친다. 시퀀스·함수 권한은 TD-8 8-4.
- **엣지케이스/주의**:
  - **m-3(알려진 잔여 결함, 사용자가 남기기로 함)**: 확장을 *업무 스키마에 설치*하면 그 스키마는 `extnamespace` 로 제외되어, 명세에서 빠져도 관리 역할의 표 권한까지는 자동 회수되지 않는다. 명세에 적힌 스키마는 확장 스키마여도 회수된다. 설계 문서에 계획된 확장이 0개라 지금 발생 경로는 없다. 리뷰가 제안한 TD-8 **8-10** 행은 아직 추가되지 않았다.
  - 역할 *목록에서 뺀* 역할의 기존 권한은 못 걷는다(명세가 이름을 더는 모른다) — 사람이 `DROP OWNED BY` 후 `DROP ROLE`(TD-8 8-7).
  - 역할이 클러스터에 없으면 마이그레이션은 커밋되고 권한 단계에서 종료 1이다(TD-8 8-8). 역할 생성 SQL 은 사용자 결정(Q4)으로 이 작업의 범위 밖이다.

### [scripts/db-migrate.ts] — `bun run db:migrate`

- **목적**: 배선만 한다. 설정 읽기 → 모듈 탐색·거르기 → `roles.json` 읽기 → 풀 → `runMigrations` → 종료 코드. 마이그레이션 로직은 여기 없다.
- **한 줄 해설**:
  - 종료 코드: 0 성공 · 1 실행·인자 오류(모르는 모듈은 연결 전에 끝) · 78 설정 오류(`@pf/config` 의 `exitCodeFor`). 값(연결 주소)은 출력하지 않고 이름·사유만 낸다(`db-migrate.ts:98`).
  - `discoverModules`(`:21`)는 `modules/<이름>/migrations/meta/_journal.json` 이 있는 폴더만 모듈로 본다. 저널이 없으면 "마이그레이션 없음"이다.
  - `selectModules`(`:40`)는 인자가 없으면 전부, 있으면 요청 순서·중복 제거로 고르고 모르는 이름이 하나라도 있으면 목록을 돌려준다.
  - `import.meta.main`(`:146`) 가드 덕에 시험이 `discoverModules`·`selectModules` 를 임포트해도 `main` 이 돌지 않는다.
- **수정 포인트**: 새 옵션은 `parseModuleArgs`(`:62`)의 `parseArgs` 에서 고친다(지금 `options: {}`, `strict`). 실행기 결과 문구는 `:126`~`:133`. `package.json:16` 이 `bun --env-file=.env` 로 로컬 `.env` 를 읽는다 — 루트 `bunfig.toml` 이 `env = false` 라 자동으로는 안 읽힌다.
- **엣지케이스/주의**: 로컬 템플릿 `.env.example` 은 `DATABASE_URL_*` 넷만 갖고 `db:migrate` 는 `DATABASE_URL` 하나만 읽어 **그대로는 종료 78** 이다(TD-8 8-9, S1-7 몫). 성공 경로(설정→실행기→종료 0)에는 자동 시험이 없고 수동 L3 한 번으로 확인했다(계획이 가장 약한 고리로 신고).

### [scripts/check-migration-immutable.ts] — 적용된 마이그레이션이 안 바뀌었는지

- **목적**: 이미 배포된 마이그레이션 SQL·저널을 PR 이 몰래 고치지 못하게 한다. CI 배선은 S1-6 이고 지금은 로컬 `bun run migration:immutable [--base <ref>]` 다.
- **핵심 개념**: *Drizzle 은 SQL 해시를 비교하지 않는다.* 마지막 적용 행의 `created_at` 이 저널 `when` 보다 작은 항목만 실행한다(조사 기록). 그래서 적용된 `.sql` 을 고쳐도 조용히 무시되고, 저널의 `when` 이 새 항목에서 거꾸로 가면 그 항목이 **영원히 건너뛰어진다**. 이 검사는 그 둘을 막는다.
- **한 줄 해설**:
  - 판정(순수 함수)과 git 호출(얇은 층)을 가른다. 판정은 `judgeMigrationChanges`(`:126`)이고 입력은 변경 목록과 모듈별 기준·HEAD 저널이라 git 없이 시험된다.
  - 규칙 6개(`:26`): `.sql` 수정·삭제, 저널 삭제·재작성(기준 항목의 idx·tag·when 이 바뀜), 새 항목 순서 위반(`MI-journal-order`), 새 항목이 기준 마지막보다 오래됨(`MI-journal-stale`). `.sql` 추가(`A`)만 허용한다(`:54`).
  - 비교 기준은 `merge-base(기준, HEAD)..HEAD` 의 **커밋된** 변경이다(`:224`~`:234`). 작업 트리의 미커밋 변경은 보지 않는다(PR 의 의미).
  - 저널을 읽을 수 없으면 조용히 통과하지 않고 던진다(`readJournal` `:195`, 종료 1).
- **수정 포인트**: 규칙을 더하면 `IMMUTABLE_RULE_IDS`(`:26`)와 시험의 "규칙 ID 는 여섯 개다"(`scripts/check-migration-immutable.test.ts:189`)를 함께 고친다. 대상 경로 정규식은 `:36`~`:37` — ADR-052 의 `modules/<m>/migrations/` 배치에 묶여 있다.
- **엣지케이스/주의**: 한계는 파일 머리말(`:3`)에 있다 — 저널 항목의 `(idx·tag·when)` 접두 일치만 보고 `.sql` 내용의 의미는 보지 않는다. CI 얕은 checkout 이면 merge-base 가 없어 던진다(TD-4 H-5, S1-6 이 `fetch-depth: 0` 으로 해결).

### [bunfig.toml · packages/db/test/integration/job-double.test.ts] — 통합 시험의 분리와 "관찰이 위반을 구별한다"는 증명

- **목적**: 실제 DB 가 필요한 시험(L3)을 평소 `bun test`(L2)에서 빼면서, 빠뜨리지 않고 돌릴 길을 둔다.
- **한 줄 해설**:
  - `bunfig.toml:8`~`:9` 의 `[test] pathIgnorePatterns = ["**/test/integration/**"]` 가 평소 `bun test` 에서 통합 시험을 뺀다. `[test]` 표는 최상위 `env = false`(파일 첫머리) **뒤**에 둬야 한다 — 표 안에 `env` 가 들어가면 효과가 없다고 파일 주석이 적는다.
  - `package.json:18` `test:integration` 은 `--path-ignore-patterns='**/node_modules/**'` 로 그 목록을 **덮어써서** 통합 시험만 돌린다. `TEST_DATABASE_URL`(슈퍼유저로 접속하는, 버려도 되는 Postgres)이 없으면 **건너뛰지 않고 실패**한다(`support.ts:30`) — 조용히 초록이 되는 것을 막으려는 선택이다.
  - 시험 파일마다 새 DB(`pf_t_<무작위>`)를 만들고 지운다.
  - AC-023 "잡 쓰기가 tx 안에서 일어난다"는 잡이 아직 없어 **대역**으로 본다(사용자 답 Q1·Q6, 대역은 `packages/db/test/` 안). 대역이 게이트에서 멈춘 동안 *다른 연결*이 그 행이 보이는지(`:77`)와 `pg_stat_activity` 가 `idle in transaction` 인지를 본다(`:139`~`:151`) — 멈춤이 결정적이라 타이밍 우연이 없다.
  - 같은 관찰 함수에 **대조군**(자동 커밋 대역, `:117`)을 넣어 반대 판정(보임·`idle`)이 나오는 것을 상시 시험으로 둔다(`:180`). 관찰 수단이 위반을 구별한다는 증명이 매 실행에 남는다.
- **수정 포인트**: 통합 시험을 더하려면 `*/test/integration/` 아래에 두면 된다. 픽스처 모듈(alpha·beta·broken)은 `packages/db/test/fixtures/modules/` 이고 `_journal.json` 은 손으로 탭 들여쓰기로 썼다 — drizzle-kit 이 생성하면 공백 2칸이라 Biome 과 충돌할 수 있다(TD-8 8-5, S2-1 몫).
- **엣지케이스/주의**: 패키지 디렉토리에서 `bun test` 를 돌리면 `bunfig.toml` 이 cwd 범위라 통합 시험이 잡혀 7개가 실패한다(영향분석 P-5, 기록만). 루트에서 돌린다. 이 L3 가드 30여 건과 `migration:immutable` 은 아직 `.claude/verification.json` 의 고정 매니페스트에 없어 자동 게이트 밖이다(영향분석 P-4, 런 뒤 사람 몫).

## 바뀐 과정에서 배울 것

구현이 네 번(r1~r4), 리뷰가 세 번(r1~r3) 돌았다. 요구사항도 한 번 바뀌었다(00-r2: Q1 답 "잡 대역을 만들어 L3 까지"로 AC-023 L3 가 범위에 들어옴).

| 사이클 | 처음 상태 | 지적 | 교정 |
|---|---|---|---|
| r1 → 리뷰 r1 🔴 | 권한 회수 대상을 **명세의 스키마에서만** 도출 | **M-1(보안)**: 스키마의 마지막 표를 명세에서 빼면 그 스키마의 `USAGE`·표 권한이 회수되지 않는다 — 계획 D-9 "파일에서 뺀 권한은 사라진다"가 같은 스키마 안에서만 성립. 일회용 `postgres:18` 재현. **m-1**: `timeoutMs` > 2147483647 이 입력 검증을 통과해 DB 에서 일반 오류. **m-2**: 목록에서 뺀 역할의 권한 잔존 | r2: 회수 대상 = 소유 스키마 ∪ 명세 스키마, 상한 상수, m-2 는 코드로 못 닫는 구조라 TD-8 8-7 로 문서화 |

여기서 얻는 교훈:

- **계약 문장은 그 경계에서 시험해야 한다.** "빼면 사라진다"는 계약을 시험이 "표 하나를 뺀다"까지만 덮었고, "마지막 표를 뺀다"는 경계가 비었다. 리뷰도 FP10a(되돌림 증명)의 한계가 M-1 의 공백과 같다고 짚었다. 계약을 쓸 때 "대상을 어디서 도출하는가"(입력만? 현재 상태도?)를 먼저 묻는다.
- **외부 시스템의 한도를 입력 검증이 알아야 한다.** DB 쪽 정수 상한을 모르면 입력 오류가 "예기치 않은 오류"로 둔갑한다.
- **"가져오는 연결 수"는 숨은 전제다.** 같은 풀에서 하나를 쥔 채 또 하나를 요구하는 패턴은 풀이 작으면 교착이다. 계획의 D-8 에 "연결 ≥ 2" 가 적혀 있지 않았다. 자원 전제는 문서와 **연결 전 검사**로 남긴다.
- **자동으로 대상을 모으는 범위를 넓히면 "내 것이 아닌 것"까지 건드린다.** 제외 기준은 이름 목록이 아니라 카탈로그로 가른다(확장·버전마다 스키마가 달라서).
- **고치려는 범위가 정해져도 "같은 패턴의 다른 자리"를 `grep` 으로 센다** — r2·r3·r4 모두 같은 패턴이 더 없음을 확인하고 닫았다.
